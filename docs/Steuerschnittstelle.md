# Control interface

The control interface lets an external agent or a test script play QtCraft like a human player and observe the game in structured form. It is a client of the normal protocol: commands drive a `QcClientSession`, which talks to the server only through protocol messages. There is no shortcut around the server.

## Transport

Newline-delimited JSON (one request object per line, one response object per line).

| Mode | How to start | Notes |
|------|--------------|-------|
| Standard input/output | `qtcraft-headless` | Requests on stdin, responses on stdout, logs on stderr. EOF or `quit` ends the process. |
| Script | `qtcraft-headless --script file.jsonl` | Runs all requests in order and exits with code 0 if every request succeeded, 1 otherwise, 2 on time limit. Lines starting with `#` are comments. |
| Bot on a server | `qtcraft-headless --join host:port --player-name Name [--password p]` (with either of the above) | The bot joins a server over TCP (a dedicated server or a game opened to the network) instead of starting a world in-process (decision E-270). Its identity on the server is the key in `<data>/player.key` (`--data-dir`; made on first use), the password also comes from `QTCRAFT_SERVER_PASSWORD`, `--view-distance` is the wished view distance. `joined '<server name>'` on stderr once the server let it in; the requests start then. Exit code 3 when the join fails (`join failed: <reason>` on stderr: no connection, wrong password, other content, the name belongs to another key, banned, full), 4 when the server ends the connection later (`disconnected: <reason>`). The world commands (`worldList`, `worldCreate`, `worldLoad`, `worldSave`, `console`) are refused; operator commands go through `chat` and need operator rights on that server. Leaving (`quit`, end of input) says goodbye, so the server saves the player at once. |

The interface is **off by default**: the graphical game does not open it. It only exists in processes started explicitly with the options above and never listens on a network port. A local socket in the graphical game (e.g. `--control local:<name>`) is not implemented; it would only forward the same lines.

`qtcraft-headless` options: `--console` (a server console instead of the control interface, see below), `--no-eof-stop` (with `--console`: the end of standard input does not stop the server), `--seed <n>`, `--world <name>`, `--view-distance <chunks>` (default 4), `--time-limit <seconds>` (default 120), `--script <file>`, `--data-dir <dir>` (data directory like `QTCRAFT_DATA_DIR`: `worldCreate`/`worldLoad` keep worlds in `<dir>/worlds`, mods come from `<dir>/mods`; default: the game's own data directory), `--mods-dir <dir>` (overrides the mods directory), `--no-mods`, `--generator terrain|flat|void|showcase` (world type of the throw-away world started at once; default terrain), `--generator-options <options>` (its options: the layers of a flat world, e.g. `bedrock,3*dirt,grass_block`, or the platform of a void world, e.g. `platform=glass,radius=4,y=40`; invalid ones, or options for a type that takes none, end the start with exit code 1), `--showcase-tour` (prints the camera stops of the showcase screenshot tour, one `name x z yaw pitch` per line, and exits; used by `scripts/showcase-tour.sh`), `--export-sounds <dir>` (writes every sound and the music piece of `--seed` as WAV files and exits), `--export-handbook <dir>` with optional `--language <locale>` (writes the handbook of the base game, with `--mods-dir` also of those mods, as Markdown and exits; problems go to stderr), `--export-handbook-web <dir>` (the same handbook in every language as the data of the web handbook `web/handbook`, with the icon sheet and colours; exits). Without a world command the bot plays a throw-away world that is not saved.

## Requests and responses

Every request is an object with `cmd` and an optional `id`, which is echoed in the response. Parameters are type-checked (numbers, booleans); a line that is not a JSON object is answered with an error mentioning its line number, in order with the other responses. Successful responses contain `"ok": true`; failures contain `"ok": false` and `"error"`. Commands that take time (`move`, `jump`, `wait`, `waitUntilReady`) answer when they complete and report the player status at that moment. Requests are processed strictly one after another.

### Player status

Returned by `status` and by all tick-based commands:

```json
{"ok":true,"state":"Playing","tick":63,"world":"Headless","seed":"0",
 "position":[1.7,68,0.5],"velocity":[0,0,0],"onGround":true,"inWater":false,
 "yaw":90,"pitch":0,"loadedChunks":81}
```

Additional fields: `flying`, `riding` (id of the minecart the player rides, or `null`; decision E-382), `largestCorrection` (the largest distance in metres the server moved the predicted player since the session began; riding and getting in or out are no corrections), `gameMode` (`survival` or `creative`, decision E-282), `health`, `maxHealth`, `dead`, `burning` (the player is on fire, decision E-393), `food`, `maxFood`, `experienceLevel`, `experiencePoints` (towards the next level) and `experienceForNext` (points the next level needs; decision E-398), `worldTime` (seconds; a day lasts 600 s), `night`, `weather` (decision E-395: `rain` and `thunder` strengths 0–1 as shown, `precipitation` falling at the eye's height in the open (`rain`, `snow` or `none`; `none` also in a dry biome), the climate where the player stands (`dry`, `snowFrom`: the height from which it snows) and `strikes`, the lightning seen since the session began), `targetEntity` (id of the creature under the crosshair), `target` (the block the player looks at within 5 m: `x`, `y`, `z`, `face`, `block`), `selectedSlot`, `held` (`{"item","count"}` or `null`) and `messages` (chat lines received while the request ran).

`position` is the centre of the player's feet in metres (1 block = 1 m). `yaw` 0 looks north (-Z), 90 east (+X), 180 south (+Z); `pitch` is positive upwards. `state` is one of `Connecting`, `Loading`, `Playing`, `Disconnected` (then `disconnectReason` is set). `tick` counts client simulation ticks (20 per second).

### Commands

| Command | Parameters | Effect |
|---------|-----------|--------|
| `status` | – | Player status. |
| `waitUntilReady` | `timeoutPolls` (50 ms each, default 1200) | Waits until the session plays, the 3×3 chunks around the player are loaded and the player stands or swims. |
| `look` | `yaw`, `pitch` (degrees) | Sets the view direction. |
| `move` | `forward`, `strafe` (-1..1), `jump`, `sneak`, `sprint` (bool), `ticks` (default 20) | Applies the movement intent for the given number of ticks, then stops. |
| `jump` | `ticks` (default 2) | Jumps (same as `move` with `jump: true`). |
| `fly` | `on` (bool, default `true`) | The wish to fly, as after a double tap of jump (decision E-284); fails outside the creative mode. While flying, `move` with `jump` rises, with `sneak` sinks, with `sprint` flies twice as fast; landing ends the flight. Answers after 2 ticks. |
| `gamemode` | optional `mode` (`survival`, `creative`) | Without `mode` the player status (with `gameMode`); with it sends `/gamemode <mode>` (an operator command) and answers once the server reported the new mode, or fails with a timeout (the refusal is in `messages`). |
| `wait` | `ticks` (default 20) | Lets time pass. |
| `block` | `x`, `y`, `z` | Name of the block at a position (`null` if not loaded), its `state` (property → value, e.g. `{"facing":"east","half":"bottom"}`, empty for blocks without states) and `blockLight` (0–15, computed from the light sources around it). |
| `blocks` | `radius` (0..8, default 3) | All non-air blocks in a cube around the player's feet: `[{"x":..,"y":..,"z":..,"block":"qtcraft:stone"}]`; blocks with states also carry `state`. |
| `lookAt` | `x`, `y`, `z` | Turns towards the centre of a block. |
| `mine` | optional `x`, `y`, `z`; `maxTicks` (default 400) | Looks at the block (or keeps the current target) and mines until it is gone. The server checks the mining time; drops go into the inventory. |
| `place` / `use` (also eats held food when hungry, opens crafting tables, furnaces and chests, opens and closes doors, trapdoors and gates; an empty bucket aims at liquids and takes a source, a full one pours it; a clicked tall grass is replaced) | optional `x`, `y`, `z`, `face` (`east`, `west`, `up`, `down`, `south`, `north`, default `up`) | Looks at the centre of that face and uses the held item on it, which places a block next to it; the server derives its state (facing from the view, upper or lower half from the face, attachment towards the clicked block). Answers after 4 ticks; check the block and its state with `block`. |
| `ignite` | `x`, `y`, `z`, `face` as for `use` | Selects the first item of the hotbar that lights fire (flint and steel, decision E-393) and uses it like `use`: fire appears in front of the face where fire may stand. Fails without such an item in the hotbar. Check the cell with `block`. |
| `select` | `slot` (0–8) | Selects a hotbar slot; answers with the inventory. |
| `inventory` | – | `{"selectedSlot":0,"slots":[{"slot":0,"item":"qtcraft:dirt","count":3}],"craftingSize":2,"craftingGrid":[...],"craftingResult":null}` |
| `moveItem` | `from`, `to` (0–35 inventory, 36–44 crafting grid, 3 per row; 2 × 2 uses 36, 37, 39, 40; 45–47 the open machine's input, fuel and output, or 45 onwards the slots of an open chest), optional `count` (0 = whole stack) | Moves, splits or merges stacks. The machine's fuel slot takes only fuel, its output nothing. |
| `openMachine` | `x`, `y`, `z` | Looks at the block and uses it; answers with the machine state once the server opened it, fails when the block is out of reach, hidden or no machine. Works for chests too. |
| `machine` | – | State of the open machine: `{"open":true,"position":[x,y,z],"category":"smelting","input":{"item","count"},"fuel":…,"output":…,"burn":0.8,"progress":0.25}` (`burn`: share of the current fuel left, `progress`: share of the current item done; empty slots are `null`), or `{"open":false}`. For a chest: `{"open":true,"position":[x,y,z],"chest":true,"slots":[stack or null, …]}`. |
| `fillMachine` | `item`, optional `into` (`input` default, or `fuel`), `count` (0 = whole stack) | Moves the first inventory stack of that item into the open machine; answers with the machine state. |
| `takeOutput` | optional `count` | Moves the output into a matching stack with room or an empty inventory slot; answers with the machine state. |
| `closeMachine` | – | Closes the machine screen (the server also closes it when the player walks away, dies or the block is broken). |
| `openTrade` | `entity` | Looks at the villager and uses it; answers with `trades` once the server opened its trading screen (decision E-414), fails when it is out of reach or does not trade now (no profession, asleep, fleeing, another player trading with it). |
| `trades` | – | The open trading screen: `{"open":true,"villager":12,"profession":"profession.qtcraft.smith","level":2,"experience":30,"levelStart":10,"levelEnd":70,"offers":[{"index":0,"costs":[{"item","count"},…],"result":{"item","count"},"uses":1,"maxUses":12,"affordable":true},…]}` (costs at the current price), or `{"open":false}`. |
| `trade` | `offer` (index), optional `repeat` (`true`: as often as the inventory and the uses allow, like shift-click) | Asks the server to trade; answers with `trades` after 3 ticks (a refused trade changes nothing). |
| `closeTrade` | – | Closes the trading screen (the server also closes it when the player walks away or dies, or the villager flees, sleeps or dies). |
| `takeResult` | – | Takes the crafting grid's result once into the inventory. |
| `creativeItem` | `item`, optional `slot` (0–35, armour 100–103; default: into the inventory, hotbar first), `count` (default a full stack) | Creative mode: a stack from the catalogue of all items (decision E-283); onto the same item up to the stack size, else replacing the slot. Without `item` the slot is cleared. The server refuses it in other modes (the inventory stays). Answers with the inventory after 3 ticks. |
| `pickBlock` | optional `x`, `y`, `z` | Looks at the block (or keeps the current target) and picks it like the middle mouse button (decision E-285): selects its item in the hotbar, swaps it in from the storage rows, or in creative mode takes a full stack from the catalogue. Answers with the inventory. |
| `closeCrafting` | – | Puts the grid's items back into the inventory and leaves a crafting table's 3 × 3 grid. Items in the grid are also kept when the player disconnects or the world is saved. |
| `recipes` | optional `all` (bool) | Recipes the inventory can make now (or all): `recipe`, `result`, `count`, `needs`, `needsCraftingTable`, `possible`. |
| `craft` | `recipe`, optional `count` (1–64) | Crafts directly from the inventory (recipe book). 3 × 3 recipes need a crafting table within 5 m. The result appears in `messages` and the inventory. |
| `sounds` | optional `clear` (bool) | The last 64 sound cues (oldest first), each `{"key","origin":"server"\|"local","position","volume","pitch","tick","known","distance","gain","pan"}` (`gain` and `pan` as heard from where the player is now; `distance`, `gain`, `pan` only for sounds the content defines), and `"ambience":{"wind","cave","water","rain"}` (current loop levels 0–1). With `clear` the list is emptied after answering. The headless bot plays no audio; scenario tests use this to check sounds. |
| `mods` | – | Content packs the server loaded, base game first: `{"packs":[{"id","name","version"}]}`. |
| `handbook` | optional `language` (default `en`; only languages the content has, others fail), and one of `entry` (an entry id such as `block:qtcraft:iron_ore` or a content name such as `iron_ore`, `qtcraft:zombie`), `search` (text), `category` (`playing`, `blocks`, `parts`, `liquids`, `items`, `tools`, `food`, `creatures`, `biomes`, `worldgen`, `tags`, `tables`) | The handbook built from the loaded content (only in `qtcraft-headless`). Without parameters: `{"categories":[{"id","title","count"}],"entries":n,"problems":[…]}`. `entry`: `{"entry":{"id","name","category","categoryTitle","pack","packName","title","icon","text","facts":[{"label","value","links"}],"sections":[{"title","text","links","recipes"}]}}` with links `{"target","text","icon","note"}` and recipes `{"kind":"crafting"\|"machine","name","shapeless","needsTable","width","height","cells","result","count","seconds","machines","note"}` (empty cells are `null`); `search`: `{"results":[{"id","title","icon","category","pack"}]}` (best first, titles in the language and in English); `category`: `{"entries":[…]}`. Unknown entries or categories fail. |
| `chatLog` | optional `clear` (bool) | Every chat line received so far, oldest first, also those that came while no request ran (at most 200): `{"lines":[…]}`; with `clear` the log is emptied after answering. Other players' lines read `<Name> text`. |
| `players` | – | Everyone on the server: `{"players":[{"name","entity","operator"}]}` (the server's `PlayerList`). |
| `appearance` | optional `outfit`, `hair`, `cape` (content names; `""` for no hair or cape), `skinColor`, `hairColor`, `shirtColor`, `pantsColor` (`"#rrggbb"`) | Changes the given parts of the own look and sends it to the server, which checks it and shows it to the others; answers with the whole look as sent (a look the server refuses stays the old one for the others). |
| `chat` | `text` | Sends a chat line or a command; server replies appear in `messages`. The bot is the local player and therefore an operator (decision E-243); its chat is not rate limited. A bot that joined a server with `--join` is an ordinary network player there: operator only when the server made it one, chat rate limited like everyone's. All commands with their usage: `/help`, `/help <command>` and the handbook chapter Commands (`docs/handbook/playing.md`). Among them: `/give`, `/summon` (creatures, `armor_stand`, and `minecart`, `chest_minecart`, `hopper_minecart` with an optional count: in a row from 3 m ahead, on a rail there or below, E-393), `/time`, `/gamerule`, `/setblock <x> <y> <z> <block>` (`~` or `~n` relative to the player's feet; the block may carry a state, `oak_stairs[facing=east,half=top]`, otherwise connections follow the neighbours), `/fill <x1> <y1> <z1> <x2> <y2> <z2> <block> [replace <block>]` and `/clear …` (at most 32768 blocks; more than 4096 wait for `/confirm`), `/regenerate`, `/remove`, `/tp`, `/backup`, `/worldinfo`, `/tick`. Destructive commands answer with a request to `/confirm` within 30 s (decision E-245). |
| `worldList` | – | `{"worlds":[{"folder","name","seed","generator","error"}]}` (`generator`: `terrain`, `flat`, `void` or `showcase`) |
| `worldCreate` | `name`, optional `seed` (integer; random when omitted), optional `generator` (`terrain`, default, `flat`, `void` or `showcase`; E-220, E-223), optional `options` (the layers of a flat world, e.g. `"bedrock,3*dirt,grass_block"`, or the platform of a void world, e.g. `"platform=glass,radius=4,y=40"`; refused when invalid or longer than 4096 characters; the world stores the defaults of its type as they are when it is created), optional `gameMode` (`survival`, default, or `creative`: the mode of players who join for the first time, decision E-282) | Creates a saved world and switches to it; answers with its `folder`. Follow with `waitUntilReady`. |
| `worldLoad` | `folder` | Switches to a saved world (the current one is saved first). Follow with `waitUntilReady`. |
| `worldSave` | – | Saves the current world and reports failures (`ok: false` with the reason). |
| `console` | `text` | Runs a line of the server console (decision E-247) with the console's rights, without the bot's position (`~` and commands acting on a player are refused); the leading `/` is optional. Answers `{"lines":[…]}` with the English replies. Example: `{"cmd":"console","text":"op Alice"}`. The state of the nearest village (decision E-403) as one JSON line: `{"cmd":"console","text":"village <x> <z>"}` answers `{"lines":["{\"id\":…,\"style\",\"centre\":[x,y,z],\"min\",\"max\",\"beds\":[{\"at\",\"claimedBy\"}],\"workstations\":[{\"at\",\"kind\"}],\"population\",\"golems\",\"known\",\"freeBeds\"}"]}` (`known`: false while none of its chunks was loaded yet, the state as planned), or "No village within 2048 blocks". |
| `entities` | `radius` (1–64, default 32) | `{"entities":[{"id","type","name","hostile","position","distance","health","yaw","animation"}]}` – mobs and other players in view, at the position the client shows them (about 100 ms in the past, decision E-271). `animation`: `{"speed" (m/s),"walkDistance","onGround","inWater","sneaking","sprinting","swinging","hurt"}` as the character model animates it. Creatures and players also carry `burning` (on fire, E-393); creatures also `young` and `inLove` (breeding, E-293). Other players also carry `appearance` (as in the `appearance` command), `armour` (`{"head","chest","legs","feet"}`, item names or `null`) and `held` (item name or `null`). Dropped items (sent within 32 m) appear as `{"id","type":"item","item","count","position","distance"}`, falling blocks as `{"id","type":"fallingBlock","block","position","distance"}`, minecarts as `{"id","type":"minecart","item","yaw","position","distance"}` (`item`: the cart's item, e.g. `qtcraft:chest_minecart`; decision E-386), experience orbs (sent within 32 m) as `{"id","type":"experienceOrb","value","position","distance"}` (decision E-398). |
| `view` | optional `mode` (`first`, `behind`, `front`, `side`) | Sets the view mode of the graphical client (the headless bot only stores it) and answers with the current `mode`. |
| `drop` | optional `all` (bool) | Throws one item (or the whole stack) of the selected hotbar slot ahead; it can be picked up again after 2 s. Fails when the slot is empty. |
| `collect` | optional `radius` (1–32, default 8), `maxTicks` (default 200) | Walks to the nearest dropped item within the radius again and again until none is left or the time is up; items are picked up by touching them. An item lower than the feet (in a hole) is approached at the middle of its block, so the player drops in. |
| `attack` | `entity` (id from `entities`) | Turns towards the entity and hits it with the held item (reach 4 m). Fails if the entity is out of reach, hidden behind blocks, or the hit did not land (0.4 s attack cooldown, short invulnerability after a hit). |
| `useEntity` | `entity` (id from `entities`) | Turns towards the creature and uses the held item on it: an empty glass bottle catches a firefly, food an animal eats feeds it (it falls in love or a young one grows up sooner, decision E-293); other food is eaten. Only food, armour, the creature's catching item and its breeding food are used on it; other items act on the block behind it like `use`. Succeeds when the creature was caught, fell in love or (young) took the food, also from a creative hand. Fails if the creature is out of reach or hidden, when the item was eaten or put on instead, or when nothing happened. |
| `ride` | `entity` (id of a minecart from `entities`) | Turns towards the minecart and uses it; answers when the server reports the player as its rider (decision E-382). While riding, the player sits in the cart and moves with it; `move` with `forward` pushes the cart along the view. Fails if the cart is out of reach or hidden or the server did not let the player in (the cart has a rider, or it is a chest or hopper cart: a use of one opens its screen, decision E-386). |
| `leave` | – | Sneaks until the server lets the player out of the minecart beside it, then releases sneak. Fails when the player rides no cart. |
| `respawn` | – | Leaves the death screen; answers when the player is alive again. |
| `debug` | optional `goals` (bool: also where creatures near the player are heading), `off` (bool: stop the server's debug data) | The debug display's data as JSON (decision E-225): `{"client":{"tick","protocol","world","seed","position","block","chunk","section","yaw","pitch","facing","light":{"sky","block"},"target":{"position","block","state","tags","light"},"targetEntity","entities":{"mobs","players","items","fallingBlocks"},"loadedChunks","memoryMb","peakMemoryMb"},"server":{"tick","phases":{"players","saving","chunkLoading","blockUpdates","liquids","mobs","items","plants","fallingBlocks","minecarts","machines","streaming","clientSync","messages"},"tickMs","lateMs","skippedTicks","loadedChunks","players","mobs","items","fallingBlocks","pendingBlockUpdates","waitingBlockUpdates","biome","worldType","chunks":{"stored","arriving","unsaved","groups","largestGroup","playerGroup","oversizeGroups","tickets","refusedTickets","forced","loaders"},"goals":[{"id","kind":"wander"\|"chase"\|"flee","goal"}]}}`; every phase and `tickMs`/`lateMs` as `{"mean","max"}` in milliseconds over the server's latest 100 ticks (5 s). The first request subscribes and answers with the server's next message (within half a second); later ones answer at once. Light is -1 where unknown. |
| `gamepadConnect` | optional `type` (`xbox` default, `playstation`, `switchPro`, `generic`), `name` | Connects a virtual gamepad (decision E-540) with everything released; answers with the pad (see `gamepads`), whose `pad` id the other gamepad commands take. Ids start at 1 and are not reused. |
| `gamepadSet` | `pad`, optional `buttons` (`{"south":true,"leftShoulder":false}`), `axes` (`{"leftX":0.5,"rightTrigger":1}`), `release` (bool: start from a released, centred pad instead of the current state) | Changes the given buttons and axes of a virtual pad and answers with the pad. Unknown names or wrong value types fail and change nothing. |
| `gamepadDisconnect` | `pad` | Disconnects a virtual pad. |
| `gamepads` | – | `{"backend":"virtual","pads":[{"pad":1,"name":"Virtual xbox","type":"xbox","pressed":["south"],"axes":{"leftX":0.5,"leftY":0,…}}]}` |
| `quit` | – | Ends the process (the current world is saved). |

All tick-based commands fail with `"Timed out"` if the session stops ticking for much longer than requested (e.g. after a disconnect).

### Virtual gamepads

The gamepad commands feed a `QcVirtualGamepadSource` (decision E-540), the same interface the game's SDL3 backend implements, so scenario tests can play with a controller without hardware. Buttons are named by position: `south`, `east`, `west`, `north` (A, B, X, Y on an Xbox pad; Cross, Circle, Square, Triangle on a PlayStation pad), `back`, `guide`, `start`, `leftStick`, `rightStick` (stick clicks), `leftShoulder`, `rightShoulder`, `dpadUp`, `dpadDown`, `dpadLeft`, `dpadRight`. Axes: `leftX`, `leftY`, `rightX`, `rightY` in [-1, 1] (x positive to the right, y positive downwards, as the pads report them), `leftTrigger`, `rightTrigger` in [0, 1]; values outside are clamped. `gamepadSet` takes `buttons` and `axes` only as objects (name to value); any other type fails the request. The commands report the raw values; dead zone and response curve belong to the input mapping. The pads do not move the player yet: the mapping of gamepad input to game actions follows in stage 40.

## Server console

`qtcraft-headless --console` starts the world without a bot and without the control interface: every line of standard input is a server command (decision E-247), the leading `/` is optional, the replies go to standard output as English text. `stop` or the end of the input saves the world and ends the process; the time limit only applies when `--time-limit` is given. A service without standard input passes `--no-eof-stop`: the server then keeps running until the time limit or until the process is ended (saving on SIGTERM comes with the dedicated server of stage 25; until then a terminated process loses what happened since the last autosave). Example:

```sh
printf '%s\n' 'whitelist on' 'op Alice' 'tick query' 'stop' | build/debug/src/headless/qtcraft-headless --console --seed 42
```

The console has all rights but no position; commands that act on a player (`/give`, `/kill`) are refused, coordinates must be absolute.

## Tick control as a test tool

`/tick` (decision E-249) changes the simulation for tests and measurements, through `chat`, `console` or the game's `--chat`: `/tick sprint 1d` runs a day of game time as fast as the machine allows (plant growth, furnaces, liquids, the day cycle), `/tick freeze` holds a scene still while players can still move and the camera can be placed, `/tick step <n>` advances a frozen world by exactly n ticks, `/tick rate <1..100>` slows down or speeds up, `/tick query` reports the measured rate and the tick phases. Rate and freezing are not saved.

## Statistics log

`--stats <ms>` or `QTCRAFT_STATS=<ms>` (at least 100) writes the same JSON every interval as one line `STATS {...}` into the log (stderr, category `qtcraft.stats`) while a world runs, in `qtcraft-headless` and in the graphical game. The game has no control interface; its lines add `"frame":{"fps","phases":{"frame","guiCpu","entityMesh","renderCpu","worldRender","upload","gpu"},"drawCalls","visibleSections","meshedSections","meshBacklog","lightJobsPending","meshJobMs","lightJobMs"}` (frame phases over the latest 240 frames; `gpu` only with `QSG_RHI_PROFILE=1`). Example: `QTCRAFT_STATS=1000 qtcraft --play 2>&1 | grep STATS`.

Not available: screenshots through the interface (the graphical game's `QTCRAFT_SCREENSHOT` hook covers visual checks) and a local socket in the graphical game (see above).

## Example

```sh
printf '%s\n' '{"cmd":"waitUntilReady"}' '{"cmd":"look","yaw":90}' \
              '{"cmd":"move","forward":1,"ticks":40}' '{"cmd":"status"}' '{"cmd":"quit"}' \
  | build/debug/src/headless/qtcraft-headless --seed 42
```

The scenario tests (`tests/gameplay/test_scenarios.cpp`, `tests/scenarios/*.jsonl`) use exactly this interface.

## Relation to future bridges

The interface is plain JSON over a byte stream, so an MCP server or any other bridge can be layered on top by forwarding lines; no protocol or game code would change.
