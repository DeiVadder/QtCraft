# QtCraft architecture

This document describes the current state. Sections marked *planned* are not implemented yet.

## Modules

| Target | Layer | Depends on | Content |
|--------|-------|-----------|---------|
| `qc_common` | Common | QtCore | Coordinates, chunk storage (palette sections, indices packed with 1–16 bits per cell, E-844), content registry, JSON parser and content-pack loader (`QcContentPackLoader`), block states and shapes (`QcBlockStateTable`), the rules deriving block states from the surroundings (`QcBlockRules`: placement states, connections, support and ground rules; shared with the client's block prediction, E-853), building parts (`QcPartGenerator`), the light engine of server and client (`QcLightEngine`: block and sky light per section as nibbles, incremental; `QcLightTable`; decision E-389), block light flood fill (`QcLightVolume`, on demand and as the reference), the handbook model (`QcHandbook`, `QcHandbookBuilder`, Markdown and JSON forms), protocol messages and codec, transports (`QcTransport`, `QcInProcessTransport`, `QcConnection`), shared physics, thread hand-over helpers (`QcMailbox`, `QcWorkerPool`). |
| `qc_network` | Common | `qc_common`, Qt Network | TCP transport (`QcTcpTransport`: length-prefixed frames, keep-alive, timeout, send limit), connecting (`QcTcpConnector`), server addresses (`QcServerAddress`); decision E-251. With `QC_TLS` the TLS of network games (`src/network/tls`: `QcTlsListener`, `QcTlsCredentials` with the bundled OpenSSL, E-872). |
| `qc_base_content` | Data | `qc_common` | Base game content pack embedded as `:/content/qtcraft` and its loader `QcBaseContent` (source in `src/common/content/loader`); linked by the server and by the tests that load the base content, so other `qc_common` users do not embed it (E-419). |
| `qc_texture_packs` | Data | – | Built-in texture packs embedded as `:/texturepacks/<folder>`. |
| `qc_worldgen` | Server (generation) | `qc_common` | World generation as pure functions of seed, region and content (E-418): world types and generators (`QcWorldGenerators`, flat, void, test terrain), the terrain generator with noise, caves, pools and trees, structures, villages (`QcVillageGenerator`, `QcVillagePlanner`) and the showcase world (`QcShowcaseGenerator`). Never includes server headers, so the generation tests link it without the server. |
| `qc_server` | Server | `qc_common`, `qc_worldgen`, `qc_network`, `qc_base_content` | `QcServer` (authoritative tick loop, players, chunk streaming, neighbour updates), `QcLiquidFlow` (flowing water and lava, E-054; spreading prefers the way to the nearest drop, E-103), `QcFallingBlockManager` (falling sand and gravel, E-055), `QcServerCircuits` (Signal Dust circuits, E-335, with hoppers and dispensers, E-344, E-345), `QcBlockEntities` (block entities per chunk, E-357), `QcMachineRules`, `QcInventoryAccess` (slots as hoppers reach them), `QcHunger`, `QcServerWorld` (with its parts `QcChunkSaveState`: what the storage holds, changed and quarantined chunks; `QcBlockEntityExtras`: furnished chunks and kept block entity parts; E-716), `QcNetworkServer` (TCP listener in the server thread), `QcServerLogin` and `QcIdentityStore` (login of remote clients, E-252), `QcServerSettings` (server.json). |
| `qc_worlds` | Worlds (composition) | `qc_common`, `qc_network` (public); `qc_server` (private: no header of `qc_worlds` includes a server header) | Running worlds in a process, shared by game and headless tool (E-705): `QcLocalServerHost` (server thread for single player, optionally listening for network players; opens a world from a `QcWorldStart` and turns it into the server's configuration), `QcWorldLibrary` (worlds and the data folder on disk), mods (`QcModLoader`, `QcBundledMods`, `QcModStatus`) and their comparison with a server (`QcContentFingerprint`), `QcHandbookRules` (rule values quoted by the handbook). |
| `qc_clientcore` | Client (GUI-free) | `qc_common`, `qc_network`, QtGui (`QImage` only) | `QcClientSession` (world mirror and facade, login answer `QcClientLogin`; the local player's parts `QcPrediction`, `QcHandActions`, `QcLocalAnimation`, `QcClientInventory`), `QcNetworkClient` (joining a network game), `QcChunkMesher`, `QcMeshScheduler`, texture atlas, camera, the character preview's logic (`QcPreviewCamera`, `QcPreviewPose`, `QcPreviewPacer`, `QcPreviewScene`), `QcControlInterface`, debug data (`QcDebugSnapshot`, `QcDebugText`, `QcDebugJson`, `QcDebugLines`, `QcLightProbe`, `QcStatsLog`), sound synthesis and mixing without audio devices (`QcSoundSynthesizer`, `QcSoundBank`, `QcAudioMixer`, `QcSoundSpatial`, `QcLocalSounds`, `QcAmbience`, `QcMusicComposer`). |
| `qc_audio` | Client (audio) | `qc_clientcore`, Qt Multimedia, Qt Concurrent | `QcAudioOutput` (default device through `QAudioSink` in pull mode on the audio thread of `QcAudioSinkHost`, `QcMixerDevice`; follows device changes with `QcAudioRoute`, E-876), `QcAudioEngine` (cues, UI clicks, ambience loops, music scheduling). |
| `qc_app_core` | Client (UI) | `qc_worlds`, `qc_clientcore`, `qc_audio`, Qt Quick, SDL3 (static, only with `QC_GAMEPAD`; only `src/app/input` includes it, E-540) | Library (static; shared in the Debug and sanitizer presets, E-890) with the app's C++ side and the QML module `QtCraft` (QML UI, `QcGameController`, `QcHandbookModel`, `QcWorldView`/`QcWorldRenderer` (QRhi), hooks); linked by the game and by tests (E-417). Links the worlds layer to host worlds in-process. |
| `qtcraft` | Client (UI) | `qc_app_core` and its QML plugin | `src/app/startup` (`main.cpp` with the order of the start, command line, window, language, scripted runs), platform side of scripted runs, shaders, translations, icon and bundle. |
| `qtcraft-headless` | Tool | `qc_server`, `qc_worlds`, `qc_clientcore` | Server plus control-interface client without a window; with `--server` the dedicated server (`QcDedicatedServer`, `QcSignalWatcher`, E-255); with `--join` the control-interface bot joins a server over TCP instead (`QcHeadlessJoin`, E-270). |

Client code without process responsibilities (`qc_clientcore`, `qc_audio`) never includes server headers. `qtcraft-headless` (`src/headless`) may include everything. `src/app` includes no server header and sees no server type (decision E-705): the headers of `qc_worlds` include none (`HEADER_LAYERS` in `scripts/fix-includes.py`), and the data types they share with the server are in `qc_common` and `qc_network` (`QcWorldInfo`, `QcDamagedFile`, `QcTickSummary`, `QcLoginSettings`, `QcNetworkConfig`). The app uses `qc_worlds` for:

| Task | Worlds headers | App files |
|------|----------------|-----------|
| Start the in-process server from a `QcWorldStart` and take a transport from it; open it to the LAN | `QcLocalServerHost`, `QcWorldStart` | `QcGameController`, `QcWorldStarter`, `QcMultiplayerController`, `QcBenchmarkRun` |
| Manage worlds on disk and the data folder (list, create, delete; `settings.ini` lies in the data folder) | `QcWorldLibrary` | `QcWorldLibraryController`, `QcSettingsController`, `QcGameController` |
| Load mods and compare them with a server's content | `QcModLoader`, `QcBundledMods`, `QcModStatus`, `QcContentFingerprint` | `QcAppStartup`, `QcWorldLibraryController`, `QcMultiplayerController`, `QcWorldStarter` |
| Rule values quoted by the handbook | `QcHandbookRules` | `QcHandbookController` |

All game interaction still goes through protocol messages, also in a single-player game.

## Source layout

Inside each library folder the classes live in thematic subfolders (E-089, E-418); the library boundaries are those of the module table. Includes name the header by its path below `src/` (`#include "common/blockrules/QcRails.h"`); the shared test fixtures by their path below `tests/` (`#include "fixtures/QcServerTestFixture.h"`). These two folders are the only include roots: every library adds `src/` to its public include directories, the tests add `tests/`. After moving files, `scripts/fix-includes.py` rewrites the includes, the paths in the CMake files and the source locations of the translations; `verify.sh` checks with `--check` that every include names its path and keeps the layers of `src/` (E-419: `common` includes nothing else, `worldgen` and `network` only `common`, `clientcore` `common` and `network`, `audio` `common` and `clientcore`, `server` `common`, `network` and `worldgen`, `worlds` also `server` (its headers not: `HEADER_LAYERS`), `app` `common`, `network`, `worldgen`, `clientcore`, `audio` and `worlds` (E-705), `headless` anything; tables `LAYERS` and `HEADER_LAYERS` in the script), and `--deps <folder>` lists which folders a folder includes.

## Threads

| Thread | Runs |
|--------|------|
| GUI | QML, `QcGameController`, `QcClientSession` (applies the ordered events of its tick core between two frames, so every reader of a frame sees one state; E-560), mesh scheduling decisions |
| Session tick | `QcSessionCore`, one thread per session (`QcSessionLink`, `QcSessionThread`; a network join starts it first and connects in it, so the TLS socket never changes threads, E-872): the connection to the server (in-process or TCP), the 20 Hz ticks on a fixed grid that catches up to 5 missed ticks after a hold-up (`QcTickPacer`), the local player's prediction with its own block mirror (sharing the immutable chunks, with the player's predicted blocks, `QcBlockMirror`, E-853) and the creatures that push him (`QcPushBodies`, E-882), the wish to fly and the death state; commands from the session and events to it through one `QcMailbox` each, in order (E-560). `QcSessionTickMode::Timer` (headless: exact tick counts for the control interface), `Manual` (tests) and `QTCRAFT_SESSION_THREAD=0` keep the core in the session's thread |
| Render (Qt Quick) | `QcWorldRenderer` |
| Server | `QcServer` and, when listening, `QcNetworkServer` with every TCP socket of the remote clients (no locks for the game state, E-251): client messages and the 20 Hz ticks (1–100 Hz with `/tick rate`, back to back in 20 ms slices during `/tick sprint`, E-249) in one event loop; input budgets, rate limits, autosaves and confirmations follow the players' time (`QcServerClock::playerTimeNs`, the real time each tick stands for), not the tick count; the next tick is a single-shot timer on the deadline grid of `QcTickScheduler` (E-090); console commands arrive as blocking queued calls from the host (E-247) |
| Generation workers | `QcTerrainGenerator::generate` (`QcWorkerPool` in `QcServerWorld`) |
| Mesh workers | `QcChunkMesher` on immutable chunk snapshots (`QcWorkerPool`), including sky light of the section's neighbourhood |
| Light worker | `QcBlockLightEngine` (one `QcWorkerPool` thread of `QcMeshScheduler`): incremental block light, published as immutable section snapshots |
| Map preview worker | `QcWorldMapWorker` (one `QcWorkerPool` thread of `QcWorldMapPreview`, only while "New world" or "World options" shows a normal world): builds the new world's generator and samples `QcBiomeMap` coarse, then fine, then the sites; results with their build number through a `QcMailbox`, older builds stop between rows (E-921) |
| Backup copy | `QcBackupRunner`: copies the hard-linked snapshot of `/backup` (one `std::thread` at a time, result through a `QcMailbox`, collected every tick; E-256) |
| Qt thread pool | Rendering the sound bank and music pieces (`QtConcurrent::run`, results to the GUI thread through `QFutureWatcher`) |
| Audio (`QcAudioSinkHost`, own QThread "audio", time-critical priority; E-876) | Owns the `QAudioSink` and pulls mixed samples from `QcMixerDevice`, so a stalled GUI thread does not stop the sound; opening and closing go through a blocking queued call; every access to the mixer is guarded by one mutex in `QcAudioOutput` |

Data crosses threads only as immutable snapshots (`std::shared_ptr<const QcChunk>`, encoded frames) through `std::mutex`-guarded mailboxes; Qt queued calls only wake the receiver (see decision E-010).

## Protocol

Frames are `[quint16 type][QDataStream payload]`, see `QcProtocol.h` and decision E-007. Over TCP every frame is preceded by its length as a big-endian `quint32` (a length of 0 is a keep-alive, `QcFrameReader`, E-251). Version: `QcProtocol::version` (69, the predicted block actions; the history of the versions is in decision E-368). The payload codecs are one encode/decode overload pair per message, grouped by topic (`QcSessionCodec`, `QcWorldCodec`, `QcPlayerCodec`, `QcEntityCodec`, `QcMachineCodec`, `QcDebugCodec`, `QcAdminCodec`, shared field codecs in `QcProtocolCodec`, chunks in `QcChunkCodec`); `QcProtocol.cpp` dispatches on the type tag. Each peer only accepts the message types the other side may send. Chunk sections are a palette plus run-length encoded indices (E-016).

Content packs are directories with `pack.json` (`id`, `name`, `version`, `dependencies`) and the folders `blocks/`, `textures/`, `lang/`. Emblems are textures of the pattern `emblem` (`QcTextureEmblem`: a bitmap and a palette in the data).

Sounds (sent to clients, decisions E-040, E-042): `sounds/*.json` (`name`, `bus` `effects`/`ambient`/`music`, `volume` 0–1, `pitchVariation` 0–0.5, `volumeVariation` 0–0.5, `drive` 0–8, `variants` 1–8, `loop`, `range` 1–128 m, `layers`: 1–8 of `wave` `sine`/`square`/`triangle`/`saw`/`noise`/`crackle`, `frequency`, `endFrequency`, `start`, `duration`, `attack`, `curve`, `gain`, `lowpass`, `highpass`, `bandpass`, `resonance`, `tremoloRate`, `tremoloDepth`, `density`). Mobs have `sounds` (`ambient`, `hurt`, `death`), machines a `sound`, storage blocks an `openSound` and `closeSound` in their `container` (server side, played by `QcContainerSounds`, decision E-879). Names nothing defines are reported when loading and are silent at run time.

Runtime block ids are block states, assigned in registration order and never stored; persistent data uses names (decisions E-045, E-046).

Shapes and states (E-045, E-046): `shapes/*.json` (`name`, `parts` with `when` conditions on state values, `boxes`/`crosses` as `[x0, y0, z0, x1, y1, z1]` in block metres, optional `collision` boxes up to 1.5 m high, a texture `slot`, `uv` `cell`/`box`; `rotate` names a facing property, `flip` a property whose value `top` mirrors the shape). `QcBlockStateTable` derives for every state its boxes, collision, full faces, face texture turn and whether it is a full opaque cube; mesher, physics, raycast and selection use the same boxes. Every combination of a block's property values is a runtime id (at most 2048 per block, `QcBlockStateTable::maxStatesPerBlock`); a block's name resolves to its default state.

Building parts (E-048): `parts/*.json` describe families (`name`, `kinds`, `suffix`, `block` template, `hardness` and `fuel` factors, `recipe` with `@` for the base, `translations` with `%1` for the material's name), `materials/*.json` materials (`name`, `block`, `kind`, `exclude` families, `translation`) or exclusion entries (`excluded`, `blocks`). `QcContentRegistry::finish()` runs `QcPartGenerator` after all packs and then creates block items. Recipes accept item tags (`#qtcraft:planks`, `items/*.json` field `tags`, block field `tags`).

Handbook content (server side, not synchronised): optional `description` translation keys on blocks, items, mobs and biomes (default `<translation>.description`), `handbook/*.json` chapters (`name`, `order`, `icon`, `sections`, `related`; texts from `chapter.<ns>.<name>[.<section>.title|.text]`), labels as `handbook.*` translations. Language files may be split: `lang/<language>.handbook.json` adds to `<language>` (only this suffix is removed).

Mods are content packs in the mods directory (`<data root>/mods`, `--mods-dir`); `QcModLoader` loads the base game first and then every mod after its dependencies, skipping broken ones. The base game goes through exactly the same loader. Details, the boundary between core and mods and the file formats are in `docs/Modding.md`; open security questions in `docs/Mod-Sicherheit.md`.

## Game modes

The game mode is a server state per player (E-282): `QcGameMode` and its rules (`QcGameModes::rules`) live in `qc_common`, so the server (`QcServerGameModes`, `QcServerClient::gameMode`) and the client (`QcClientGameMode`, mirrored from `GameMode`) apply the same table. Flight is part of the shared physics (`QcPhysics::stepPlayer` with `mayFly`; the wish to fly travels with every numbered input, E-284), so prediction and server agree. Creative rules are checked where the action happens: instant breaking in `QcServerInteraction::finishMining`, endless placing in `applyPlacement` and `QcServerStands`, invulnerability in `QcPlayerHealth::damage` and the creatures' targets, frozen hunger in `QcHunger`. Survival and creative keep separate inventories (`keptInventory`, E-283). The creative inventory is `QcCreativeCatalog` (`qc_common`, tabs and search), `QcCreativeItemModel` and `CreativeScreen.qml` (E-286); pick block is `PickBlock` (E-285).

## Loading and unloading chunks

Decisions E-373 to E-377. `QcChunkLoading` keeps the chunks that are needed: the view square and the sent chunks of every player, forced chunks (`/forceload`, `forcedChunks` in `world.json`), the spawn chunks (game rule `spawnChunkRadius`), the chunks of the first `chunkLoaders` chunk loader blocks (`QcChunkLoaders` in `QcServerWorld`, blocks whose item has the tag `qtcraft:chunk_loaders`; `chunkLoadersPerPlayer` checked when a player places one), circuit load tickets (`QcChunkTickets`) and the chunks of signals that wait for a ticketed chunk.

- **Groups** (`QcChunkLinks`, `QcChunkGroups`): per loaded chunk and side the server counts the circuit parts within two cells of that side and the pistons that could push across it, at every block set and chunk arrival; the marks are saved with the chunk (index entry of its block entities). Two neighbours are linked when both have parts at their shared side or one reaches into the other; linked chunks form a group of at most `chunkGroupLimit` chunks. A chunk that arrives waits (`m_waiting`) until its whole group arrived, then all enter the world in the same tick; a group leaves only when none of its chunks is needed, all in the same tick; `QcServerWorld::loadChunk` loads the whole group at once (`loadGroupNow`). A larger group comes and goes chunk by chunk with a warning (log, debug display) and its circuits wait at the loaded edge (E-348).
- **Leaving** (end of a tick, at most `chunkUnloadsPerTick` chunks, groups whole): contents spilled in the tick drop, then per chunk the entities (`QcEntityRecords::take`), the block entities with scheduled ticks, the circuits' work and the hoppers' queue (`QcBlockEntityRecords::take`), pending block updates and planned flow steps (as block updates), whether the chunk got its animals, its marks and its blocks if they changed go to `QcChunkIo::keep`, which encodes them on its thread and keeps them until the next save. Waits are counted from the upcoming tick (`QcChunkLoading::upcomingTick`), so a chunk that comes back goes on with exactly the tick that followed when it left.
- **Arriving**: `QcServerWorld::requestChunk` reads a stored chunk through `QcChunkIo` (before other waiting work unless that chunk is still being handed over) or generates it (`QcWorkerPool`); a chunk with only kept block entities or entities is read and then generated. On arrival the records go back (`QcChunkLoading::restore`): block entities, block updates, entities (new ids after those already there). Answers to an older request of the same chunk are dropped (request numbers). Damaged chunk data makes the chunk play as generated and never be saved (`QcChunkSaveState::isQuarantined`, `QcServerWorld::saves`).
- **Tickets** (E-376): a signal on its way (a changed block, a scheduled tick, a reading; not the look of components at a chunk that arrived) that waits for a chunk that is not loaded asks for a ticket of that chunk (`QcCircuitState::takeTicketWishes`); at most `chunkTicketsPerTick` new ones per tick and `chunkTickets` at once, each lasts `chunkTicketTicks` ticks after its chunk arrived. The chunk of the waiting signal stays loaded until the ticketed chunk is there.
- **Numbers**: `QcChunkLoading::numbers` (stored, arriving and unsaved chunks, groups, the largest and the player's, groups over the limit, tickets and refused ones, forced chunks, loaders) go to the debug display (`ServerDebug::chunks`) and `/worldinfo`.

## Interaction

The client sends intentions; the server decides (`QcServer`):

- **Limits for every action:** spammable messages pay into per-player token buckets (`QcRateLimiter`, E-091; over the limit they are dropped and logged, nobody is kicked; the local player of the in-process host is exempt from the chat bucket only). Mining, using, placing, scooping, attacking and catching need reach and a line of sight from the eye (now or before the last input) to a point of the target, with the client's raycast (`QcLineOfSight`, E-092).

- **Mining:** `StartMining`/`CancelMining`/`FinishMining`. The server checks reach (5 m + 1 m slack), the target and the elapsed ticks against `QcMining::breakSeconds` (hardness × 1.5 s, divided by the tool speed with the right tool; × 5 s without a required tool, which also gives no drops). Drops (each with its `chance`) fall into the world as item entities (E-028); tools lose durability; a double slab drops two slabs, the upper half of a door nothing.
- **Block prediction** (E-853): the client shows its player's breaks (creative at the press, survival at the end of the mining) and plain placements (`QcBlockForecast`: the held item only places its block; the same `QcBlockRules::placement` as the server, both halves of doors and beds) at once in both block mirrors (`QcBlockMirror` of the session and of the tick core) and meshes the changed sections before all others (`QcMeshScheduler::Priority::Player`). `FinishMining` and `UseItem` carry the action's number; the server answers every numbered message with `BlockAck` after the blocks it set or resent and after the world sync of the next tick (the entities the action spawned, such as drops, arrive first), also when it refused or dropped the action. Until then the server's blocks for a predicted cell are only remembered; the acknowledgement shows them, so a refusal rolls back and a confirmation changes nothing (no second mesh). Neighbour updates (light, liquids, falling blocks, connections) come from the server as before.
- **Placing:** `UseItem` on a block face places the held item's block into the neighbouring cell if it is replaceable, within reach and no player is inside its collision boxes. `QcBlockRules::placement` derives the state (E-046): `facing` from the player's view (`away` or `toward` the player), `half`/`type` from the clicked face or the height of the aimed point, `attach` towards the clicked block (`floor`, `ceiling`, a side; values the block does not list refuse the placement), connections from the neighbours; a slab clicked on its open half becomes a double slab in place; doors need two free cells and take their hinge from the aimed side. Saplings need one of their `plantOn` blocks below.
- **Neighbour updates** (E-047): every block change queues the changed position (unless it became air) and its six neighbours; updates caused by players go into their own queue, which goes first; commands and their cascades use what is left of the budget. Each tick the server works through at most 1024 of them, re-deriving connection properties (fences, walls, panes to their group and full solid blocks; walls show a post except in straight runs) and breaking blocks without support (`below`: full solid top below; `attached`: full solid face on the attach side; doors: the other half) with their drops. A block with `hardens` that finds its `with` block on one of its sides turns into `into` before it could fall (`QcBlockSimulation::processUpdate`, E-208), and a falling one that lands in a `with` cell turns into `into` there (`QcBlockSimulation::landBlock`, E-217); chunks that load re-check such blocks on their borders. Updates only change states derived from neighbour types, so they settle after one pass; the budget bounds the work per tick. Sides towards unloaded chunks keep their state and supports there count as present; updates for unloaded positions wait for their chunk (at most 65,536), and a chunk that loads re-checks the connecting and wall-mounted blocks on its borders and those of its loaded neighbours. Pending updates are saved in `blockupdates.qce`. A door half breaks its partner with the same drop decision; a half without partner breaks without drops. Doors, trapdoors and gates do not toggle onto a player or mob, and no block is placed into one.
- **Doors, trapdoors, gates and ladders:** using a block with `toggles` (not sneaking) flips `open`, for doors on both halves; open gates have no collision. Climbable blocks (ladders) let bodies climb at 2.4 m/s while pushing into the wall or jumping, slide down at most 2 m/s and hold while sneaking (`QcPhysics`, also for client prediction); falls end on ladders.
- **Movement in and on blocks** (E-207): `QcPhysics::stepEntity` (server and client prediction) multiplies the wished horizontal speed by the liquid's `movement`, the smallest `slowsInside` of the cells the body overlaps (cobweb 0.25) and, on the ground, the `surface.speed` of the block under the centre of the feet (mud 0.6); inside a slowing block the vertical speed is scaled by the same factor (slow sinking, no fall damage), and a jump starts with `surface.jump` times the normal jump speed (mud 0.93).
- **Block entities** (`QcBlockEntities` in `QcServerWorld`, E-357): containers, machines, sapling timers, what circuit components remember and their scheduled ticks, one table per kind with an index per chunk. Every block set (`QcServerWorld::setBlock`) runs `placed()`: what no longer fits the block spills (dropped by `QcServerBlocks::dropSpills`), containers and machines of the new block appear; chunks entering the world are fitted to their blocks and get the containers and machines of their blocks (sections with `QcBlockTrait::BlockEntity`); a regenerated chunk loses its entries; pistons move everything of a cell with `relocate()`. `QcBlockEntityChecks::problems` checks the rules between blocks and entries (tests). Limits `maxContainers`, `maxMachines`, `maxSaplings`.
- **Chests** (E-050): using a block with `container` opens its slots like a machine screen (`QcBlockScreens`, `OpenMachine` with empty category, slots 45 onwards); breaking or replacing the block drops the contents; a storage block of another size keeps what fits and drops the rest; one whose block went away with a mod spills its contents when its chunk is loaded.
- **Dropped items** (`QcItemEntityManager`, E-028): physics through `QcPhysics::stepEntity` with weak air drag, floating in water, resting items skipped until their ground changes; merging of equal stacks within 1 m every 10 ticks; pickup when touching a living player after 0.5 s (thrown: 2 s), partial when the inventory is full; ageing only in loaded chunks, despawn after 300 s; at most 512 awake items (when a chunk loads with more, the youngest sleep in place: frozen, not sent, same id, woken oldest first), a bounded queue for further drops that appear only in loaded chunks, 4096 items in the world; stacks above `maxStack` are split; moves are sent once an item is 2 cm from its last sent position. `DropItem` (key Q, Ctrl+Q for the stack) throws items from the eyes along the view direction. On death without `keepInventory` (E-029) inventory and grid scatter as items.
- **Plants** (`QcPlantManager`, `QcServerPlants`, E-030, E-031): leaves of tree features decay a few at a time once no trunk is within four blocks (checked after a trunk is removed); saplings grow into their feature after a random time while loaded (timers in `QcBlockEntities`, in planting order), using the generator's tree shapes (`QcTreeShape`); a despawning sapling item plants itself with its `plantChance`. Blocks with `growth` (sugar cane) grow upwards on random ticks (`QcPlantGrowth`, E-102): every tick picks `randomTicksPerSection` (3) random blocks in each loaded section whose palette holds such a plant; a ticked top block grows by one with the chance `68 s / averageSeconds` while the column is below `maxHeight` and its base keeps its ground.
- **Farming** (E-289 to E-295): the same random ticks drive crops and soil (`QcCropGrowth`, called by `QcPlantGrowth` for blocks with `crop` or `soil`; the section marks count every block with `QcBlockDefinition::hasRandomTicks`). A crop advances a stage of its `age` property with the chance `68 s / (averageSeconds / steps)`, halved on dry soil, only in light 9 or more (block light, sky light estimated down the column); a ripe stem puts its fruit on a free neighbour. Farmland turns wet with water within 4 blocks, dries without it and reverts to dirt when dry and bare or covered. Block drops can carry `when` conditions (harvest only when ripe). `QcServerPlants::till` tills with items that `tills` (hoes; wear except in creative mode), `QcServerAnimals` feeds animals and spawns the young ones of `QcMobBreeding` (timers `love`, `breedCooldown`, `growUp` in `QcCreature`, saved with the entities of their chunk). `QcServerPlants::plantSeeds` lets resting seed items on free soil plant one of their stack once a second with the crop's `plantChance`. A seed stack whose own cell is taken plants the free soil in the 3 × 3 ring around it, one seed per check. Items in flowing liquid drift along its current (`QcLiquidFlow::current`, E-296). Food that plants (carrots, potatoes) is eaten where it cannot be planted; the client sends `UseEntity` only for food, armour and what the creature takes (catching item, breeding food, which the content sync carries, protocol 29), other items act on the block behind it. Animals in love walk towards each other, breed only in sight of each other and get their young at a parent's feet, within caps per 3 × 3 chunks and per world (`QcMobBreeding`). The game rule `randomTicks` stops all random ticks (off in the showcase world). Growth runs only in loaded chunks, nothing is made up later.
- **Inventory:** 36 slots (9 hotbar). The server sends the full `InventoryState` after every change; `MoveInventoryItem` merges or swaps stacks.
- **Chat and commands:** `ChatInput`/`ChatMessage`; plain lines go to everyone, lines with `/` run a command (decisions E-243 to E-249). `QcServerCommands` checks the source's rights (`QcPermission`: player, operator, console; the local player is always an operator, `QcServerState::permissionOf`), logs the call (`qtcraft.commands`) and runs the `QcCommandSpec` from `QcCommandRegistry` or a macro of the content (`commands/*.json`, E-248). Command groups: `QcCheatCommands` (give, spawnitem, summon, equip, armorstand, kill, heal, feed, time, gamerule, gamemode, locatebiome), `QcBlockCommands` (setblock, fill with `replace`, clear, regenerate via `QcChunkRegeneration`), `QcPlayerCommands` (list, kick, ban, unban, banlist, whitelist, op, deop, tp; lists in `QcAccessList`, `access.json`), `QcWorldCommands` (save, backup via `QcWorldBackup`, worldinfo, remove, stop), `QcTickCommands` (tick: freeze, step, rate, sprint, query; `QcTickControl`, `QcTickScheduler`). Destructive commands wait in `QcPendingCommands` for `/confirm` (30 s of real time; the confirming source needs the command's rights). The server console (`QcServer::runConsoleCommand`, `QcLocalServerHost::runConsoleCommand`, `qtcraft-headless --console`, control command `console`) uses the same layer with all rights and no position.
- **Eating and hunger** (`QcHunger`, E-039): `ConsumeItem` eats one of the held item if it has `food` and the player is not full; the item's `food` points are added (at most 20). Walking, sprinting, swimming, jumping, mining, attacking and taking damage add exhaustion (rates in `QcHunger`, E-100: a full bar lasts about 124 min of walking or 8 min of sprinting); every 4 points cost one food point. At 18 food or more the player heals one point every 4 s (2 exhaustion each); at 0 food they lose one point every 4 s down to 1. Respawning refills the food. Using a machine or crafting table opens it even with food in hand.
- **Machines** (`QcMachineRules`, `QcServerMachines`, E-037, E-038): using a block with `machine` opens it (sneaking places against it) within 5 m + 1 m slack; the server closes it when the player dies, walks away or the block goes. Slots 45–47 of `MoveInventoryItem` are the open machine's input, fuel (fuel only) and output (take only). A machine lights one fuel item when its input has a recipe of its category and the result fits; burning and progress run at the machine's `speed`, without fuel the progress falls back twice as fast. Only machines in loaded chunks tick, at most `maxMachines` (4096) exist; breaking or replacing the block drops the contents as items.

Every visible, non-liquid block automatically gets an item of the same name that places it (`QcContentRegistry::createBlockItems`); `items/*.json` defines further items (`name`, `translation`, `texture`, `maxStack`, `places`, `tool`, `toolLevel`, `toolSpeed`, `durability`, `attackDamage`, `food` in food points, `fuelSeconds`, `emptiesTo` (left in the hand when eaten or poured, in the fuel slot when burnt, E-212), `armour` (`slot`, `points`, `set`, `layers`, `parts`; see Modding, E-234/E-235), `placesStand` (places an armour stand, E-238), `scoops` (takes a liquid source that has `flow.bucket`), `bottles` (fills from a liquid that has `flow.bottle` and leaves the liquid, E-211; an item cannot have both)); block items inherit the block's `fuelSeconds`.

UI controls: F1 opens the handbook (at the block or creature in view), left mouse mines or attacks, F mines, right mouse / R places, eats or opens a crafting table or furnace, Q throws one item (Ctrl+Q the stack), 1–9 and the wheel select the hotbar slot, E opens the inventory, T or Enter the chat, Esc the pause menu (save, quit to menu).

## Signal Dust circuits

Decisions E-333 to E-340. A block takes part in circuits through its `signal` definition (`QcSignalDefinition`): the kind (dust, lever, button, plate, torch, repeater, lamp, opener, piston, piston head) and its numbers come from data; only the kind reaches the client (switches are used instead of placed against). `QcSignalTable` decodes every block state once into a `QcSignalState` (kind, emitted strength, on, facing, delay, lock, dust sides, conductor, piston mobility), so the engine never compares property strings while it runs.

- **Power** (`QcSignalPower`): sources send power directly into neighbouring components and dust (levers, buttons and plates into all six, torches into all but their block, repeaters forward) and strongly into one conductor (the block a lever or button hangs on, under a plate, above a torch, in front of a repeater). Dust powers the block under it and the blocks its lines point at weakly. A conductor is a full solid opaque block unless its data says `conducts: false`; a strongly powered one powers neighbouring dust and components, a weakly powered one only components. Every answer is a maximum over the six faces.
- **Phase "signal"** (`QcServerCircuits`, after block updates): `QcServerBlocks::setQuietly` reports every block change to `QcCircuitState::noteChange`, which keeps it only when a component may lie within two blocks (section marks `QcServerWorld::marks`, trait `Circuit`). Each tick presses plates from the bodies standing on them, then works in steps: a step takes the pending changes, collects the components next to them (and next to what the changed block powered before or after) and the dust within one block, decides everything on the world as it is (`QcDustNetwork`, `QcCircuitComponents`, `QcPistonPlanner`) and applies it together in a fixed order (`QcCircuitPlan`). Its own changes are the next step. Then the scheduled ticks (`QcSignalSchedule`, one entry per position, groups by tick and priority release before diode) run as steps the same way. A tick does at most `QcServerCircuits::maxUpdatesPerTick` work (dust looked at, components, pushed blocks); the step that crosses it ends, the rest waits for the next tick.
- **Dust** (`QcDustNetwork`): links flat, up the side of a block when nothing opaque covers the lower dust, down the side of a block that is not opaque. A change recomputes only the dust within 15 links of the dust next to it (the region), in one breadth-first pass from the strongest inputs; dust just outside the region feeds it with its strength minus one. Connections (dot, line, corner, cross, slopes) come from the same pass; only changed dust is written. A new strength of dust never makes other dust recompute.
- **Components** (`QcCircuitComponents`): torches switch 2 ticks after their block's power changed and burn out after 8 times out within 60 ticks (160 ticks); repeaters wait 2 ticks per delay step, stretch short pulses to their delay and are locked by a powered repeater pointing at their side; lamps light at once and go dark `offDelayTicks` later; openers follow rising and falling power (`QcCircuitState::poweredOpeners`); pistons plan at once (quasi-connectivity: also powered through the block above, only noticed on an update next to them, game rule `quasiConnectivity`); buttons and plates release by schedule. Torches and lamps are two blocks (`counterpart`) (light belongs to a block).
- **Pistons** (`QcPistonPlanner`, `QcPistonMover`): plans of one step that share any cell are all dropped; the rest move. Blocks move in the world at once, far end first, chests and furnaces re-keyed to their new cell before the block is set there; bodies in the cells taken are pushed along. The clients see the source cells empty at once, a sliding block entity (`QcMovingBlocks`, 2 ticks) and the new cells when the slide ends. A sticky piston retracting within the 2 ticks of its extension lets go of its block.
- **Budget and unloaded chunks:** a step takes at most a quarter of the budget left in changes or due scheduled ticks (in a fixed order of positions; such a split step is no longer simultaneous), a quarter of the budget stays for due scheduled ticks. Changes, components, scheduled ticks and dust regions within two blocks of an unloaded chunk wait for it (`QcCircuitState::waitingOn`).
- **Bodies:** pushes of a step are summed per body and direction, then moved with `QcPhysics::moveBox` against the world after the move; a body left inside a block goes to the nearest free cell or suffocates (`QcEnvironmentDamage::applySuffocation`).
- **Waking** (`QcCircuitState::wake`, `chunkLoaded`): demo positions of a world's setup and positions saved with their chunk wait until their chunk and the eight around it are loaded; when a chunk loads, the components along its borders with loaded chunks look at their neighbours once (pistons excepted, they wait for a block update).
- **Unloaded chunks and dust:** only the part of a step's dust region that reaches an unloaded chunk (dust linked to each other) waits for it; other parts of the step are recomputed (E-348).

### Simulation limits

`QcServerLimits` (decisions E-349, E-360) holds every tunable budget and bound of the simulation in `QcServerConfig::limits` (signals, hoppers, summons, block entities, block updates, liquids, falling blocks, items, creature caps, breeding, random ticks, leaves, fire, armour stands, sliding blocks, chunks; table in `docs/Multiplayer.md`). `QcServerSettings` reads them from `server.json` (dedicated server, `limitsFromServer`), `QcServerPersistence` from `world.json` otherwise; `QcServerState::applyLimits` hands them to the parts that keep a copy; the class constants are only the defaults, taken from `QcServerLimits{}`. Each limit is one row of `QcServerLimits::fields` (key, description, range, member).

### Signal machines

Decisions E-342 to E-348. Four more kinds: comparator, observer, hopper and dispenser (the dropper is a dispenser with `uses: false`).

- **Comparators** (`QcCircuitComponents`, scheduled like repeaters): the back input is replaced by what `QcComparatorReadings` reads from the block behind it or, through a conductor, two behind it: container and machine fullness by the reference formula or a state property scaled to 0..15, as the block's `signal.comparator` says. Contents changes reach them through `QcServerState::noteContents` → `QcCircuitState::noteContents`, which looks right away for comparators that read the block (`readersOf`, facing away from it) and notes only those, once per tick (`readers`); without one it costs the circuits nothing. Hoppers are not part of the circuit section marks.
- **Observers:** every real state change (before ≠ after) wakes the observers whose face looks at its cell (`QcServerCircuits::Collected::addObservers`) in the same simultaneous step; on 2 ticks later, off 2 ticks after.
- **Dispensers and droppers:** rising power (direct or quasi-connectivity, `QcCircuitComponents::poweredOrQuasi`) sets `triggered` and schedules a fire 4 ticks later; the plan's `fires` run after the pistons (`QcDispenserActions`): a seeded slot choice, insertion into a container in front shared with all dispensers of the step, otherwise the item's `dispense` action (pour or take a liquid, equip armour) or a throw; actions on one cell that collide fail together.
- **Hoppers** (`QcServerHoppers`, end of the signal phase, own budget of 4096 acting hoppers per tick): `QcServerWorld::hoppers()` (`QcBlockIndex`) knows every loaded hopper and notes cells changed on or next to one; `QcHopperQueue` (`QcServerState::hoppers`) holds the awake hoppers and timers; a hopper's cooldown belongs to its container (`QcBlockEntities::Container::readyAt`, saved with its chunk). A tick wakes hoppers next to touched cells, next to changed contents and below item entities that moved (`QcItemEntityManager::takeStirred`), takes the awake ones whose cooldown ended, and runs a push step and a pull step, each decided on the world before it and applied as differences (`QcInventoryAccess`: slots by side, first fitting slot, `resolve` for several insertions into one container). Targets get their entry while deciding (`QcInventoryAccess::ensure`); an item leaves its source only after it was put in. Pickup reads a grid of item entities built in one pass over the items, only for the cells of the hoppers that search, and never under a block whose collision fills its cell. Hoppers that moved rest 8 ticks; those that found nothing sleep.

## Crafting

- **Recipes** come from `recipes/*.json`: `name`, `type` (`shaped`, the default, or `shapeless`), for shaped recipes `pattern` (up to 3 strings of up to 3 characters, space = empty) and `key` (one character → item), for shapeless ones `ingredients` (1–9 item names), and `result` (`item`, `count`). Patterns are trimmed to their bounding box when parsed. `QcCrafting` (shared by server and client) matches a square grid against all recipes: shaped recipes at any offset and mirrored horizontally, shapeless ones as a multiset. A recipe needs a 3 × 3 grid if its shape or ingredient count does not fit 2 × 2.
- **Grid:** the inventory screen has a 2 × 2 grid; using a block with `"crafting": true` (crafting table) opens 3 × 3 as long as the player stays within 5 m. Grid cells are slots 36–44 (three per row) and live on the server; `MoveInventoryItem` moves, splits and merges between inventory and grid. `TakeCraftingResult` consumes one item per used cell and adds the result if it fits. `CloseCrafting` puts the grid back into the inventory; what does not fit is thrown on the ground (also when the player disconnects).
- **Recipe book:** `CraftRecipe` crafts directly from the inventory, round by round, each round all-or-nothing on a copy of the inventory. 3 × 3 recipes need a crafting table within 5 m. The inventory screen lists the recipes that can be made now; the control interface offers `recipes` and `craft`.
- **Base recipes:** planks from each log (oak, birch, spruce), sticks, crafting table, chest, door, trapdoor and wooden tools from any planks (tag `planks`), torches from a stick and coal or charcoal (tag `coals`), ladder, glass pane, furnace (8 cobblestone), stone/iron/diamond tools, sandstone, and the recipes of the building parts (stairs 6 → 4, slab 3 → 6, wall 6 → 6, fence 4 + 2 sticks → 3, fence gate 2 + 4 sticks → 1).
- **Smelting** (E-037): `smelting/*.json` (`name`, `category` default `smelting`, `input`, `result` with `item`/`count`, `seconds` default 10). Base recipes in the furnace: iron and gold ore to ingots, sand to glass, clay to bricks, cobblestone to stone, logs to charcoal, raw to cooked porkchop. Fuel: coal and charcoal 80 s, logs, planks and crafting tables 15 s, wooden tools 10 s, sticks and saplings 5 s. The furnace screen (`FurnaceScreen.qml`) shows the three slots, a flame for the fuel left and an arrow for the progress.

## Entities

Every entity of a world is a `QcEntity` of one kind (`QcEntityKind`: player, creature, item, falling block, armour stand, sliding block, minecart, experience orb, projectile) in the register `QcEntities` (E-364). Each kind's table carries its own behaviour (`QcMobManager`, `QcItemEntityManager`, `QcFallingBlockManager`, `QcArmourStandManager`, `QcMovingBlocks`, `QcMinecartManager`, `QcExperienceOrbManager` (E-398), `QcProjectileManager` (E-425); players are the clients). Once for all kinds: ids, visiting in a fixed order, the body box, pushes by pistons (`displace`), resting while the own chunk is not loaded (`settle` at the start of each simulated tick: not simulated, not sent), the sync to clients (`QcEntitySync`: 64 m, items and orbs 32 m) and saving per chunk (`QcEntityRecords`, `entities/r.<x>.<z>.qen`, E-366). Players move only through their inputs (prediction, E-008) and are saved per player. Players and creatures that overlap push each other apart softly (E-882, `QcBodyPush`): the server adds the creatures' push to each player input (`QcPlayerInput::push`, from a grid of their bodies built once between two ticks, `QcCreatureBodies`), the client's tick core predicts the same push from the creatures as the server last sent them, each moved on along its last step by the lead of the input (`QcPushBodies`), and players push walking creatures through their steering like their crowd (`QcMobBehaviour::withCrowd`). Entities leave memory with their chunk and come back with it, with new ids after those already there (E-374); one in a chunk that is not loaded (a stray, from `settle`) brings its chunk in so it goes back to storage with it.

Rails and minecarts (E-382, E-383): a rail's state (`facing`, `shape`) follows from where rails lie beside it, level or a block higher or lower (`QcRails::shapedState`, independent of update order and rotation). Minecarts move in their own tick phase (`QcServerMinecarts::tick`): bumps and pushes by living bodies first, worked out from the state before the tick, then each cart on its own along the track (`QcMinecartMotion`); a cart at rest on a level rail is skipped until something moves it. A riding player is moved by the server with the cart, not by inputs; `PlayerState::vehicle` names the cart, and the client then predicts nothing and shows the player on the seat of the cart as its entity mirror shows it (`QcClientRiding`).

Signal rails and container carts (E-384 to E-387): powered and activator rails are rail slots of the circuits (`QcSignalKind::Rail`): a change at one decides every rail of its line within reach (`QcRails::lineOf`, eight rails) from the power the rails get from outside; the cart reads what the rail does from `QcRails::Table::behaviourOf` (boost, brake, activate). A detector rail is a plate that only carts press (`detects: carts`); a comparator reads the container cart on it (`QcComparatorReading::Carts`). Chest and hopper carts carry the slots of the block their item names (`cartBlock`, `QcMinecartManager::Load`); their screens are those of chests with the cart's entity id (`QcBlockScreens::openCart`). After the carts moved, `QcMinecartHoppers` lets hopper carts pull from containers above and pick up items, and Signal Hoppers under rails pull from the container carts above them, within the hoppers' cooldown and budget.

## Creatures, health and time

- **Mobs** come from `mobs/*.json`: `name`, `translation`, `health`, `width`, `height`, `walkSpeed`, `chaseSpeed`, `hostile`, `attackDamage`, `attackRange`, `attackCooldown`, `sightRange`, `spawn` (`time` `day`/`night`/`any`, `blocks`, `maxGroup` 1–4, `weight`, `caves`; night creatures spawned in caves stay by day), `model` (boxes `from`/`to` in metres around the feet, facing north, with a `texture`) and `drops`; further `spawn.ambient`, `spawn.maxCount`, `spawn.biomes`, `spawn.chunkChance`, `spawn.maxY`, `spawn.also` (up to 8 extra rules with their own `time`, `blocks`, `weight`, `caves`, `maxLight`, `chunkChance`, `maxY` and `biomes`; group size and caps stay shared), `flying`, `glow` and `catch` (E-057). Base mobs: zombie (hostile, night and caves), slime (hostile, caves in slime chunks below y 40, and at night on swamp surfaces up to y 70), pig and sheep (passive, persistent), firefly (ambient, flying and glowing, night, swamps, catchable with a glass bottle).
- **Server** (`QcMobManager` with `QcNaturalSpawner`, E-422): monsters (hostile, not aquatic or ambient) by the original game's rules (E-836): every tick two attempts per living player at one of the floors of a random column in the 17 × 17 chunks around it, 24–128 m away, where the light test passes (`QcSpawnLight`: block light at most `maxLight`, 0 by default, and a random draw against the sky light darkened by time and weather) and the ground carries (`QcSpawnGround`: solid, opaque, full top); 70 monsters per 289 loaded chunks of the players' areas, and below 70 in the area of a player near the chunk (`QcMonsterCap`); the other kinds every second up to four spawn attempts per player in a ring of 20–48 m, on the surface (by time of day) or on cave floors at least 8 blocks below the surface; caps of 6 passive and 10 ambient mobs per player (plus `maxCount` per kind); biomes come from the generator (`QcWorldGenerator::biomeAt`). Behaviour per tick (`QcMobBehaviour` with the brain of each creature's `ai`, E-423): hostile mobs chase the nearest player they see (one ray from their eyes to the player's every 10 ticks, `QcLineOfSight::seesPoint`; a player out of sight is followed for 5 s more, E-401) along a path and strike in range with a cooldown, only with a line of sight from their eyes (`QcLineOfSight`, as for players); passive mobs wander to reachable places nearby and flee from an attacker to a reachable place away from it; flyers drift above the ground; walkers are counted into block cells each tick (`QcMobCrowd`, E-401): each is pushed away from the centre of the others in its cell and of the eight cells around it (linear cost, never off a cliff), and the count of its cell sets its AI tier: below `crowdThrottled` (8) full, from it throttled (thinks every 4th–10th tick, staggered by id, without path searches; in between it follows its path without searching and never off an edge; it looks for players once in 10 ticks like the others), from `crowdIdle` (24) no AI (gravity, currents, damage, push); hostile ones strike the nearest player they reach in melee in every tier; dormant creatures neither think nor count. The game rule `maxEntityCramming` (24, 0 off) hurts creatures in a cell with more (6 damage in every fourth tick staggered by id, until the cell holds no more than the rule; loot drops, no experience; `QcMobCramming`, sounds and loot in `QcServerCreatures`); swimming. Mobs that are not kept despawn beyond 128 m, and with 1 in 800 per tick once no player came within 32 m for 30 s (E-836); night mobs by day once nobody is near; they are not saved. Peaceful animals are persistent (E-086): 10 % of the chunks seen for the first time get a group, they never despawn, rest (`dormant`: not ticked, sent or counted) while their chunk is not loaded and are saved with the entities of their chunk, with the set of populated chunks; natural animal spawns happen only while no awake animal is within 128 m. `spawn.chunkChance` limits a kind to a seed-chosen share of chunks (slime chunks), `spawn.maxY` caps the spawn height. No mob spawns on a block with `contactDamage` (magma) or with its feet or head in a block with `slowsInside` (cobwebs), whatever its `blocks` list; the block fields decide, not names.
- **Path finding** (E-400, E-402, `src/server/pathing`): every block state is one byte for walking creatures (open, also a ladder's cell; low like a slab, carpet or snow layer, with its height in eighths; solid floor; tall like a fence; wall, thin collision without room for a body like panes, iron bars and closed iron doors; water; closed wooden door or gate; dangerous like fire and lava; unknown; flags for hurting floors like magma and slowing cells like cobwebs; `QcPathCellTable`). Collision over less than half of the cell's ground is never a floor. A creature stands where its feet cell is free, the cell below is a solid floor (or the feet cell is low, or water at its surface) and its height fits (`QcPathTerrain`). A* (`QcPathFinder`) moves to the four sides (a step up of at most 1.125 blocks with room to jump, level, or a drop of at most 3, down to 12 into water two blocks deep) and the diagonals between two free sides; it costs a little for climbing, dropping and passing walls, more beside fire and lava, much for water (a walker swims only without a dry way), magma floors and cobwebs; fire, lava, walls, closed doors (unless the creature opens doors, a hook for stage 37.2) and unloaded chunks are never entered, and a search never reads beyond a window of 64 × 32 × 64 cells around the start. The heuristic is weighted (1.25). A goal out of reach gives a partial path to the closest cell reached. Searches wait in a queue and run at the start of the next tick, first come first served, until the next would overrun `pathNodesPerTick` (`QcPathPlanner`); one search expands at most `pathNodesPerSearch` nodes (a wanderer a quarter), a path keeps at most `pathLength` waypoints. A creature follows its path (`QcMobNavigator`), jumping where the next waypoint is higher; it searches again when its goal moved by more than a quarter of the distance (at least a cell), the next waypoints (every second all of them) can no longer be stood on, it made no progress for a second, a chase path is five seconds old or a partial path ended; after a path that did not get there it waits one, two, four, then eight seconds, searching earlier only for a blocked path or a goal that moved eight cells; a goal of another purpose (wander, chase, flee) starts without a path. `pathNodesPerTick` 0 switches path finding off: creatures walk straight at their goals.
- **Combat:** `AttackEntity` (reach 4 m plus the target's size, 0.4 s cooldown, damage from the held item's `attackDamage`, 1 by hand), 0.5 s invulnerability after a hit, knock-back both ways. Loot falls where the mob died.
- **Contact damage:** `contactDamage` hurts players and mobs whose body touches such a block and, for solid blocks, those standing on it: the block under the centre of the feet counts, a liquid beside it does not (magma, `QcEnvironmentDamage` with `QcContactDamage`, E-209).
- **Health:** 20 points; fall damage of one point per metre beyond 3 m; regeneration of one point every 4 s while food is at least 18 (see Eating and hunger); death shows a screen and waits for `Respawn` (back to the spawn point with full health; the inventory is kept or dropped depending on `keepInventory`). Health is saved with the player.
- **Time:** a day lasts 600 s (`QcDayCycle`); the server keeps `worldTime` (saved in `world.json`) and sends `WorldTime` every second; the client advances it between updates and derives sky colour, fog and the daylight factor of the block shader.
- **Client:** `QcClientSession` mirrors entities (`EntitySpawn`/`EntityMoves`/`EntityRemove`, interpolated between ticks) and finds the creature under the crosshair; `QcEntityMesher` turns the boxes into triangles every frame and draws dropped items as small spinning, bobbing cubes (cube blocks) or crossed sprites (other items), up to three copies for larger stacks; the HUD shows hearts, the food bar and the time of day.

## Sound and music

- **Synthesis** (E-040): `QcSoundSynthesizer` renders a definition and a variant into mono float PCM (44.1 kHz by default, the output device's rate in the game): per layer a tone (with exponential sweep), white noise or sparse crackle, a resonant two-pole band-pass (state-variable filter, decision E-879), two one-pole low-pass stages, a one-pole high-pass, linear attack, decay `(1 - t)^curve`, tremolo and a 3 ms fade at the end. The result is normalised to a peak of 0.9 (then saturated by the sound's `drive` and scaled back to that peak); loops blend their tail into their head (equal power, a quarter of the length, at most 0.3 s). Noise comes from a seed derived from the sound's name and the variant, so renderings are deterministic. `QcSoundBank` renders all sounds of the content on a worker thread within a budget of 16 Mi samples (64 MiB); sounds beyond it stay silent with a warning.
- **Mixing** (E-041): `QcAudioMixer` plays voices (buffer, gain, constant-power pan, pitch with linear interpolation, loop, bus) on the buses effects, ambient and music under a master volume and mute; at most 32 voices, a new sound replaces the quietest voice that does not loop; gain changes ramp over one mix block; a soft limiter (above 0.75, tanh) keeps the sum below full scale. `QcAudioOutput` opens the default device (float stereo, else 16 bit) with an 80 ms buffer; without a device or when it fails, the game stays silent and logs the reason once.
- **Events** (E-043): the server sends `SoundEvent` for broken and placed blocks, creature ambience (on average every 10 s per creature), hurt and death of creatures and players, eating, picking up items and burning machines (on average every 2.5 s). The client computes the gain `(1 - d / range)^2` with `range` = the sound's range × max(1, volume), damps sounds behind the listener by up to 25 % and pans them by the side (`QcSoundSpatial`, at most 85 % to one side). Client-side cues (`QcLocalSounds`, `QcClientSession`): own steps every 1.7 m on the block below, jumps, landings (louder above 6 m/s), splashes (entering water faster than 3 m/s), swimming strokes every 2.2 m, mining strikes every 4 ticks, steps of other creatures from their movement; UI clicks on buttons come from the controller. `QcClientSounds::recent()` (`QcClientSession::sounds()`) keeps the last 64 cues for the control interface.
- **Ambience and music** (E-044): `QcAmbience` derives levels for wind (open sky, rising from 0.3 at y 64 to 1 at y 120, muffled under a thin roof), cave (at least 4 opaque blocks within 24 above the head) and water (water blocks in a sampled box of radius 6) every 10 ticks and fades them by 0.5 per second; the three loops play on the ambient bus. `QcMusicComposer` composes a piece per seed on a major or minor pentatonic scale (66–90 bpm, motifs A A' B A, bass per bar, held chords, closing bar on the root, about 30 s); the engine renders it on a worker thread and plays pieces with pauses of 60–180 s while a world is open.

## Keys and screens

Keys (decision E-077): `QcKeyBindings` (`qc_common`, GUI-free) is the table of actions (walk, jump, sneak, sprint, look, mine, use, drop, inventory, chat, command, camera view, handbook, debug display, debug options, labels, hotbar 1–9, fullscreen (E-835), pause) with a primary and a secondary `Qt::Key` each, portable key names (`V`, `F5`, `Space`, `/`) and conflict handling (binding a used key swaps it with the slot's old key) and platform defaults (`Platform::Mac`: sprint Option, no Cmd or Control, Cmd not bindable, whole stack with Control). `QcGameSettings` stores it as `keys/<action>` and `keys/<action>.2` in `settings.ini`; unknown names fall back to the default, keys an earlier action already uses are dropped, Esc (pause) is fixed. `QcKeyControls` (`qc_clientcore`, QML name via `QcKeyControlsForeign`) exposes it to QML as `GameController.keys` (rows for the controls page, labels of the primary keys for hints, `matches()`, `bind()`, `reset()`), `QcKeyLabels` gives translated key and action names (Cmd/Control/Option on macOS). In the world `QcGameController::handleWorldKey` maps every key event through the table and takes all of them, so nothing below the world reacts; movement keys count while held. The controller filters application events, so it also accepts the `ShortcutOverride` of every bound key (Qt sends it to the focused item). The handbook fills `{key.<action>}` (all keys), `{key1.<action>}` (primary key) and `{key.stackModifier}` from the same table: the export with the Windows/Linux defaults (platform-neutral), the game with the player's keys and the platform's key names.

Sizes (E-725): every size of a screen goes through `Ui.px()`, every size of the HUD through `Ui.hudPx()` (QML singleton `controls/Ui.qml`); both read the factors of `UiScaling` (`QcUiScaling`), which `Main.qml` feeds with the player's choice (`GameController.settings.uiScale`: Auto or 75–200 %) and the window size. The screens' factor stops where a screen laid out for 1024 x 640 would no longer fit the window, the HUD's where 640 x 360 would not (`QcUiScale`, `qc_clientcore`); the controls' font follows through the window's font (`controls/WindowFont.qml`). Accessibility (E-725): interactive items carry `Accessible.role` and a translated `Accessible.name` (slots: item and count, `ItemSlot.slotLabel`; sliders, boxes, fields and lists: their label); click catchers behind a screen are `Accessible.ignored`. Colours (E-097): every screen takes its colours from `Theme` (`QcUiTheme`, the palette `QcUiPalette`); HUD texts lie on a dark semi-transparent backdrop (`HudLabel.qml`). `test_ui_palette` checks every text/background pair of the palette over seven world backgrounds (snow, sand, sky, water, grass, night, cave) against WCAG 4.5:1 (3:1 for large text) and that no QML file has colours of its own. Slot screens (E-099): `SlotScreen.qml` with `InventorySlot.qml` and `PlayerSlots.qml` is the base of the inventory, chest and furnace screens: the picked-up stack follows the mouse, its slot is dimmed, shift-click sends `QuickMoveItem`, slot clicks sound like buttons. Mouse capture (E-098): `QcMouseCapture` captures the mouse again whenever the input steps back from a screen into the world; the release of a button held at that moment does nothing.

Screens (E-078): overlays are QML items over the world (`GameController.overlay`); the pause and main menus own their sub-screens (settings with the pages General and Controls, character, mods, delete dialog) as popups and close them when the menu is hidden or the overlay changes, so no popup outlives its menu (closing stores the settings). Esc closes the topmost popup first (the popup's own Esc handling), then the menu; a closed popup gives the keyboard back to its menu. Every screen takes the keys it does not use (Tab still moves the focus); text fields keep typed letters, so a letter handbook key in the handbook search types instead of closing.

Display options (decision E-835): `QcDisplayOptions` (`qc_clientcore`) holds the window mode (`windowed`, `borderless`, `fullscreen`), the mode the fullscreen key returns to, the screen (by `QScreen::name`), the windowed frame, VSync and the two frame limits (`frameLimit` while playing, `backgroundFrameLimit` in the menus, while paused and while the window is inactive; 0, 30, 60, 90, 120 or 144; defaults unlimited and 30) as `display/<key>` in `settings.ini`; unknown values give the default with a warning. `QcDisplaySettings` (`GameController.settings.display`) writes every change at once and, once `main()` hands it the window (`showWindow`, not in scripted runs: `--background`, offscreen, `--screen`, `QTCRAFT_WINDOW_SIZE`), sets the swap interval (VSync, read when the window is made: a change needs a restart), shows the window in its mode (`QcWindowPlacement`: frameless over the screen's geometry, or `showFullScreen`; a screen that is gone falls back to the primary one with a warning; the windowed frame and screen are stored when leaving windowed mode and at quit; a fullscreen switch by the platform, macOS's green button, is followed) and limits frames: `QcFrameDriver` asks `QcFrameLimiter::frameDue()` first (an early frame changes nothing in the scene, so the scene graph skips rendering it) and requests the next frame with a precise timer instead of `QQuickWindow::update()` at once. Without a limit both pass every frame, as before. `QcGameController::updateForeground` picks the limit from the phase, `QcScreenState::isMenu` and the window's activity; the character previews draw at most at that limit (`GameController.preview.frameLimit`). The fullscreen key (action `fullscreen`, F11, on a Mac the secondary key) works in the world through `QcGameInput` and elsewhere through an event filter on the window, except while the controls page captures a key.

## Handbook

`QcHandbookBuilder::build(registry, language, rules)` (`qc_common`, decision E-064) turns a complete registry into a `QcHandbook`: twelve categories (playing, blocks, building parts, liquids, items, tools and weapons, food, creatures, biomes, world generation, item groups, overviews), entries with id (`block:<name>`, `item:`, `mob:`, `biome:`, `ore:`, `feature:`, `tag:`, `chapter:`, `world:terrain`, `table:fuels|tools|smelting`), title (and English title for search), icon item, description, facts and sections with links and recipes. Facts are computed with the shared rules (`QcMining` break times, tool levels, drops, light, support, flow, machine and fuel times, spawn rules with the caps from `QcHandbookRules`). Cross references come from reverse indices built once: recipes by result and ingredient (tags expanded), smelting by input and result, drops of blocks and mobs, biome layers, features, ores and pools, spawn blocks, catches, building parts by base. Entries are sorted by pack (namespace of the name, packs in load order, unknown namespaces after them) and title; links are checked at the end (`problems()`). Labels and texts come from the registry's translations, so the same code serves the game and the export (E-065). `QcHandbook::search` matches all words against titles (language and English), names and texts, without case and accents.

- **Export** (E-066): `QcHandbookMarkdown::files` gives `index.md` and one file per category, entries as `### <a id="block-qtcraft-stone"></a>…` with relative links; byte-identical for the same content. `docs/handbook/` (English) and `docs/handbook/de/` are the base game's handbook; `test_handbook` fails when they differ from a fresh export.
- **Game** (E-067): `QcGameController` builds the handbook on first use from the full content of the world (or, in the menu, the content it loads for the character screen and menu sounds) and again after a content or language change; in the menu it also draws the item icons from that content. `QcHandbookModel` gives QML the categories, entry lists (with pack headings when mods are loaded), search results and pages (`QcHandbookJson`, converted per page). `HandbookScreen.qml` lies above every other screen and keeps the screen below open; it opens with the handbook key (H or F1 by default; in the world at the target, in inventory, furnace and chest at the hovered item), from the main and pause menus and with the "?" on a hovered slot.
- **Control interface:** `handbook` in `qtcraft-headless` (see `docs/Steuerschnittstelle.md`).
- **Web handbook** (E-950): `web/handbook/` (`index.html`, `handbook.css`, `handbook.js`, no framework, no build step) shows the handbook like `HandbookScreen.qml`: categories, entry list or search results, the page with facts, link chips and recipe grids, English and German, addresses `#<language>/<entry id>`, one column at a time on phones. ## World generation

`QcTerrainGenerator` (decision E-014) is deterministic per seed and thread-safe. The climate (temperature, humidity, ruggedness, rarity) is read at coordinates bent twice: the large warp shared with the coasts (420 blocks, ±140) and a smaller one only for the climate (160 blocks, ±200), which frays biome borders (temperature and humidity take half of it, so the climate never folds; cold and hot biomes lie at least 0.3 apart in climate space and never meet, transition biomes such as snowy taiga, forest steppe and jungle edge lie between them, E-824, E-825); mountains cover about a quarter of the land (E-085, E-101). Players spawn on natural ground of the stored world near the generator's spawn point (E-101). Features and ores take their seeds from their names (`qcNameSalt`, FNV-1a, plus a fixed offset per purpose, E-214), so new content does not move the trees and ores of others; ores may replace cave air (cobwebs, E-216). The server generates chunks on a `QcWorkerPool` (`QcServerWorld::requestChunk`), nearest first with a bounded queue, and collects finished chunks every tick; stored chunks are read on the thread of `QcChunkIo`. Which chunks stay loaded and how chunks with their groups come and go is `QcChunkLoading` (section "Loading and unloading chunks"). Sky light is computed client-side while meshing, block light incrementally on the client's light thread (decisions E-015, E-049).

Villages (decision E-403): the world is cut into square regions (`worldgen/villages.json`, `spacing`); `QcVillagePlanner` decides for each region from the seed and the terrain noise alone (never from generated chunks) whether it has a village: a chance, up to `attempts` places for the centre on flat land (`maxHeightSpread`) of a biome with `villages: true`, four roads from the centre with branches (stopping at water and steps), pieces of the biome's style (`villages/*.json`, else the fallback style) on both sides of the roads facing them, lamp posts along the roads. The plan (`QcVillagePlan`) is computed once per region and cached in `QcVillageGenerator` (shared by the generation threads); each chunk writes only the roads and pieces that lie in it, after clearing the terrain above a piece's footprint and filling the ground below it, so a village spanning chunks comes out the same in any generation order. Columns of a village (and a margin) get no trees or plants, chunks near one no surface pools. On the server `QcVillages` (in `QcServerWorld`) learns a village from its plan when its first chunk arrives, rescans every chunk of it that arrives for beds and workstations and follows every block set (`noteBlock`); the state is saved in `villages.json`. `/locate village` and `/village` (JSON) use `QcWorldGenerator::nearestVillage`.

Villagers (decision E-411) are creatures of a kind with `villager`, naming their species' settings (`villagers/<name>.json`: routine, default look, trading, breeding; professions in `professions/<name>.json`, joined into every species by `QcVillageContent` when the content is finished; each style's look, creature kind and golems in its file, decision E-421). `QcMobManager::populateChunk` has `QcVillagePopulation` let a villager move into every free bed of a village whose head lies in the chunk (`QcVillagerHomes::settle`: bed claimed under the creature's persistent id, population counted; limits `villagersPerVillage`, `villagers`); the villager is persistent and saved with its chunk (`QcVillagerCodec`, the villager component of its entry, E-420). `QcMobBehaviour` hands villagers to their brain `QcVillagerBehaviour` (the villager AI, E-423): every 20 ticks (at most `villagerThoughtsPerTick` per tick) a villager checks and makes its claims (an unemployed one takes the profession of the free workstation it claims), looks out for hostile creatures and picks its goal from the routine by the time of day; in between it walks there with `QcMobNavigator`, in legs along the road graph of its village's plan when the goal lies beyond one search window (`QcMobLegs` with the routes of `QcVillagerRoads`, `villagerRoutesPerTick`), takes turns at doors (`QcDoorPassage`), and lies in its bed at night without physics (pose `Lying`, E-423). Doors it opens and closes and crops farmers harvest are actions that `QcServerVillagers` carries out after the creatures' tick through `QcOpeners` and `QcServerBlocks` (`villagerHarvestsPerTick`); a villager that dies or is removed frees its claims (the departure notification of `QcMobManager`, which `QcVillagePopulation` listens to, E-422). `QcEntitySync` sends a villager's look (`QcVillagerLooks`, the joined outfits of `QcVillagerOutfits` registered when the content is finished) and its pose (`QcCreature::pose`, the flag bits `Lying` and `Sitting`, E-423); the client draws villagers in that look and lying on their back (`QcAnimator`), and box and eyes follow the pose (`QcPoses`).

Village life (decision E-415): every `QcVillagePopulation::villageLifeTicks` (100) ticks `QcVillagePopulation::liveInVillages` runs `QcVillagerBreeding` (farmers share produce; two willing adults of a village in sight by day and dry weather get a child that settles in the nearest free bed, `growUp` set, timers on `QcMobBreeding`) and, with natural spawning, `QcVillageGolems` (golems counted by position in the village area once its chunks are loaded, `QcVillage::golems`, `lastGolem`; one spawned near the bell by population and cooldown below `villageGolems`; inactive while the golem creature named in `worldgen/villages.json` or the village's style is missing).

Trading (decision E-414): `QcVillagerTrades` (held by `QcVillagerBehaviour`) builds the offers of each profession from the content's trade sets (`trades/`), draws a villager's offers by level and look, prices them with demand and restocks them when the villager is at its workstation during work. `QcServerTrading` (in `QcServer`) opens the screen when a player uses a villager with offers (one trader per villager, `QcVillager::trader`; the villager stands facing them and only looks out for danger), carries out `Trade` (costs from the inventory, result given or thrown, villager experience and levels, player experience as orbs via `QcServerExperience::drop`) and closes screens in the Machines phase when the villager flees, sleeps or dies, or the player dies, leaves or walks out of reach. On the client `QcClientTrading` (part of `QcClientSession`) keeps `TradeState`; `QcTradeController` (`GameController.trade`) feeds `TradeScreen.qml` (overlay `trade`); the control interface has `openTrade`, `trades`, `trade`, `closeTrade`.

World types (E-221, E-223): `terrain` (`QcTerrainGenerator`), `flat` (`QcFlatGenerator`: the same layers everywhere, from `worldgen/flat.json` or the world's own layer list), `void` (`QcVoidGenerator`: air but a platform at the spawn, `worldgen/void.json`) and `showcase`; `QcWorldGenerators::create` builds the generator of a world's type and options.

Showcase world (decisions E-219 to E-222): generator type `showcase` (`QcShowcaseGenerator`), chosen when a world is created and stored in `world.json`; `QcWorldGenerators::create` builds the generator of a type. `QcShowcasePlanner` lays out a `QcShowcasePlan` once per content: flat ground from `worldgen/showcase.json`, then in rows north of the spawn the demo structures (`structures/*.json` with `showcase`), the trees, an enclosure per creature, a podium area per block category with every state of every block, and every item in chests, each with a title and a lookout (tour stop). The plan holds `QcStructurePlacement`s indexed by chunk; `generate()` writes the ground and the placements of a chunk. Labels come per chunk (`labelsIn`, sent as `ChunkLabels`); the one-time setup (`setup()`: noon standing still, no natural spawning, creatures, chest and furnace contents, block updates, growing saplings) is applied by `QcServerSetup` when the world opens for the first time. Each row of the village area is a village of its own (`QcShowcaseGenerator::villageFor`, plans with `alwaysLivedIn`): residents move into its beds although creatures do not spawn there (E-411). East of the rows lies the village station (`QcShowcaseSettlement`, E-490): a bed beyond the first row that makes its village grow, and a settlement in one chunk (three beds, a composter, a wheat field, a chest of bread, two homeless villagers, a rail with a minecart). Its beds and composter are the generator's points of interest (`QcWorldGenerator::pointsOfInterestIn`, `QcShowcasePlan::pointsOfInterestByChunk`): whenever their chunk enters the world `QcServerWorld` notes each one with `QcVillages::notePointOfInterest` (the generated villages within reach become known first; idempotent, a broken one is air and counts no more), so they count as placed by a player. Structures are general: a palette of block states and layers of palette keys, placed in quarter turns with turned states (QcStateRotation), chunk by chunk and thread-safe, so villages (stage 37) can use them. On the client `QcLabelProjector` picks the labels to draw each frame (reach, view, not behind an opaque block) and `QcWorldLabelModel` hands them to `WorldLabels.qml`.

## Debug display and runtime diagnostics

Decision E-225. Server: `QcTickPhaseTimer` laps one monotonic clock through `QcServer::tick`, one lap after each registered tick system (`QcTickSystems`, E-700) to its phase (players, saving, chunk loading, block updates, Signal Dust circuits (E-335), liquids, fire (E-392), weather (E-395), creatures, projectiles (E-425), items (with experience orbs, E-398), plants, falling blocks, minecarts, machines, streaming, client sync; their sum is the tick) and collects the time of the client messages between ticks; `QcPhaseWindow` (`qc_common`) keeps mean and maximum of the latest 100 ticks without allocating per tick; `QcTickStats` sums the phases for the BENCH line; `QcServerDebug` sends `ServerDebug` to subscribed clients. Client: `QcServerDebugMirror` keeps the latest message and the tick history; `QcDebugSnapshot` gathers the debug data of a session (light from `QcLightProbe`), `QcDebugText` writes the translated lines, `QcDebugJson` the JSON for the control command `debug` and the statistics log `QcStatsLog` (`--stats`, `QTCRAFT_STATS`). Graphical game: `QcFrameMonitor` collects frame statistics only as deep as needed and hands render samples to the benchmark; `QcDebugHud` (`GameController.hud.debug`; the frame phases include the character previews' meshing, E-231) updates text, graphs (`QcGraphItem`, QML `DebugGraph`) and light labels four times a second and keeps the server subscription in step with the settings (`QcDebugSettings`, `QcDebugOptions`: `debug/level`, `debug/<option>`); `QcDebugVisuals` builds `QcDebugLines` per frame while a visualisation is on, `QcDebugLineRenderer` draws them (`debugline.{vert,frag}`). QML: `DebugOverlay.qml`, `DebugOptionsPage.qml` (settings page "Debug", overlay `debug`).

Playtest diagnostics (decision E-834, guide `docs/Playtest.md`): `QcDiagnosticsSession` runs from the start of `main()` to its end in both programs: it installs the log file (`QcMessageLog`, chained before the console handler) and the crash handler (`QcCrashHandler`), prunes old sessions and names a crash report of the previous one. The health line (`QcHealthLog`) takes its sample from `QcFrameDriver` with `QcClientHealth` (frame times, chunks, entities, players, input round trip from `QcLinkStats` in the session core, connection bytes from `QcConnection::traffic`) or, on the dedicated server, from `QcLocalServerHost::health` (`QcServer::health`, tick times since the previous line). The server logs every network client's `Hello` with its client text, the login, a refusal and the leaving with its reason and duration (`qtcraft.server`), and ticks longer than 50 ms with their five longest phases, at most one line per ten seconds plus one for the rest at the stop (`QcLagReport`, `qtcraft.lag`); a tick running longer than 10 s makes `QcLocalServerHost::health` log a warning with the last finished phase instead of blocking on the server thread (`QcTickPhaseTimer::stall`). The server, session tick, render and worker threads call `QcCrashHandler::prepareThread()` at their start (alternate signal stack and terminate handler on macOS and Linux, stack guarantee on Windows). The game's settings page "Debug" switches the log file (`GameController.settings.diagnostics`, `QcDiagnosticsSettings`), opens the log folder and collects a bundle; the main menu shows a crash notice (`crashNotice`).

## Rendering

Sky (E-095): `QcSky::at(worldTime)` gives the colours of zenith and horizon, the sunrise and sunset glow, sun and moon directions, the moon phase, star visibility and cloud drift; `QcSkyRenderer` draws it first as one screen-filling triangle (`sky.{vert,frag}`, no vertex buffer, no depth test) with sun disc, lit-sphere moon, turning stars and noise clouds on a layer at 160 m. Fog takes the horizon colour.

Render modes (E-390, E-899): a frame is a `QcFramePlan`. The classic plan draws straight into the item's output. The realistic plan (setting `render/mode`, `QcRenderOptions`, `QcRenderSettings` as `GameController.settings.rendering`) draws the same steps into the HDR scene target of `QcPostProcess` (RGBA16F colour, sampled depth), runs the bloom chain (`QcBloomChain`, dual filter, levels by quality) and then the composite pass into the output: height fog reconstructed from depth (faded in caves by `FrameInput::outdoors`), bloom, exposure and a highlight roll-off (`post.vert`, `bloom_down.frag`/`bloom_prefilter`, `bloom_up.frag`, `composite.frag`). In the realistic mode light sources, lava (frame uniform `animation.y`) and the sun (`sunDirection.w`) shine beyond white; in the classic mode those factors are exactly 1 and 0, so its picture is unchanged.

`QcWorldView` is a `QQuickRhiItem`. Its GUI-thread setters write one snapshot, `QcWorldView::FrameInput` (camera, atlas with its version, sky, fog range, selection, entity and hand meshes, debug lines, precipitation, the benchmark flag); `QcWorldRenderer::synchronize()` runs on the render thread while Qt Quick blocks the GUI thread, copies that snapshot as a whole (shared lists and meshes, no allocation) and takes the queued mesh submissions and hands over the benchmark samples; `initialize()` and `render()` read only the copy (E-710). The renderer's GPU resources come in two groups by lifetime (E-710): `QcWorldDeviceResources` belongs to the QRhi (frame uniforms, atlas texture, sampler and bindings, the outline's bindings and vertices, entity and hand buffers) and is replaced only for a new QRhi; `QcWorldPassResources` belongs to the render pass (block, water, entity, hand and outline pipelines, the sky, debug-line and precipitation renderers, the pass descriptor) and is dropped with the device group (first) and whenever `initialize()` gets a render target it does not fit (incompatible pass or another sample count); a new atlas drops only the pipelines built with its bindings, then bindings and texture. A group is dropped whole through `std::exchange`, so its destructor releases bindings and pipelines before what they refer to; a refused pipeline is tried once per group. `QcGpuMeshStore` is reset with the device group but kept, because its queue of received meshes outlives the QRhi; when sections handed to the GPU are lost (a new QRhi, or a new renderer after Qt Quick dropped the node), the view emits `meshesLost` and the controller has `QcMeshScheduler::remeshAll()` deliver every section again. Meshes are immutable `std::shared_ptr<const QcChunkMesh>` snapshots with four lists (opaque, translucent, water, underside of the world). Vertex format (`QcBlockVertex`, 24 bytes, E-069): position (relative to the section's corner, `QcChunkMesh::origin`, float), atlas UV, then four unsigned bytes: shade (face shading × ambient occlusion), sky light, block light and the surface (normal and `QcSurfaceMaterial`, E-390, not read by today's shaders); the shaders take the brighter of sky light × daylight and a warm-tinted block light. Cross-shaped blocks become two double-sided diagonal quads.

Camera-relative rendering (E-883): the GPU sees only positions relative to the camera, so the picture is as exact a billion blocks out as at the origin. The camera position is double (`QcCamera::position`), the view matrix the camera's rotation alone (`QcCamera::viewRotation`), and the shaders' `cameraPosition` is zero. Every piece of geometry lies in small floats relative to an origin of its own: a section relative to its corner (`QcChunkMesh::origin`), entity, framed-map and hand meshes relative to the block of the camera or eye (`QcEntityMesh::origin`), debug lines and rain relative to the block of the feet or eyes. `QcDrawOrigins` (owned by `QcGpuMeshStore`) holds one `vec4` per origin in a dynamic vertex buffer: the origin's offset from the render anchor, a whole block near the camera that follows it only when the camera has moved `QcRenderOrigin::anchorReach` (128) blocks away along an axis (subtracted in double, `QcRenderOrigin::entry`; whole numbers for sections), and for sections the corner modulo 1024 for the leaves' corner hash. A section gets its entry when it is uploaded and frees it when it is removed; the renderer's entity, framed-map and hand entries move when their mesh origin does; only written entries are uploaded, all of them when the anchor moves. The camera's offset from the anchor goes once per frame into the Frame uniform `drawCamera`, which the block and entity shaders subtract. The pipelines read the entry per instance (binding 1, location 6), picked as the draw's first instance (`QRhi::BaseInstance`) or by binding the buffer at the entry. Culling, translucent sorting, entity culling, labels and the selection outline work relative to the camera; debug lines get their offset added on the CPU, rain through its Shape uniform; the clouds wrap camera and drift by their 40 km period. The world reaches to the technical bound (`QcWorld::maxHorizontalBlock`, 2^30 - 16 blocks): bodies stop there (`QcEntityMotion::keepInsideWorld`) and the server loads no chunk beyond it (`QcChunkPos::isInsideWorld`).

Frame (E-390): `QcFramePlan` lists the steps of a frame (`QcRenderPass`: shadow, sky, opaque, entities, water, translucent, weather (rain and snow, E-395, E-397), overlay, post-processing) and their targets (shadow map, offscreen scene, the water's copy of the scene, the scene continued after it, output); consecutive steps with one target share a GPU render pass, which clears it, so a plan never returns to a target (`QcFramePlan::visitsTargetsOnce`, E-391). Today's mode is `QcFramePlan::classic()` (sky, opaque, entities, translucent, overlay into the output); the realistic mode (`QcFramePlan::realistic()`, E-899) draws the sun's shadow map first (`QcShadowMap`: cascades side by side in one depth texture, fitted and texel-snapped by `QcShadowCascades`, casters are the opaque and cut-out lists and the entities; the receiving shaders are the `QC_SHADOWS` variants, E-903), then sky, opaque world and entities into the HDR scene, a copy of it for the water (`QcWaterSurface`: colour and distance in RGBA16F, E-906), the water with its own pipeline (`water.frag`: waves, Fresnel, sky/sun and on High screen-space reflections, refraction with absorption, caustics, writes depth), translucent faces, weather and overlay on over the same scene (`QcPostProcess::sceneContinuedTarget`, loads instead of clearing), then post-processing (under water a water fog instead of the height fog); `QcWorldRenderer::drawPlan` culls once and draws the steps of each group; the sections it culls and draws are the meshes of `QcGpuMeshStore`, which takes the latest mesh of each section from `synchronize()` and uploads them, with their light, in the frame's first resource update batch (E-413). Translucent faces: sections back to front, within a section water (`waterPipeline`) and glass (`translucentPipeline`) in the mesher's order (`QcChunkMesh::translucentRuns`), so the picture is that of one mixed list; while the water pipeline equals the translucent one, the step draws both with the translucent pipeline and binds it once per frame (E-391); a plan with a water step draws the water lists on their own. When the plan reads section light (`QcMeshInput::sectionLight`, set through `QcMeshScheduler::setSectionLight` from `QcFramePlan::selected()`), every mesh with faces carries the light of its cells (`QcSectionLight`: block light shared from the light snapshot, sky light copied from the mesher's light volume, uniform channels as a single level); when a step reads it (`QcFramePlan::sectionLight`, test hook `QTCRAFT_SECTION_LIGHT=1`) `QcSectionLightPool` uploads it into pages of RG8 3D textures, 64 slots of 16³ texels per page, uniform sections as two constants.

Light (E-049, E-389): `QcLightEngine` (`qc_common`) keeps block and sky light of all loaded chunks per section as nibble arrays (a section whose cells all have one level, all dark or all lit by the open sky, keeps no cells), updated incrementally; sky light shines with 15 above the highest cell of a column that keeps the sky out (`QcLightPassage::skyStop`) and spreads like block light. The server's `QcServerWorld` keeps one with both channels in step with every block set, arriving, leaving and regenerated chunk (the own light of an arriving chunk is computed by the generator threads or the I/O thread, `QcLightEngine::prepare`, the tick only joins the borders); crops (`QcCropGrowth::plantLightAt`: brighter of block and sky light) and spawning (block light) read it, nothing is saved. On the client `QcBlockLightEngine` is the same engine with block light only plus the snapshots for the mesher; sky light stays in the mesher (E-015), which gives the same values for the loaded neighbourhood. `QcBlockLightEngine` keeps the light of all loaded chunks (each step costs max(1, opacity), opacity 15 stops it, unloaded chunks are dark walls). Partial shapes of light-dimming blocks (stairs, slabs) have opacity 0 and stop light only at the faces they cover completely (`QcBlockState::lightBlockedFaces`, `QcLightPassage`, E-104); block light, sky light in the mesher and the sky column used for remeshing all follow that rule. A loaded chunk floods its sources and the light over its borders; a block whose light level or opacity changes clears the light that depended on it breadth-first and refills the cleared cells from their lit boundary and from sources; an unloaded chunk takes its light along. The engine runs on its own thread in `QcMeshScheduler`; results are immutable section snapshots (`QcChunkLight`) that the mesher reads instead of flooding (`QcMeshInput::blockLight`). A chunk is meshed once its light is known; a block change marks the sections next to the block, the sky-light column only when the opacity changed, and the sections whose light changed (plus neighbours of changed border cells); changes with light work are meshed together with their new light. `QcLightVolume` floods a volume in one go: the client's control command and light probe use it on demand, the mesher without light snapshots, and the tests as the reference the engine must match. Partial shapes (`QcBlockRenderTable` quads per state): faces on the cell border are hidden when a neighbour's faces on that side cover them (any opaque state, or the same translucent block), interpolate corner light and ambient occlusion of the full face, faces inside the cell take the light of the open space in front; faces lying on another box of the same state are left out. Entities and the hand read the engine's light at their position; items whose block gives off light are drawn at least that bright (`ItemLook::glow`); the server reads the block light of its engine for spawning (hostile mobs need at most 7 by default, `spawn.maxLight`). Inventory icons of blocks are drawn from their boxes (`QcBlockIcon`). Entities and the first-person hand use their own vertex format with a tint colour and the shaders `entity.{vert,frag}`; the hand is drawn last with `hand.vert`, which squeezes its depth to the front (E-034). Skeleton models are meshed every frame by `QcEntityMesher` from `QcAnimator` poses (E-033); the camera mode and its wall collision come from `QcViewCamera` (E-035). Block pipelines: opaque with alpha test, translucent (blended, no depth write, sorted back to front per section). Shaders: `src/app/shaders/block.{vert,frag}` (GLSL 440, compiled for all RHI backends by `qt_add_shaders`); the opaque pipeline uses the variant `block_opaque.frag.qsb` (`block.frag` baked again with `QC_OPAQUE`), which writes alpha 1, and `entity.frag` writes alpha 1 too: both pipelines draw without blending, and the partial alpha of the mip levels must not reach the target (screenshots, transparent targets such as the character previews; a colour write mask without alpha did the same but cost GPU time; E-332).

## Texture packs and atlas

Decisions E-297 to E-304, author guide `docs/Texturpakete.md`. Client side only; the content (and with it the mods' textures) still comes from the server.

- **Packs** (`QcTexturePackManifest`, `QcTexturePackLoader`, `QcTexturePackLibrary`): a folder with `texturepack.json` (format 1, name, description, resolution 16–512 as a power of two, licence, credits, `procedural`, preview) and `textures/<namespace>/<name>.png|json`. Found in `:/texturepacks` (built in), `<data>/texturepacks` and `<mods>/<mod>/texturepacks`; ids `builtin:`, `user:`, `mod:<mod>/`. The loader checks everything at the boundary (only listed plain files, no links or hidden files, file count and sizes, PNG signature and size against the resolution, damaged images, a decoded-memory budget, previews) and turns each problem into a translatable `QcTexturePackProblem`; a bad file is skipped, only a bad manifest makes a pack unusable. A loaded `QcTexturePack` is immutable and shared (`QcTexturePackRef`).
- **Sources** (`QcTextureSources`): per texture the active packs in priority order (image before spec; a `procedural` pack paints the content's definition), then the content; everything scaled to the atlas tile size (pixel-exact when enlarging).
- **HD procedural textures** (`QcProceduralTexture`, `QcTextureDetail`): the 16×16 pattern enlarged with Scale2x on similar colours (per pattern on or off), then grain and a bevel along strong edges; amounts per pattern, `detail` in a definition overrides them. 16× stays bit-identical to before.
- **Atlas** (`QcTextureAtlas`, `QcAtlasLayout`): a grid of cells of 1.25 tiles with a gutter of tile/8 that repeats the edge pixels; UVs measured in eighths of a tile, so the same for every tile size (`sameLayout`). Tiles are drawn in parallel by up to 8 short-lived `QThread`s (half the cores), each writing its own tiles and ending with a release store the caller reads after `wait()`; a thread that cannot start leaves its share to the caller (QtConcurrent's hand-over is invisible to ThreadSanitizer on macOS). The tile size is at most 256 (`Options::maxTileSize`; a 512× pack is shown at 256× with a notice), procedural packs paint at the tile size, not larger. Mip levels by alpha-weighted 2×2 averaging down to tiles of 8 pixels (gutter ≥ 1 pixel); cut-out tiles get their alpha raised per level until the share of drawn texels is back at that of level 0 (`QcAlphaCoverage`). Fully transparent texels carry the colour of the nearest drawn one (`QcAlphaCoverage::fillTransparentColour`, while the tiles are drawn; alpha stays 0), and `QcAtlasLayout::halve` keeps the plain mean of the colours of a fully transparent 2×2 block, so the GPU's blending between mip levels does not darken the edges of plants (E-332). The tile size is the highest pack resolution (stored at most 256), halved until the atlas fits `QcGpuLimits::maxTextureSize()` (8192 until a renderer reported `QRhi::TextureSizeMax`) and 256 MiB.
- **GPU** (`QcAtlasTexture`, app): a mipmapped RGBA8 texture from the first level within `TextureSizeMax` (a level the GPU refuses is retried one smaller, then the magenta placeholder, logged; the world renderer tries once per atlas and draws no world without a texture), the chain continued by halving to 1×1; sampler nearest/nearest with linear blending between mip levels. The world renderer and the character previews (`QcPreviewAtlasCache`) share it.
- **Switching** (`QcTexturePackController`, `GameController.settings.texturePacks`; `QcTextureStackBuild` in clientcore): listing the pack folders (on start and Reload), loading the active packs (reusing loaded ones; at most 384 MiB of decoded images for all active packs), reading changed previews (cached by file time) and building the atlas run in a worker thread; the old atlas stays until `atlasBuilt`. Every change (selection, Reload, entering or leaving a world) raises a generation; a result of an older generation is dropped when it arrives, so nothing waits for a running build and no stale atlas is applied. Only the active packs stay loaded. `QcWorldAtlas::apply` (app/session) re-uploads the texture, redraws icons and previews and keeps render table and meshes when the layout is unchanged (always, unless the content changed). A world start builds the atlas synchronously (`enterWorld`); leaving the world releases atlas, render table and content (`leaveWorld`). The menu's handbook icons use an atlas with tiles of at most 32 pixels; the menu preview's atlas is built in the background. Item icons use a small mip level (`QcBlockIcon::sourceTileSize` 32; 64-pixel icons above 16×). Settings page `TexturePacksPage.qml` (all pack texts as plain text, E-272), previews through the image provider `image://texturepacks/<id>`. Packs change everything drawn from the atlas; QML-drawn HUD elements (hearts, hunger, hotbar frames, crosshair, buttons) are not part of them (E-297).

## Armour and armour stands

Armour (decisions E-234 to E-239): items with `armour` are worn in four slots (`QcEquipment`, slot numbers 100–103 in the inventory messages). The server (`QcServerInventory`, `QcServerCombat`) checks every move, takes 4 % off armoured damage per point (at most 80 %), wears the pieces and breaks them (`QcArmour`), repairs two worn pieces in the grid (`QcRepair`) and drops armour on death. Others get a player's armour with the spawn (sent again on every change). Drawing: `QcArmourLook` turns worn pieces into `QcEntityMesher::Attachment`s – the boxes of the humanoid reference model a layer covers, grown and cut, plus parts on the bones – that `appendModel` draws with the bones (`Figure::attachments`, `Figure::hiddenBones`); the world, the character preview and armour stands share it. Armour stands are entities of their own (`QcArmourStandManager`, `QcServerStands`, `QcStandCommands`/`QcStandProperties`), no creatures: no AI, physics or health; they are synced with their pose (`QcStandPose`) and their cape (in the spawn's `appearance.cape`) and move only when a piston pushes them. A cape hangs outside a worn chest layer: `QcFigureLook::armour` sets `ModelLook::capeClearance` from how far the body attachments stand out behind the back (`QcArmourLook::capeClearance`), for players, the preview and stands alike. The showcase shows every set on stands (`QcShowcaseArmourArea`) and a pose demo from structure data.

## Character preview

Decision E-231. `CharacterPreview` (`QcCharacterPreview`, a `QQuickRhiItem`) shows the player's figure as a UI element in the character screen (`CharacterScreen.qml` with `CharacterPreviewPanel.qml` and `CharacterPresets.qml`), the inventory and the main menu's `ProfileCard.qml`. Every frame it builds the figure with `QcPreviewScene::build`, which uses the world's code for other players (`QcFigureLook::player`/`item`, `QcAnimator::animateBody`, `QcEntityMesher::appendModel`); `QcCharacterPreviewRenderer` draws it with the world's entity pipeline and shaders (`QcRenderPipelines`) at full daylight over a transparent background. `QcPreviewCamera` turns the figure (dragging) and zooms (wheel), `QcPreviewPose` gives the animations stand, walk and mine and turns the head towards the mouse pointer (`QcEntityPose::headYaw`) while the window is active. `QcPreviewPacer` lets it draw only while it is shown and at most 30 times a second (the menu's profile card 15); a hidden preview stops its timer. `QcPreviewSource` (`GameController.preview`) hands out the content and atlas (the world's, or in the menu the library content with an atlas built on first use), the look, the held item and the `--preview` hook, and sums the meshing time for the debug display's frame phase "Character preview". Looks and presets: `QcCharacterSettings` (`GameController.settings.character`) with `QcCharacterProfile` (colours on offer, four built-in presets, up to eight own presets stored as `characterPresets/<n>/…` in `settings.ini`, random looks). The server checks every look and name before taking them over (`QcProfileValidation`, E-232).

## Build options and test hooks

- **TLS (`cmake/QcTls.cmake`, decision E-872):** `QC_TLS` (default on) links the network layer
  against the bundled OpenSSL (imported targets `QcOpenSSL::SSL` and `QcOpenSSL::Crypto`, compile
  definition `QC_TLS_ENABLED`); the version and the SHA-256 of its release tarball stand in
  `3rdparty/openssl-version.txt`. `scripts/build-openssl.sh` builds it once into
  `~/.cache/qtcraft/openssl/<version>-<arch>-<config>` (`QC_OPENSSL_CACHE`; universal on macOS,
  macOS 13.3, shared libraries with `@rpath` install names); on Windows
  `scripts/windows/build-openssl.ps1` builds the DLLs `libcrypto-3-<x64|arm64>.dll` and
  `libssl-3-<x64|arm64>.dll` with MSVC, which QcTls.cmake copies next to the programs and tests;
  the first configure step runs the script when the entry is missing (`QC_OPENSSL_AUTO_BUILD`).
  Linux uses the OpenSSL 3 of the system (`find_package`). `QC_OPENSSL_ROOT` takes another prefix of the same
  version. At run time `QcTlsBackend::ensure()` makes `openssl` Qt's active TLS backend before the
  first certificate or socket; the libraries are already loaded when Qt's backend opens libssl by
  name, so it gets the same ones: on macOS through the executable's rpath (in the bundle
  `Contents/Frameworks`), on Windows as import DLLs from the executable's folder (Qt's
  `QSystemLibrary` also searches that folder first), on Linux the system's `libssl.so.3`. `QC_TLS=OFF` builds
  plain TCP with a configure warning (no certificate, no pinning, `test_tls_credentials` not built).

## Release bundle

`scripts/release.sh` (decisions E-073 to E-076) builds the preset `deploy`, copies `qtcraft.app` to `deploy/QtCraft.app`, adds the example mods under `Contents/Resources/mods`, runs `macdeployqt` with `-qmldir=src/app/qml` (Qt frameworks, QML modules in `Contents/Resources/qml`, plugins in `Contents/PlugIns`: platform, image formats, styles, TLS, multimedia with the FFmpeg backend whose libraries go to `Contents/Frameworks`, `qt.conf`), removes the SQL drivers that need foreign client libraries, signs ad hoc from the inside out and checks the result (otool, required parts, universal executable, signature, four starts of a copy in a temporary directory with audio output and caches kept there: world with the list of loaded images, mod and German texts, Launch Services, x86_64 under Rosetta when installed); it packs `QtCraft-<version>-macOS.zip` and `.dmg`. Inside the bundle nothing is looked up by source or build paths: base content, shaders, QML and translations are Qt resources in the executable, the bundled mods are found relative to the executable (`QcBundledMods::directory`). Player data stays in the application data directory (`~/Library/Application Support/QtCraft/QtCraft`: `settings.ini`, `worlds/`, `mods/`); on the first start, while `mods/` does not exist, the bundled mods are copied there switched off (`QcBundledMods::installDisabled`, a new staging folder `mods.installing-XXXXXX` renamed when complete). Info.plist comes from `cmake/Info.plist.in` (identifier `org.qtcraft.QtCraft`, version from `project()`, build number = UTC build time `YYYY.MMDD.HHMM`, minimum macOS 13.3 from `CMAKE_OSX_DEPLOYMENT_TARGET`, category games, high resolution, copyright, English and German).

All own targets are compiled with `-Wall -Wextra -Wpedantic -Werror -fno-exceptions` (MSVC: `/W4 /WX /EHs-c-`) through the `qc_project_options` interface target. Qt headers are system includes.
