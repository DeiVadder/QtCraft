# Modding

QtCraft mods are **data-only content packs**: JSON definitions (including synthesized sounds) and PNG textures, no executable code. The base game itself is such a pack (`content/qtcraft`, embedded in the binary) and is loaded by the same code, so everything the base game defines a mod can add or replace.

## Where mods live

| Game | Directory |
|------|-----------|
| Default | `<app data>/mods` (macOS: `~/Library/Application Support/QtCraft/QtCraft/mods`) |
| `QTCRAFT_DATA_DIR=<dir>` | `<dir>/mods` |
| `--mods-dir <dir>` | `<dir>` (game and `qtcraft-headless`) |
| `--no-mods` | base game only |

Every sub-directory with a `pack.json` is one mod. The main menu's **Mods** screen lists all mods with their state and lets you switch them off; the choice is stored in `mods.json` in the mods directory (`{"disabled": ["mod_id"]}`) and applies when the next world starts. The control interface reports the loaded packs with `{"cmd":"mods"}`.

Try the example mod shipped in the repository:

```sh
build/debug/src/app/qtcraft.app/Contents/MacOS/qtcraft --mods-dir mods
```

## Manifest: `pack.json`

```json
{
    "id": "rubies",
    "name": "Rubies",
    "version": "1.0.0",
    "description": "Example mod: ruby ore, ruby tools, a ruby block and the crystal beetle.",
    "dependencies": [{"id": "qtcraft", "minVersion": "0.1.0"}]
}
```

| Field | Required | Meaning |
|-------|----------|---------|
| `id` | yes | Lower-case letters, digits, `_`, `-`, `.` (starting with a letter or digit, no `..`, at most 64 characters). Also the default namespace of the pack's names. Must be unique; `qtcraft` is the base game. |
| `version` | yes | Dotted version number (`1`, `1.2`, `1.2.3`); `1` and `1.0.0` count as the same version. |
| `name`, `description` | no | Shown in the Mods screen. |
| `dependencies` | no | Pack ids, either `"other_mod"` or `{"id": "other_mod", "minVersion": "1.2"}`. Up to 64. |

## Load order

1. The base game.
2. Every enabled mod, each after all of its dependencies. Among mods that are ready at the same time, the smaller id goes first, so the order is always the same.

A mod is **skipped** (and every mod that depends on it) when its manifest is broken, a dependency is missing, disabled, skipped or older than `minVersion`, dependencies form a cycle, or its id is already taken. The game still starts; the Mods screen and the log say why.

Inside a mod, broken files are skipped one by one with a warning (`qtcraft.game: Content: mod rubies: …` in the log, `content warning:` on stderr for `qtcraft-headless`); the rest of the mod still loads. After loading, references to unknown items, blocks or textures are reported as warnings; such recipes never match and such drops are never given.

## Content files

All files are optional. Names without a namespace get the pack id (`ruby` in pack `rubies` is `rubies:ruby`); write `qtcraft:stick` to refer to base content or `other_mod:thing` to refer to a dependency.

| Folder | One file per | Notes |
|--------|--------------|-------|
| `blocks/` | block | Every visible, non-liquid block automatically gets an item that places it. |
| `shapes/` | block shape | Boxes, crossed planes, collision, conditions on states, turning; see below. |
| `parts/` | building-part family | Stairs, slabs, walls … made from every material of a kind; see below. |
| `materials/` | material or exclusion | Base block and kind of a material, or blocks that never get parts. |
| `items/` | item | Tools, weapons, food. |
| `recipes/` | recipe | Shaped (`pattern`, `key`) or shapeless (`ingredients`), up to 3 × 3. An ingredient `#tag` accepts every item with that tag (`#qtcraft:planks`, `#qtcraft:coals`, `#qtcraft:logs`). An ingredient with `emptiesTo` (a milk bucket) leaves that item behind: in its grid cell, else in the inventory (decision E-771). |
| `smelting/` | smelting recipe | One input item becomes a result in a machine of the recipe's `category`. |
| `stonecutting/` | stonecutting recipe | One input block becomes `result.count` of a result in the stonecutter (decision E-784); same fields as a smelting recipe without `category`, `seconds` and `experience`. |
| `mobs/` | creature | Stats, spawn rules, box model or skeleton with outfit, drops. |
| `models/` | skeleton | Bones with roles, pivots and slotted boxes. |
| `appearance/` | outfit, hair style or cape | Textures and tints per slot; hair boxes; cape shape. |
| `sounds/` | sound | Synthesis parameters; see below. |
| `textures/` | texture | `*.json` procedural textures or `*.png` files (at most 128 × 128, scaled to the atlas tile size), named by file name. |
| `lang/` | language | `en.json`, `de.json`, …: translation key → text. The language is the file name; a suffix `.handbook` is left out, so `de.handbook.json` adds German texts as well (other dots stay part of the language). |
| `handbook/` | handbook chapter | A chapter of the handbook's "Playing" category; see below. |
| `biomes/`, `features/`, `ores/` | world-generation entry | Used by the server's terrain generator. |
| `trades/` | set of offers of a profession | What villagers of a profession buy and sell (stage 37.2c); see "Trading". |
| `commands/` | command macro | A chat and console command made of other commands; see below. |
| `worldgen/terrain.json` | – | Global terrain settings (replaces the earlier one). |
| `structures/` | structure | Buildings from block layers with creatures, armour stands, contents, labels; a `showcase` entry makes it a demo of the showcase world; see below. |
| `villages/` | village style | The pieces, roads, lamp posts and block swaps of the villages of some biomes (E-403); see Villages below. |
| `worldgen/showcase.json` | – | Settings of the showcase world: ground, time of day, podium blocks, block categories (replaces the earlier one). |
| `worldgen/villages.json` | – | Where villages go, which creature lives in them and which golems guard them (E-403, E-421; a later pack changes the fields it gives); see Villages below. |
| `villagers/` | villager species | How the villagers of a creature kind live (E-411, E-421, server side only): daily routine, default look, fleeing, trading, breeding; see Villagers below. |
| `professions/` | profession | A villager profession with its workstation blocks, outfit layers and hat (E-421, server side only); see Villagers below. |
| `worldgen/flat.json`, `worldgen/void.json` | – | Flat world: default layer `preset` (`"bedrock,59*stone,3*dirt,grass_block"`); void world: `platform`, `platformRadius`, `platformY`; both `timeOfDay`, `daylightCycle`, `mobSpawning` (E-223; replace the earlier ones). |
| `held.json` | – | How items are held, by category (decision E-831; a later pack overrides only the fields it sets; synchronised to clients): `{"categories": {"<category>": {"grip": ..., "firstPerson": {...}, "swing": {...}, "thirdPerson": {...}}}}`, see “Held items” below. |
| `weather.json` | – | What the weather does (decision E-396; replaces the earlier one, missing keys keep the defaults; server side only): `lightning` with `meanSeconds` (10: one strike per player on average every that many seconds of a thunderstorm, 0.5–3600), `damage` (5, 0–100, players through their armour), `radius` (3, 0–8: blocks to each side and below the struck cell, six above), `burnSeconds` (8, 0–60: the struck bodies burn), `sparks` (2, 0–8: fires a strike may light at and right around the struck cell, each a spark with all limits of fire and none while fire does not spread); `snow` with `layer` (`snow_layer`: the block snow leaves on top of opaque blocks with a full top face under the open sky; it must be a block of this or an earlier pack that is not opaque, no liquid and has `"support": "below"`, else the whole file is refused with a warning, decision E-397) and `columnsPerTick` (4, 0–64: random columns within 48 blocks of each player looked at per tick while it snows). The values in the handbook are those of the base game. |

`"render"` is `opaque` (the default), `cutout` (alpha-tested: leaves, plants, torches, rails, anything with holes) or `translucent` (blended: glass, water). An `opaque` block is drawn without alpha test (decision E-756), so its textures must have no transparent texels: a block with holes needs `cutout`.

Blocks can also define plants: `"shape": "cross"` draws two crossed quads (non-solid cutout by default), a drop can carry a `"chance"` (0–1, default 1), and a `"sapling"` object turns a block into a sapling that grows into a tree or column feature:

```json
{
    "name": "ruby_sapling",
    "shape": "cross",
    "hardness": 0,
    "sapling": {
        "feature": "ruby_tree",
        "minSeconds": 90,
        "maxSeconds": 240,
        "plantOn": ["qtcraft:grass_block", "qtcraft:dirt"],
        "plantChance": 0.75
    },
    "textures": { "all": "ruby_sapling" }
}
```

`plantOn` lists the blocks it may stand on (empty: any solid block), `plantChance` is the chance that a dropped sapling item plants itself when it despawns. Leaves of tree features decay once no trunk of a tree feature is within four blocks; give them a drop with a chance (e.g. the sapling, 0.08) to let forests regrow. The procedural texture pattern `sapling` draws a small plant.

A plant that grows upwards by itself (like sugar cane) gets a `"growth"` object: `maxHeight` (2–64, default 3) is the tallest column it reaches, `averageSeconds` (1–86400, default 600) the average time between two growth steps of one column. It needs `"support": "below"`. Growth runs on random ticks of loaded sections (three random blocks per section and tick, so each block is ticked about every 68 s); a ticked top block adds a block of its kind above when the block above is air, the column is shorter than `maxHeight` and the column's base still has its `ground` and `groundLiquid`. Example: `"growth": { "maxHeight": 4, "averageSeconds": 300 }`. Server side only (not sent to clients); the handbook shows it on the block page.

Farming (stage 27, decisions E-289 to E-294; all server side only):

- `"crop"` makes a block ripen in stages on the same random ticks: `property` (default `age`; a state property with at least two values, the last one is ripe), `averageSeconds` (1–86400, default 1200, from the first to the ripe stage on wet soil), `dryFactor` (0–1, default 0.5, pace on dry soil or other ground), `minLight` (0–15, default 9), `plantChance` (0–1, default 0: a dropped item placing this crop that rests on free soil plants one of its stack with this chance once a second). With `fruit` (a block), `fruitSeconds` (default 300) and `fruitGround` (block names) a ripe crop is a stem that puts its fruit onto a free neighbour with that ground, one at a time. Crops need `"support": "below"` (usually `"ground": ["farmland"]`), must not be solid and cannot also have `growth`. Draw the stages with a shape whose parts are conditioned on the stage; a part's `texture` slot also applies to its `crosses`.
- `"soil"` makes a block farmland: `property` (default `moist`, last value wet, first dry), `water` (default `qtcraft:water`), `reach` (0–8, default 4), `revertsTo` (required, another block).
- `"tillsInto": "farmland"` on a block and `"tills": true` on an item (the hoes) turn the block into that soil when the item is used on it.
- `"flattensInto": "dirt_path"` on a block and `"flattens": true` on an item (the shovels, decision E-406) turn the block into that path when the item is used on its top with air above, wearing the item by one (not in creative mode). `"coveredInto": "dirt"` on a block turns it into that block at its next block update while an opaque full block lies on it (the dirt path).
- `"carving": { "into": "carved_pumpkin", "drop": "pumpkin_seeds", "count": 4 }` on a block and `"carves": true` on an item (the shears, decision E-472) turn the block into `into` when the item is used on it, its `facing` towards the clicked side (on the top or bottom: towards the player), `count` (0–64) of the item `drop` falling out of the clicked face, wearing the item by one (not in creative mode).
- `"dyeProperty": "color"` on a block and `"dye": "red"` on an item (the sixteen dyes, decision E-765): using the item on the block sets that state property to the dye's colour when the property has that value, and takes one dye (not in creative mode; the same colour again takes none). The signal indicator light changes its colour this way.
- `"sign": {"lines": 4, "lineLength": 15}` makes a block a sign (decision E-766): placing it or using it (not sneaking) opens a text screen with that many lines (1–4) of at most `lineLength` characters (1–32); the server cleans the text (no control or format characters, trimmed) and keeps it with the chunk, and every player near it sees it drawn on the front of the board. The text lies on the shape `qtcraft:sign` (a board on a post, or flat on a wall) and needs the states `attach` (`floor`, `north`, `east`, `south`, `west`) and `rotation` (`"0"`–`"15"`, the shape's `spin`): on the floor it turns towards the player in sixteenths of a turn, on a wall it stays `"0"`. Any block with a `rotation` property takes the player's view this way when placed.
- `"dial": "compass"` or `"dial": "clock"` on an item (decision E-769): while it is held, the HUD shows beside the hotbar a needle pointing to the world spawn, or a clock face with the time of day.
- `"map": "empty"` with `"filledMap": "<item>"` makes an item an empty map (decisions E-798, E-804): the use button turns one of it into the filled map item with a new map id, scale 0, around the player (creative players keep the empty map). `"map": "filled"` makes an item a filled map: its stack carries the map id in `damage`, held in the hand it reveals the land around its holder and is drawn large on the screen; stacks of one map id stack up to `maxStack`. `"zoomsWith": "<item>"` on a filled map: the map in the middle of the 3×3 grid with eight of that item around it makes a new map one scale larger (up to scale 4); a filled map with empty maps of its kind in the grid copies it. A map item can neither place a block nor wear out.
- **Stacking:** two stacks merge when item and `damage` are equal (`maxStack`, 1–64, default 64). An item with `durability` (tools, armour, launchers) always stacks to one, so worn items never merge; an explicit larger `maxStack` is overridden with a warning.
- `"strippedInto": "stripped_oak_log"` on a block and `"strips": true` on an item (the axes, decision E-753) turn the block into that block when the item is used on it, keeping the state properties both have (the `axis` of a log); nothing drops and the item wears by one.
- **Climate of a biome** (decisions E-014, E-821, E-824; all fields in `docs/Architektur.md`, section Content): `temperature`, `humidity` and `ruggedness` (0–1) place the biome in climate space, and a column takes the biome whose point lies nearest to its climate. `spread` (0–0.1, default 0) is subtracted from the biome's squared climate distance: its cell grows with straight borders and keeps its neighbours (the base game's desert, jungle and swamp). `rarity` (0–1, default 0) lets the biome take part only inside the spots of the world's rarity map (the flower valley). Keep cold biomes (the base game's tundra, snowy taiga, taiga) at least 0.3 from hot ones (desert, forest steppe, jungle edge, jungle, swamp) in climate space, or they meet on the map.
- **Rivers** (decisions E-840, E-841): with `"rivers": true` in `worldgen/terrain.json` (the base game) winding rivers run through the land at the sea level down to the sea or into lakes; they cross mountains in gorges and fade out in the driest land (humidity below about 0.2); small closed rings of the river noise fade out too. The water of a river channel takes a river biome: a biome with `"river": true`, which the climate never chooses (its `temperature` and `humidity` only set the weather); a land biome names the river biome of its rivers with `riverBiome` (the base game's tundra, snowy taiga and taiga: `frozen_river` with `frozenWater` ice), else `riverBiome` of `worldgen/terrain.json` (the base game's `river`), else the first river biome. A river biome's `underwater` is the bed, `underwaterPatches` (`[{"block", "share"}]`, both required, up to 8, shares adding up to at most 1; blocks that are not solid or are liquid are left out with a load warning) mixes patches of a few blocks into it (any biome may use it), and its `beach` lines the low banks in patches. A river biome's own `riverBiome` and `rarity` are ignored (load warning). Roads of villages on land cross rivers on bridges (a deck one block above the water, oak planks and logs through the style's `palette`) up to 24 blocks wide; at a lake or the sea they end as before. Mob spawn lists name the river biomes like any biome (the base game's salmon).
- **Cold edges** (decision E-858): with `"freezing": {"block": "ice", "temperature": 0.28, "riverTemperature": 0.2, "ragged": 0.03}` in `worldgen/terrain.json` (the base game) the top water layer at the sea level freezes by the climate's temperature of its column instead of by biome: still water (lakes, the sea) below `temperature`, the water of river channels only below `riverTemperature`, with a noise of about `ragged` added to the temperature, so the ice ends in a ragged edge with single floes beyond it and crosses biome borders. A biome's `frozenWater` names the block its water freezes to; biomes without one take `block`. Without `freezing` every biome with a `frozenWater` freezes all its water as before. `"groundBlend": 4` (0–8, default 0) lets every column near a biome border take its ground blocks (surface, soil, beach, river bank and bed) from the biome at a column up to that many blocks away in a jittered direction, so grass, snow, sand and gravel mix over a few blocks instead of meeting on the border; a river channel takes the bed of that biome's river.
- **Vegetation of a biome** (decision E-814): `"vegetation": {"grass": {...}, "flowers": {...}}` on a biome, each layer optional with `plants` (1–32: block names, or `{"block", "weight"}` with weight 1–1000, default 1), `density` (0–1 per surface column, default 0: only bone meal grows the layer), `patchSize` (0–512 blocks: one kind grows in areas of about half this size with frayed borders; 0 mixes the kinds column by column) and `patches` (`chance` 0–1 per cell of 16 × 16 blocks, `tries` 1–128, default 32, `radius` 1–8, default 5): a patch picks one plant of the layer by weight at a random centre in the cell and tries `tries` columns at most `radius` blocks away on each axis (most near the centre), planting it on every free dry column of the same biome where it may stand, like the reference's flower patches. The generator places a biome's `features` first, then the scattered grass, then the scattered flowers, then the patches; every plant stands only on its block's `ground`. The base game lists the block `tall_grass` (and ferns in the jungle and the taiga) and its flowers this way; deserts and tundras have grass without density and patches, for bone meal on a grass block placed there, and the handbook leaves such a layer out. Unknown plants and solid or liquid blocks are left out of a layer with a load warning; a `vegetationBiome` in `terrain.json` that names no biome is warned about too. A mod adds a flower to a base biome by replacing the biome with its own copy (as `mods/rubies` does with the ruby rose).
- The base world grows wheat, carrots and potatoes only in the fields of villages (decision E-406; the style's `crops`); the plant features `wild_carrots` and `wild_potatoes` stay in the content for mods (a biome lists them under `features`) and later oases, but no base biome places them. Tall grass still drops wheat seeds.
- `"ignites": true` on an item (flint and steel, decision E-393) lights fire in the cell in front of the clicked face where fire may stand (a spark with the limits of fire), wearing the item by one per fire (except in creative mode); with `"dispense": "ignite"` a dispenser does the same in front of it. Such an item neither places, tills, scoops nor bottles.
- `"fertilizes": true` on an item (bone meal, decision E-426): used on a crop that is not ripe it grows 2–5 stages at once, on a sapling it lets the tree grow on the next tick with a chance of 45 % (with room for it); on a block with `"growsVegetation": true` (the grass block, decision E-814) and air above it it grows grass and flowers of the biome around it (128 tries, each a random walk of up to 7 steps over that block from the cell above it; a try ending in air plants a flower of the biome's `flowers` with one chance in 8 if it has any, else a plant of its `grass`, where the plant may stand; where the generator names no biome (flat, showcase and void worlds) the biome `vegetationBiome` of `worldgen/terrain.json` counts, the base game's plains); each takes one item, except in creative mode. Such an item neither places nor ignites. Dispensers throw it (no `dispense` action for it yet).
- **Launchers and ammunition (decisions E-425, E-427):** `"launcher": {"drawSeconds": 1.0, "speed": 60.0, "minPower": 0.1, "ammunition": ["#arrows"]}` makes an item a launcher (the bow): held with the use button down it draws for up to `drawSeconds` (0.05–10), released it shoots the first ammunition of the inventory it takes at `speed` m/s (1–200) times the power of the draw, `(f² + 2f) / 3` of the share `f` of `drawSeconds`; below `minPower` (0–1) nothing is shot. `ammunition` lists what it takes: item names and item tags as `#tag` (up to 64; unqualified names take the pack's namespace, so the bow's `#arrows` is `#qtcraft:arrows`). Without the list a launcher takes every ammunition item that is not `throwable`; an empty list (`[]`) means the same and is reported with a warning. A mod's new arrow carries `"tags": ["qtcraft:arrows"]` and fits the bow. Every shot uses one ammunition item and wears the launcher by one (`durability`), except in creative mode, where it also shoots without ammunition (the projectile of the item of the first projectile kind it takes). A launcher neither places, is eaten nor worn. `"projectile": "<name>"` makes an item ammunition (the arrow): the projectile kind it becomes when shot or thrown.
- **Fishing rods (decision E-503):** `"fishing": {"bobber": "fishing_bobber", "speed": 15.0, "minSeconds": 5.0, "maxSeconds": 30.0, "rainFactor": 0.75, "biteSeconds": 1.0, "maxDistance": 32.0, "castSound": "item.bow.shoot", "biteSound": "water.splash", "loot": [{"item": "raw_cod", "weight": 60}, {"item": "stick", "weight": 4, "count": 1}]}` makes an item a fishing rod (server side only, except that the client learns the item fishes). The use button (at most every 0.25 s) casts `bobber` (a projectile kind, required; give it `"floats": true`, `"onHit": []`) at `speed` m/s (1–200) along the view and, pressed again, reels it in. While the bobber floats on water (lava burns it up, and nothing bites elsewhere) a fish bites after a wait drawn evenly between `minSeconds` and `maxSeconds` (0.05–3600), times `rainFactor` (0.01–10) where it rains on the water; the bite lasts `biteSeconds` (0.05–60), the bobber dips and `biteSound` plays. Reeling in during the bite throws one entry of `loot` (1–64 entries; `item` required, `weight` 1–10000, default 1, `count` 1–64, default 1), drawn by weight, from the bobber to the player and wears the rod by one (`durability`; not in creative mode); reeling in at any other time catches nothing. A missed bite starts a new wait. The bobber goes when the player selects another hotbar slot, dies, leaves or is more than `maxDistance` (1–128 m) away, and it is never saved. The loot table belongs to the rod, so a pack's rod can fish other things. A rod whose bobber kind no pack has, or with no known loot left, does not fish (warning); loot naming unknown items is left out (warning). A rod neither throws, launches, places, is eaten, drunk nor worn.
- **Throwing by hand (decision E-427):** `"throwable": {"speed": 30.0, "cooldownSeconds": 0.25, "inaccuracyDegrees": 1.0}` together with `projectile` makes an item thrown with the use button (the snowball): one item at once at `speed` m/s (1–200) along the view, turned at random by up to `inaccuracyDegrees` (0–45); the player can throw that item again after `cooldownSeconds` (0–60). Each throw uses one item, except in creative mode. A throwable item neither launches, places, is eaten nor worn; `throwable` without a known projectile is dropped with a warning, and with `ignites`, `fertilizes` or a bucket or bottle use those uses are dropped with a warning (the use button throws it). Throws count against the server's rate of use actions. Signal Dispensers do not throw projectiles yet (they drop the item like any other).
- **Projectile kinds** (`projectiles/<name>.json`, decision E-425, server side only): `name`, `item` (required: the ammunition it is shot from, drawn as and given back when picked up), `gravity` (m/s², default 20; the snowball 12 like the reference's thrown items), `drag` and `waterDrag` (share of the speed lost per second as an exponential rate, default 0.2 and 10), `damage` (health points per 20 m/s of speed, rounded up, default 2: a full bow shot deals 6; only the default of the damage effect, see `onHit`), `size` (edge of the box that hits bodies, default 0.5 m), `despawnSeconds` (stuck, default 60), `flightSeconds` (default 60), `sticks` (default true; a projectile that does not stick goes when it hits a block), `hitSound`, `stickSound`, `onHit`, `floats` (default false; decision E-503: in water it rises at 1.5 m/s to the surface of the uppermost water block and rests there, its horizontal speed dying away with `waterDrag`; a fast one crossing water lands in it rather than in the floor below; a liquid that sets things alight, like lava, burns it up; the fishing rod's bobber). Armour takes its share of the damage; a projectile that meets a body during its short invulnerability bounces back, unless it breaks. A kind with an empty `onHit` (`[]`) does nothing to the bodies it meets and bounces off them.
- **Hit effects** (`onHit`, decision E-427, server side only): a list of up to 16 effects that together make one hit when the projectile hits a body, each `{"type": …}` with the type's own number; their order does not matter (the damage is dealt once, the strongest knockback and the longest burning count). Without `onHit` a kind has `[{"type": "damage", "amount": <damage>}, {"type": "knockback"}]` (the arrow). Types: `damage` (`amount` 0–1000, default the kind's `damage`: health points per 20 m/s of speed, rounded up; the body is not pushed unless a knockback effect says so), `knockback` (`strength` 0–10, default 1: pushes the body along the flight, 1 like a blow, also without damage; the strength scales the push, the lift grows only up to that of a blow; a hit without damage gives the body no invulnerability), `ignite` (`seconds` 0–3600, default 5: the body burns at least that long, as from fire; creative players do not), `break` (the projectile goes at any hit on a body or a block instead of bouncing or sticking; `sound` plays where it breaks), `effect` (`effect` names a status effect kind, `seconds` 0.05–3600, default 5, `level` 1–10, default 1: the body hit gets the effect when the hit counts, decision E-450), `spawn` (`mob` names a creature, `chance` 0–1, default 1, `count` 1–16, default 1, `groupChance` 0–1 and `groupCount` 1–16, default 4: where a breaking projectile breaks, at a body or a block, with `chance` `count` young creatures appear, or with `groupChance` of those `groupCount`; the egg: chance 1/8, group chance 1/32 of 4, decision E-452). `splash` (`radius` 0.5–8, default 4; decision E-624): where the projectile breaks, every living body within `radius` metres of that place (measured to the nearest point of its body) but its thrower takes the projectile's damage effects (their `amount`, not per speed; through armour, like a status effect's damage) and its status effects (their `seconds`), both times its share 1 − distance / `radius`; the body hit takes nothing else (a splash potion needs `break` too). The witch's poison: `"onHit": [{"type": "splash", "radius": 4}, {"type": "effect", "effect": "poison", "seconds": 20}, {"type": "break", "sound": "block.glass.break"}]`. Example, the snowball: `"onHit": [{"type": "knockback"}, {"type": "break", "sound": "block.snow.break"}]`. A type the game does not know is left out with a warning when the content is loaded, the rest of the list stays. New types are code: a row in `QcHitEffect::types` and a handler in `QcHitEffects`. An `effect` or `spawn` entry naming a kind no pack has is left out with a warning too. `teleport` (`damage` 0–1000, default 5: the player who threw it comes to where it lands, on a body or a block, and takes that much as fall damage; decision E-460) places the thrower with the feet in the nearest cell where a player fits (no solid block, liquid, fire or magma, only in loaded chunks: the cell of the landing point, else one around it, above first) and does nothing when there is none or the thrower is gone (the thrower is not saved, so a pearl that flies on after a load teleports nobody); a projectile with `teleport` always breaks where it lands. The ender pearl: `"onHit": [{"type": "teleport", "damage": 5}, {"type": "break", "sound": "entity.ender_pearl.land"}]`, thrown (`throwable`, `cooldownSeconds` 1). Planned: explosions.
- **Status effects** (`effects/<name>.json`, decision E-450; they reach the client): `name`, `translation` (default `effect.<namespace>.<name>`), `icon` (an item whose picture the HUD shows beside the time left), `colour` (`"#rrggbb"`), `tintsHearts` (the hearts take the colour while it lasts), `damage` (dealt every `periodTicks` ticks at level I, 0–1000, default 0), `periodTicks` (1–72000, default 25; every level above I halves it, at least 1), `minHealth` (its damage never takes the health below this; poison: 1), `speed` (share of the speed it adds per level, −1 to 1, default 0; decision E-838: slowness −0.15, so level I moves at 85 % and level II at 70 %; walking, swimming, sneaking and sprinting players and creatures that walk or hover, never below 0; flying players are not slowed; it reaches the client, whose prediction moves the player as slowly) and `exhaustion` (food exhaustion per second at level I times the level, 0–100, default 0; hunger: 0.1; players only, server side only). Bodies have at most one effect of each kind: a higher level replaces it, the same level keeps the longer time. Creatures name kinds that do nothing to them in `immuneTo` (`["poison"]`), and hostile creatures give effects with their blows in `blowEffects` (`[{"effect": "poison", "seconds": 7, "level": 1}]`, at most 8; only when the blow counts). Operators give and take effects with `/effect`.
- **Enchantments** (`enchantments/<name>.json`, decision E-864; they reach the client): `name`, `translation` (default `enchantment.<namespace>.<name>`), `effect` (required; one of the effects the game knows: `efficiency` (a matching tool mines faster by level² + 1), `unbreaking` (a use wears tools with chance 1/(level + 1), armour with 0.6 + 0.4/(level + 1)), `sharpness` (+0.5 × level + 0.5 melee damage), `protection` (level protection points per piece against everything armour softens and falls) and `feather_falling` (3 × level points per piece against falls only); at most 20 points, 4 % each), `maxLevel` (1–10, default 1), `weight` (how often the table picks it against the other candidates, 1–1000, default 10), `items` (required, 1–16 item kinds: a tool category such as `pickaxe`, `digger` for pickaxe/axe/shovel/hoe, `weapon` for items without tool category that hit harder than a hand, `armour` and `armour_head`/`armour_chest`/`armour_legs`/`armour_feet`, `launcher`, `durable` for everything that wears), `conflicts` (enchantment names that never come together with it, both ways), and the enchanting power each level needs: `minPower` + `powerPerLevel` × (level − 1) up to that plus `powerSpread` (defaults 1, 10, 50). Items take part with `enchantability` (0–100, default 0 = the table takes none; wood 15, stone 5, iron 14, gold 22, diamond 10; leather armour 15, iron 9, gold 25, diamond 10; bow 1, as in the reference). A block with `"enchanting": true` opens the enchanting table's screen; offers are paid with `qtcraft:lapis_lazuli` and levels, and up to 15 `qtcraft:bookshelf` blocks two blocks away from the table (with a free or replaceable block between) raise them. Enchantments sit in the stack's data (component 4) and show in the tooltip.
- **Anvil and name tags** (decision E-866): a block with `"anvil": true` opens the anvil's screen (repair, combine, rename, paid with levels); `wearsInto` names the block it wears into on use or after a fall (empty: it breaks); `landingDamage` (0–40, per block fallen beyond the first, with `falls`) hurts bodies where it lands. Items name their anvil repair material with `repairWith` (an item name or `#tag`; each item restores a quarter of the durability); `"nameTag": true` makes an item a name tag (written at the anvil, it names a creature it is used on). Anvil uses sit in the stack's data (component 5, prior work).
- **Anvil swaps** (decision E-870, server side only): a block with `"anvilSwap": {"into": "<block>", "with": "<item>"}` turns into `into` at the anvil and back: a whole stack (up to its size) in the left slot and one `with` in the right one give the same number of the other block, for one level per started 16 items (a full stack of 64: 4), plus the prior-work penalty and one level for a rename in the same step; a swap does not raise the stack's prior work, so swapped stacks stack with fresh ones, and it wears the anvil like any use. Declare it on one of the two blocks (the base game: on the decoupled variants `decoupled_signal_piston`, `decoupled_sticky_signal_piston`, `decoupled_signal_dispenser`, `decoupled_signal_dropper`, copies of their ordinary blocks with `"quasiConnectivity": false`, swapped with `signal_dust_chunk`); both items then carry it. A swap whose block has no item, that turns a block into itself, names an unknown item or an item that already swaps with another one is left out with a warning; the same pair declared on both blocks counts once. The handbook shows it on both blocks.
- A drop may carry `"when": {"age": "7"}` (like shape conditions): it only drops from those states.
- A block drop may carry `"maxCount"` (0–64): it drops between `count` and `maxCount` items, chosen evenly (lapis lazuli ore: 4 to 9; decision E-398).
- **Experience (decision E-398, server side only):** `"experience"` is a whole number of points or `[min, max]` (0–100000) for an even choice. On a block, mining it with a tool that gets its drops gives that much as experience orbs (ores: coal `[0, 2]`, diamond `[3, 7]`, lapis lazuli `[2, 5]`, Signal Dust ore `[1, 5]`); on a mob, a player killing it does (zombie 5, pig and sheep `[1, 3]`); `breeding.experience` is what a pair gives when a young one is born (default `[1, 7]`). Smelting recipes take `"experience"` per item smelted (0–100, may be fractional, e.g. 0.7 for iron); the furnace gathers it until a player takes from the output, a fraction becomes one more point with its chance.
- A peaceful creature may carry `"breeding": {"food": ["carrot"], "loveSeconds": 30, "cooldownSeconds": 300, "growUpSeconds": 1200, "partnerDistance": 8}` (the food list also reaches clients).
- A creature on the ground may lay: `"lays": {"item": "egg", "minSeconds": 300, "maxSeconds": 600, "sound": "mob.chicken.plop"}` (decision E-452, server side only; `minSeconds` and `maxSeconds` 1–86400, `maxSeconds` defaults to at least 600). Every awake adult drops one `item` at its feet after a time chosen evenly between the two, then chooses anew; young ones do not lay. The time is not saved: a loaded creature chooses a new one. The chicken lays eggs; the egg is a throwable item whose projectile has a `spawn` hit effect (one chick in eight, of those one in 32 four).

```json
{
    "name": "ruby_berries",
    "shape": "qtcraft:crop",
    "states": { "age": ["0", "1", "2", "3", "4", "5", "6", "7"] },
    "support": "below",
    "ground": ["farmland"],
    "crop": { "averageSeconds": 900, "plantChance": 0.9 },
    "drops": [{ "item": "ruby_seeds", "when": { "age": ["0", "1", "2", "3", "4", "5", "6"] } },
              { "item": "ruby", "when": { "age": "7" } }],
    "textures": { "all": "ruby_ripe", "slots": { "young": "ruby_young", "growing": "ruby_young", "ripe": "ruby_ripe" } }

```

Texture pattern for fire: `fire` (flames on a transparent background, primary at their edges, secondary in their core).

Texture patterns for farms: `crop`, `root_crop`, `stem`, `farmland`, `pumpkin_side`, `pumpkin_top`, `melon_side`, `hoe`, `wheat`, `bread`, `carrot`, `melon_slice`, `pie`.

Furnaces and other machines come from data too. A block with a `machine` object opens a screen with an input, a fuel and an output slot; `smelting/*.json` says what a machine of that category makes, and `fuelSeconds` on items or blocks says how long they burn (an item created for a block inherits the block's value):

```json
{ "name": "kiln", "hardness": 3, "tool": "pickaxe", "toolLevel": 1,
  "machine": { "category": "firing", "speed": 2.0 },
  "textures": { "all": "kiln_side", "north": "kiln_front" } }
```

```json
{ "name": "fired_clay", "category": "firing", "input": "qtcraft:clay",
  "result": { "item": "fired_clay", "count": 1 }, "seconds": 8 }
```

| Field | Meaning |
|-------|---------|
| `machine.category` | Recipe category the machine works on (default `smelting`, the base furnace). Plain names without namespace (lower-case letters, digits, `_`, `-`, `.`, at most 64 characters), so a mod can add recipes to the base furnace by using `smelting`. |
| `machine.speed` | 0.01–100 (default 1): seconds of recipe work per second; fuel burns at the same rate. A block cannot be a crafting table and a machine. |
| `machine.kinds` | Recipe kinds the machine takes (1–16 names like categories; decision E-770); without it every recipe of its category. The base smoker takes `["food"]`, the blast furnace `["metal"]`, both at speed 2; the furnace has none and takes everything. |
| `smelting`: `input`, `result` (`item`, `count` 1–64), `seconds` (0.05–3600, default 10), `experience` (0–100 per item, default 0, server side only, E-398), `category`, `kind` | Per category and input the first recipe in load order counts; a later one is reported as a warning. To change a base recipe, reuse its name. `kind` (a name like a category; base: `food` for meat, fish and potatoes, `metal` for raw metal) lets machines with `kinds` take it; a recipe without a kind works only in machines without `kinds` (a mod's recipes stay furnace-only unless they name a kind). |
| `campfire` (blocks) | A campfire (decision E-772): `slots` (0–4) items laid on it with the use button cook by the recipes of `category` (default `smelting`) and `kinds` in `seconds` (default 30, the recipe's time does not count), without fuel, and drop beside it when done; `extinguishesInto` is the block it becomes when a shovel or a bucket of a liquid without contact damage is used on it (the items drop), `lightsInto` (on the unlit block) the block that flint and steel or a dispenser lights it into. Its items are saved with the chunk; a structure's `contents` lays one item per place onto it. |
| `bites` (blocks) | `{"food": 1–20}` (default 2): the block is eaten where it stands, one bite per use while the player is hungry; the state `bites` counts the bites, the bite after its last value removes the block (cake, decision E-773). `"signal": {"comparator": "bites"}` reads twice the bites left. |
| `floats`, `burnsItems` (blocks) | `floats`: placed onto a liquid the player aims at (the cell above it; a lily pad with `"ground": ["water"]`, decision E-774). `burnsItems: false`: its `contactDamage` hurts bodies but leaves items lying in it (the campfire). |
| `fuelSeconds` (items and blocks) | 0–100000, default 0 (no fuel). Base values: coal and charcoal 80, wood 15, wooden tools 10, sticks and saplings 5. |
| `food` (items) | Food points restored when eaten, whole points up to 20 (larger values fill the bar). |

A machine lights one fuel item only when its input has a recipe and the result fits into the output; machines work only while their chunk is loaded, and their contents fall out when the block is broken. The server limits a world to 4096 machines.

### Shapes, states and building parts

Blocks can be any set of boxes (decision E-045). A shape is named in `shapes/` (or written inline as the block's `shape` object); the base game has `cube`, `cross`, `cactus`, `stairs`, `slab`, `fence`, `fence_gate`, `wall`, `pane`, `door`, `trapdoor`, `torch`, `ladder`, `chest`, `facing_cube`, `pillar` (a full cube turned by `axis`: logs, decision E-751) and `chain` (two thin crossed planes along the state `axis`, texture slots `links` and `across`). Unqualified shape names refer to the pack's own shapes, except `cube` and `cross`, which always mean the base ones; write `qtcraft:stairs` to use a base shape.

```json
{ "name": "pillar", "rotate": "facing", "flip": "half",
  "parts": [
    { "boxes": [[0.25, 0, 0.25, 0.75, 1, 0.75]] },
    { "when": { "open": true }, "boxes": [[0, 0, 0, 1, 0.125, 1]], "collision": [], "texture": "lid", "uv": "box" }
  ] }
```

| Field | Meaning |
|-------|---------|
| `boxes`, `crosses` | `[x0, y0, z0, x1, y1, z1]` in metres within the cell (0..1). Crosses are two diagonal planes (plants) and never collide. At most 32 parts with 16 boxes each and 64 boxes, crosses and collision boxes per shape together. All shape variants of all blocks together may derive at most 131,072 boxes (states that turn, flip and select the same parts share one variant); a block or shape beyond that budget is refused with a message. |
| `when` | Property → value or list of values; the part applies when all hold. |
| `collision` | Boxes for bodies instead of `boxes` (up to 1.5 m high, `[]` for none). |
| `target` | Boxes the player points at (aim and outline) instead of the drawn ones, neither drawn nor collided with; once a part of a state has them, only these are pointed at (tripwire: a flat box over the whole cell). |
| `texture`, `uv` | Texture slot of the block for these boxes (`textures.slots`), `uv: "box"` stretches the whole texture over each face (torches) instead of cutting the part where the face lies. `"$color"` takes the slot named by the state's value of the property `color` (any property; every value needs a slot), so one part draws all colours of the signal indicator light (decision E-765). |
| `rotate`, `flip` | Shapes are drawn for a block facing north; the property in `rotate` (values `north`, `east`, `south`, `west`; `up` and `down` tilt north to the sky or the ground; for an `axis` property `x` and `z` lay a block authored along y along that axis, `y` leaves it) turns them, the one in `flip` mirrors them upside down when its value is `top`. A shape's `spin` names a property with the values `"0"`–`"15"` that turns the shape in sixteenths of a full turn about the vertical axis on top of `rotate` (standing signs, decision E-766): the boxes that collide and are pointed at turn by whole quarters, the drawn faces exactly. Face textures turn with `rotate`; on a full cube the top and bottom textures turn with a horizontal turn, and a lying block turns the textures of its sides so that stripes run along it (decision E-751). |

Block states (decision E-046) are declared per block: `"states": { "facing": ["north", "east", "south", "west"], "open": [false, true] }` (the first value is the default; at most 8 properties of 32 values and 2048 states per block). The server derives these properties when a block is placed or its neighbours change: `facing` (`"facing": "away"` from the player, `"toward"` for fronts, or `"against"`: towards the clicked block on a side face and where the player looks on a floor or ceiling, the vertical slabs; decision E-755), `half` and `type` (`bottom`/`top`, slabs add `double`), `attach` (`floor`, `ceiling`, `north`, … towards the clicked block), `axis` (`x`, `y`, `z`: the axis the clicked face lies across, so a chain runs away from the clicked block; decision E-742), `hinge`, `shape` of stairs (a block with `facing`, `half` and `shape` holding `straight`, `inner_left`, `inner_right`, `outer_left` and `outer_right` takes outer and inner corners from the stairs in front of and behind it, decision E-754), `double` of vertical slabs (two facing each other fill the cell), `north`/`east`/`south`/`west` and `up` for blocks with `connects` (`{"group": "fence", "to": ["fence"]}`: connect to members of these groups and full solid blocks; `"solids": false` leaves the full blocks out, tripwire; without `to` a block connects to its own group, `"to": []` makes it a member only, the tripwire hook). Further flags: `support` (`below` or `attached`: breaks and drops without it; an attached block holds on a solid block whose side towards it is full, or on a block whose `axis` runs through that side, like a lantern on the end of a chain), `toggles` (using flips `open`), `stonecutter` (using opens the stonecutter's screen, decision E-785), `door` (two blocks tall), `climbable`, `light` (0–15), `container` (`{"slots": 27}`, a chest), `tags` (of the block's item) and `itemTexture` (a flat icon instead of the block model). Worlds store states by name (`qtcraft:oak_stairs[facing=east,half=bottom]`), so reordering values or adding properties keeps old worlds; dropped properties fall back to defaults with a warning.

Light and shapes (decision E-104): `lightOpacity` counts for states that are a full cube. A state of a light-dimming block (`lightOpacity` above 0) whose shape is not a full cube (stairs, bottom and top slabs, walls, carpets) lets light into its cell and only stops it at the sides its boxes cover completely: a bottom slab is lit from above and the sides but shades the cell below, a top slab keeps the sky out of its cell, a stair passes light through its open quarter. Blocks with `lightOpacity` 0 let light through whatever their shape. A value above 0 has no effect on a shape that never covers a whole side (crossed planes, torches, fences): give such blocks `lightOpacity` 0. The handbook shows the effective value: 0 for such shapes, "only at the sides its shape covers fully" for slabs and stairs.

Building parts (decision E-048) come from two kinds of files. A family in `parts/` describes one part for all materials of the kinds it lists; the block, item, recipe and names of every part are generated after all packs are loaded, so families and materials of different packs combine:

```json
{ "name": "pillar", "kinds": ["stone"], "suffix": "pillar", "hardness": 1.0, "fuel": 1.0,
  "block": { "shape": "pillar", "lightOpacity": 0 },
  "recipe": { "pattern": ["#", "#", "#"], "key": { "#": "@" }, "count": 3 },
  "translations": { "en": "%1 pillar", "de": "%1säule" } }
```

```json
{ "name": "ruby", "block": "ruby_block", "kind": "stone", "exclude": ["qtcraft:wall"] }
{ "name": "excluded", "excluded": true, "blocks": ["ruby_ore"] }
```

A family's `"stonecutter": {"count": 2, "kinds": ["stone"]}` lets the stonecutter cut the base block of every material of those kinds into `count` parts; a block a `stonecutting/` recipe cuts one to one into a material's base block is cut into that material's parts too (decision E-784). In a family's `recipe`, `"@slab"` (any `@<suffix>`) stands for the material's part of that suffix; a family naming other parts is only made for materials that have them. `"recipes"` adds up to four more shaped recipes, each with a plain `name` (the recipe is `<part>_<name>`) and optionally a `result` (`"@slab"`); the base family `vertical_slab` turns three slabs into three vertical slabs and one back into a slab (decision E-755). The part `<material namespace>:<material>_<suffix>` copies textures, tool, tool level, sound material, flammability and fuel (× `fuel`) and hardness (× `hardness`) from the base block and drops itself; `@` in the recipe stands for the base block; `%1` in a translation is the material's name (translation key `material.<namespace>.<name>`, override with `translation`). Base families: `stairs`, `slab`, `vertical_slab` (wood and stone), `wall` (stone), `fence`, `fence_gate`, `button`, `pressure_plate` (wood; the oak ones are defined explicitly). Entries of `exclude` are family names; a material can leave out families of other packs by their full name (`qtcraft:wall`). Base families also include `carpet` (kind `wool`). Base materials: `oak`, `birch`, `spruce` (planks), `cobblestone`, `stone` (no wall), `brick`, `sandstone`, `stone_bricks`, `polished_stone` (no wall), `smooth_sandstone`, `mud_bricks`, `mossy_stone_bricks`, `mossy_cobblestone`, `smooth_stone` and `cut_sandstone` (both only slabs), and the sixteen wool colours (`white_wool` … `pink_wool`, carpets only). Nothing is made for excluded materials: blocks listed by an exclusion entry (base list in `materials/excluded.json`: ores, sand, gravel, clay, dirt, grass, snow, ice, logs, leaves, saplings, cactus, glass, water, bedrock, crafting table, furnace, chest) and every block that is no plain building block (not an opaque solid full cube without states, a machine, crafting table or chest, unbreakable or glowing), the latter with a warning. A block defined explicitly under a part's name is never replaced, nor is a recipe a pack defines under that name. Recipes take named ingredients before tags, so a tag never uses up an item a named ingredient needs.

### Liquids, falling blocks, plants and creatures (stage 14)

Liquids flow when they have a `flow` object (decision E-054). They need the state `level` with the values `"0"` (source) up to the flow distance in order, and may have `falling` (`[false, true]`):

```json
{ "name": "molten_ruby", "liquid": true, "solid": false, "replaceable": true, "render": "cutout", "light": 10,
  "contactDamage": 1, "drops": [],
  "states": { "level": ["0", "1", "2", "3", "4"], "falling": [false, true] },
  "flow": { "distance": 4, "ticks": 15, "movement": 0.6, "bucket": "molten_ruby_bucket", "sound": "qtcraft:liquid.lava.pop",
            "reactions": [{ "with": "qtcraft:water", "source": "qtcraft:obsidian", "flowing": "ruby_sand" }] },
  "textures": { "all": "molten_ruby" } }
```

| Field | Meaning |
|-------|---------|
| `flow.distance` | 1–15 blocks a flow reaches sideways from a source (water 7, lava 3). |
| `flow.ticks` | 1–1200 server ticks (20 per second) between flow steps (water 5, lava 30). |
| `flow.dropSearch` | 0–8 blocks (default 4, lava 2) searched sideways for the nearest drop: a spreading liquid only runs towards the nearest drops it can still reach, like the vanilla game; 0 or no drop that near spreads it evenly. Server side only. |
| `flow.infinite` | Two sources next to each other over solid ground make a new source (water). |
| `flow.movement` | 0.05–2: factor on swimming speed inside the liquid (lava 0.45). |
| `flow.bucket` | Item an item with `scoops` (the empty bucket) becomes when it takes a source; without it the liquid cannot be taken. |
| `flow.bottle` | Item an item with `"bottles": true` (the glass bottle) becomes when used on the liquid; the liquid stays (water: water bottle). |
| `flow.reactions` | Touching the liquid `with`, a source of this liquid turns into `source`, a flowing part into `flowing` (lava next to water: obsidian or cobblestone). |
| `flow.sound` | Played now and then where the liquid spreads. |
| `contactDamage` (any block) | Damage per hit to players and creatures touching the block or standing on it (magma), every half second at most; items in it burn. |
| `slowsInside` (any block) | 0.01–1: factor on the movement of bodies inside a block that is neither solid nor liquid; falls through it stay slow and do no damage (cobweb 0.25). |
| `infested` (any block) | `{"block": <block>, "mob": <creature>}` (decision E-453, server side only): the block stands in for `block` (give it the same textures) and lets one `mob` out when it breaks with drops (not in creative mode, not by commands); usually with `"drops": []` and a low hardness (the base game's infested stone, cobblestone and stone bricks: 0.75, 1 and 0.75, no tool needed). A creature with `"hidesInBlocks": true` uses these blocks: when hurt, it wakes its kind in infested blocks up to 10 blocks sideways and 5 up or down (nearest layers first; after each block the waking stops with chance 1/2, as in the reference); when idle (no target, on the ground), it now and then (5 % per tick) turns a block next to it into the infested block whose `block` that is and is gone. With the game rule `mobGriefing` off, as in the reference, it does not hide, and waking turns each infested block back into its `block` instead of breaking it (no creature comes out). Ores take `"biomes": [...]` (decision E-453): a vein lies only where the column of its first block has one of them (infested stone: mountains only). |
| `surface` (any block) | `{"speed": …, "jump": …, "slipperiness": …}`: `speed` and `jump` (each 0.1–2) are factors on walking speed and jump strength of bodies standing on the block (mud 0.6 and 0.93). `slipperiness` (0.6–0.995, default 0.6) makes the block slippery, in the units of the original game (decision E-430): above 0.6 a body on it keeps `slipperiness` × 0.91 of its horizontal speed per tick instead of taking the speed it wants at once (walkers speed up and stop slowly, the top speed stays the same), dropped items keep `slipperiness` × 0.98, and minecarts off the rails keep `slipperiness` (on any ground: 0.6 stops them within a few ticks). Path searches of creatures avoid slippery floors where the way round is short, and creatures brake before the end of their path on them. Ice and packed ice 0.98, blue ice 0.989. Reaches the client (the prediction slides the same). |
| `hardens` (any block) | `{"with": <block>, "into": <block>}`: touching `with` (any state) on any side, or landing in it while falling, the block turns into `into` (concrete powder in water). |

Food with `emptiesTo` leaves that item in the hand when eaten (mushroom stew: the bowl). A bucket is an item with `"places": "<liquid>"` and `"emptiesTo": "qtcraft:bucket"`; using it pours a source and leaves the empty item in the hand. Burnt as fuel (`fuelSeconds`, the lava bucket) it leaves the empty item in the fuel slot, where it may stay or be taken out (nothing else can be put next to it); fuel with `emptiesTo` must have `"maxStack": 1`, otherwise the item is rejected. `"scoops": true` makes an item (the empty bucket) aim at liquids and take sources; `"bottles": true` (the glass bottle) aims at liquids too but fills from them (`flow.bottle`) and leaves the source. An item with both is rejected.

Blocks with `"falls": true` (solid blocks only) fall as entities while the cell below is air, liquid or replaceable, and become blocks again where they land, or drop as items when that cell is taken (a torch) or the block would end up inside a player or creature. Plants use `"support": "below"` (default for `cross`) with `"ground": [block names]` (instead of any full solid top face) and `"groundLiquid": "qtcraft:water"` (the liquid must touch the ground block from a side, unless the ground is the plant itself, as for sugar cane). World generation places single blocks with features of `"type": "plant"` (`"block"`, `"ground"`) and, with `"nearWater": true`, only on ground at sea level with water next to it (sugar cane uses a `column` feature with it); with `"onWater": true` only on the top water block of columns under the sea level, the `ground` naming the water (lily pads in swamps, decision E-774). A village style's `wetland` may add `floatingPlant` and `floatingPlantChance` (0–1) for a plant on the water of its pools.

Features of `"type": "pool"` sink a basin of a liquid (`"block"`, e.g. `qtcraft:lava`) into cave floors. They are not listed by biomes (a biome naming one gets a warning) but tried in every chunk: `attempts` (1–8) tries, each taken with `chance` (0–1), look for a cave floor in a random column at or below a random height between `minY` and `maxY`; the basin reaches up to `radius` (1–6) blocks from that column and `depth` (1–4) blocks down, narrowing with depth. Cells on the chunk's edge and every cell whose sides or bottom would not hold liquid (air, liquids, non-solid or replaceable blocks) are left out, and a pool not open to the cave above is not placed; cells under another liquid are left out too, and the rock hollowed over a pool keeps any block that holds back another liquid or carries a falling block, so generated pools never flow or meet other liquids. `"biomes"` limits a pool to some biomes. With `"surface": true` the pool is a lake on dry land (decision E-856, like the reference since 1.18): at most one per square of `region` (1–64, default 1) chunks; with `chance` per square, up to `attempts` chunks of the square are tried in turn, drawn so that `spacing` (0 to `region` − 1) chunks stay free towards the next square's, and the first that fits is taken. The basin is three to five overlapping ellipses inside the chunk, reaching up to `radius` (at most 5 used) blocks from its middle with the liquid up to `depth` deep; it fits where the middle column lies in one of the `biomes` and the basin and the ring around it are dry land (above the sea level, no coast, river or overhang) within 3 blocks of height. The liquid's top lies 1 or 2 blocks below the lowest ground there, the basin is dug out above it, and every side or bottom of the liquid that is air or soil (a biome's ground block other than stone) becomes `rim` (default the terrain's stone); the ring around the basin turns from soil to `rim`, and no plant grows within two blocks. No tree grows near a lake, and none lies in or near a village, a surface structure, a coastal tower or a mine shaft's entrance. The base game places `qtcraft:lava_pool` (y 12–44, above the lava lakes that fill the caves up to y 10; two attempts at 0.3, radius 3, depth 2) and the surface lake `qtcraft:lava_lake` (deserts, mountains, plains, taiga and forest steppe; squares of 6 × 6 chunks with `spacing` 3, eight sites tried, chance 1.0, radius 5, depth 3, rim stone: about one lake per 200 chunks); the example mod adds `rubies:molten_ruby_pool`. All mods together may define at most 64 pool attempts per chunk (a surface lake counts its attempts divided by the chunks of its square, rounded up).

Creatures may fly (`"flying": true`: no gravity, 1.2–3 m above the ground), glow (`"glow": 0–15`: drawn that bright, pulsing; it lights nothing around them), belong to the ambient category (`"spawn": {"ambient": true}`, own cap of 10 per player, gone at daybreak when they spawn at night), be limited per kind (`"spawn": {"maxCount": 8}`), spawn only in some biomes (`"spawn": {"biomes": ["qtcraft:swamp"]}`), only in a share of the chunks chosen by the world's seed (`"spawn": {"chunkChance": 0.1}`, like the base game's slime chunks) or only up to a height (`"spawn": {"maxY": 40}`), and spawn at further places and times through extra rules (`"spawn": {"also": [{"time": "night", "biomes": ["qtcraft:swamp"], "maxY": 70}]}`, up to 8, each with its own `time`, `blocks`, `weight`, `caves`, `maxLight`, `darkness`, `chunkChance`, `maxY`, `biomes`, `sky` and `water`) and be caught: `"catch": {"with": "qtcraft:glass_bottle", "item": "qtcraft:firefly_bottle"}` turns one held `with` item into `item` when the player uses it on the creature, with the sound `sound` (default `item.bottle.catch`). No creature spawns on a block with `contactDamage` or with its feet or head in a block with `slowsInside`, even if its spawn `blocks` lists that block, so mod blocks like magma or cobwebs keep spawns away by their fields.

**Monster spawning** (decision E-836, server side only): hostile creatures (`"hostile": true`, neither `aquatic` nor ambient) spawn as monsters by the rules of the original game. Every tick each living player tries two places in the 17 × 17 chunks around its chunk: a random column and one of its floors (the open surface, ground under trees and roofs, cave floors), at least 24 m from every player and at most 128 m from the nearest. A floor with more than 8 blocks above it counts as a cave floor, where a rule applies only with `"caves": true` (default `false`; the base monsters set it, the enderman does not), so a mod's monster without it keeps to the open surface, the ground under trees and roofs. All monsters together are capped at the server limit `monstersPer289Chunks` (70) for every 289 loaded chunks of those areas, and a monster appears only where a player whose area holds the chunk has fewer than 70 in its own area. A spawn rule of a hostile creature has two light fields with new defaults: `maxLight` (block light at the feet, now 0 for hostile creatures instead of 7) and `darkness` (default `true` for hostile creatures, `false` for the others): the sky light must not exceed a random draw of 0–31, and the larger of block light and the sky light less the sky's darkening (11 at night, 10 in a thunderstorm, 0 at noon) must not exceed a random threshold of 0–7. So monsters come wherever it is dark, also by day in caves and under roofs; `time` still applies on top (a mod's `"time": "night"` keeps a creature to the night), `"darkness": false` with `"maxLight": 15` turns the test off (the base slime's slime chunks). Every creature that walks, monster or not, spawns only on ground that carries it: a solid block drawn opaque with a full top face (no glass, leaves, ice, lower slab, path or farmland; an upper or double slab carries), with its feet and head in cells that are not solid, no liquid and no rail; a rule's `blocks` only narrows that down further (the base monsters name none). Creatures that are not kept vanish at once beyond 128 m from every player and, once no player came within 32 m for 30 s, with a chance of 1 in 800 per tick.

**Monster lists of the biomes** (decision E-838, server side only): as in the original game every biome has a list of monster kinds with weights, and each place a monster may appear at draws one kind of the whole list by weight and only then tests that kind's rules there; a kind whose rules do not allow the place wastes the try (nothing comes), so a kind keeps its share even where others cannot spawn. The weight of a monster kind in a biome is the highest `weight` among its spawn rules that allow the biome (no `biomes`, or the biome among them); a biome changes it with `"monsters": {"qtcraft:zombie": 20, "qtcraft:husk": 80}` (up to 64 entries, weights 0–100, 0 takes the kind out of the list; names without a namespace take the biome's). A biome's entry counts only for kinds that spawn there by their own rules, so a kind whose rules all have weight 0 never spawns by itself; entries naming no creature or one that is no monster are left out with a warning. Worlds without biomes (the test terrain, generators of their own) use the kinds' own weights. The base game uses the original's weights: zombies, skeletons, spiders, slimes and Kjuts 100 each, endermen 10, drowned 5 (100 in rivers, 1 in frozen rivers); the desert gives zombies 20 and husks 80, the tundra skeletons 20 and strays 80. Witches are in no list (`"spawn": {"weight": 0}`): they come only to their hut's guardian zone (decision E-623). Peaceful, ambient and water creatures keep their own choice among the kinds that may spawn at a place. Two further rule fields, also in `also`: `"sky": true` (the feet need the full sky light, 15: the open sky; the base game's husks and strays) and `"water": true` (only for creatures that walk, not flying, hovering or `aquatic` ones: the creature spawns with its feet in water above a solid floor and its head in water or air, never on dry land; the floor carries as for walkers; with `caves` also in deep water, which counts as a cave below more than 8 blocks; the base game's drowned: anywhere up to `"maxY": 56`, six blocks below the sea level, and at any depth in the river biomes). A creature with `"abilities": {"dives": true}` stays under water: it sinks and walks on the bottom and swims up only towards a player it chases who is above it, or at a wall (the drowned, together with `swims`); without it a walker in water keeps swimming up.

**AI and abilities** (decision E-423, server side only): `"ai"` chooses what decides what the creature does: `passive` (wanders, flees when hurt; the default), `hostile` (chases and strikes players; needs `"hostile": true`, the default for hostile creatures) or `villager` (lives by its villager settings; goes with `"villager"` and is its default). `"abilities"` says how it finds its way: `opensDoors` (opens closed wooden doors and gates on its path; only the villager AI does so far), `climbs` (`none`, `ladders`: holds on to ladders and goes up and down along them; `walls`: also holds on to every wall it touches, as on a ladder, in the physics within 0.25 m beside its box and up to a metre above its feet, and on paths in every cell beside a solid block or below one beside it, so it climbs up and down walls and, if small enough, round the face of an overhang; decision E-451), `swims` (moves through water as freely as on land; a walker uses water only without a dry way) and `divesIntoWater` (drops deeper than 3 blocks, down to 12, into water at least two blocks deep; default `true`). The villager AI starts from `{"opensDoors": true, "climbs": "ladders", "swims": false, "divesIntoWater": false}` (villagers keep to their boardwalks), the others from `{"opensDoors": false, "climbs": "none", "swims": false, "divesIntoWater": true}`; the fields given replace those values. The base game's `villager` names its abilities in its file.

**Milking, drinks, water creatures and fish buckets** (decisions E-500 to E-502): `"milk": {"with": "bucket", "item": "milk_bucket", "sound": "mob.cow.milk"}` on a creature turns one held `with` item into `item` when a player uses it on a grown one (the creature stays; `with` reaches the client). An item with `"drink": {"clearsEffects": true}` is drunk with the use button like food is eaten (it must be neither food, armour, placeable, throwable nor a launcher) and becomes its `emptiesTo`; `clearsEffects` ends all status effects of the player. `"aquatic"` makes a passive creature that is neither flying, ambient nor tameable a water creature (server side only): it swims only in water (never in lava or another liquid that sets things alight) at `swimSpeed` (0.1–10 m/s, default 1.5; hurt, it darts away at `chaseSpeed`) and never above the surface, schools with the creatures of its kind within `schoolRadius` (0–16 m, default 4) using the weights `cohesion` (0–4, default 1.5: towards their centre), `alignment` (0–4, default 0.8: along their heading) and `separation` (0–4, default 1.2: away from those closer than `separationDistance`, 0–4 m, default 0.8) with at most `neighbours` of them (0–32, default 8); on land it flops (`flopSpeed`, 0–10 m/s, default 4) and after `airSeconds` (0–600, default 15) takes `suffocationDamage` (0–100, default 1) every second. Water creatures spawn in water only (give their spawn rule `"blocks": ["water"]`), 1–3 blocks below the surface, within their own cap (server limit `waterCreaturesPerPlayer`, default 5); they never count as animals and despawn far from players unless released from a bucket. A bucketable creature has `"catch": {"with": "water_bucket", "item": "cod_bucket", "sound": "item.bucket.fill"}`, and its bucket item `"places": "water"`, `"emptiesTo": "bucket"` and `"releases": "cod"`: pouring it places the water and lets a creature of that kind out there, kept with the world like a bred animal and within the same limits (`breedingCrowd`, `bredPerKind`; without room the bucket stays full), also from a dispenser (`releases` needs `places`).

**Traits of stage 52.2** (decisions E-450 to E-453, server side only): `neutralByDay` (hostile creatures only: by day and above ground it leaves players alone until a player hurts it with a blow or a shot; then it hunts exactly that player for 30 s, by day and by night; damage without a player provokes nobody), `leapSpeed` (m/s, 0–20: leaps at a target 2–4 m away on its level, now and then), `immuneTo` and `blowEffects` (see status effects), `maxFallSpeed` (m/s, 0–60: falls no faster, as a flapping bird; at least one tick of gravity, 1.4 m/s), `hidesInBlocks` (silverfish, decision E-453: see the block field `infested`) and `lays` (decision E-452, above).

**Archers** (decision E-426, server side only): `"ai": "archer"` (needs `"hostile": true`) goes with an `"archer"` object, and that object only with it: `projectile` (the projectile kind it shoots, required; a name no pack has makes it a melee `hostile` creature with a warning), `drawSeconds` (0.1–10, default 1: how long it draws before a shot), `cooldownSeconds` (0–60, default 1: how long it waits after a shot before it draws again), `speed` (1–100 m/s, default 25; the arrow's damage grows with it: 2 per 20 m/s, rounded up, so 3 at 25 m/s), `spreadDegrees` (0–45, default 1.5: random deviation of each shot), `range` (2–64 m, default 15: it shoots at targets it sees up to this far, measured horizontally like `minDistance` and `keepDistance`), `minDistance` (default 5: it backs away from a closer target) and `keepDistance` (default 12: it walks towards a farther target, or one it does not see, and circles sideways in between); `minDistance` < `keepDistance` ≤ `range`. `choices` (at most 8, decision E-623): `[{"projectile", "unlessTargetHas"}]`, it shoots the first choice whose status effect its target lacks, else `projectile` (the witch: poison while the player is not poisoned, then harming); a choice with an unknown projectile or effect is left out with a warning. `"drinks": {"item", "heal", "seconds", "cooldownSeconds", "sound"}` (only with the archer AI, decision E-623): once its health lies `heal` (0.5–1000, default 4) or more below its most and `cooldownSeconds` (0–3600, default 3) passed since its last drink, it holds `item` (required; an unknown item switches drinking off with a warning) for `seconds` (0.05–30, default 1.6), neither drawing nor shooting, then heals by `heal` with `sound`. With `attackDamage` 0 it has no blows (no melee strike, no attack row in the handbook). It aims at the middle of the target with the lead of its movement and the drop and drag of the projectile, and strikes a target in melee (`attackDamage`, `attackRange`, `attackCooldown`). Its arrows cannot be picked up. While it draws, the client shows the creature with the `Drawing` flag (arms raised and drawn, like a player). `"heldItem": "<item>"` puts an item into the right hand of a creature with a skeleton model (the skeleton's bow); an item no pack has is not shown. `"burnsInDaylight": true` sets a creature alight in direct sunlight for 8 s, as fire does: by day, with full sky light at its head (no roof, leaves or other shade above), neither in water nor in the rain. Creatures wear no armour, so nothing else protects them. The showcase gives such creatures a pen with an opaque roof. Creature drops (`drops`) take `item`, `count` (1–64) and `chance` (0–1, default 1) per entry.

**Neutral creatures, gaze, teleporting and carried blocks** (decision E-460, server side only; the enderman): `"ai": "neutral"` wanders like `passive` until a player provokes it, then chases and strikes that player like `hostile` and stays angry for 20 s after it last saw them (a creature that should count against the hostile cap and not flee also sets `"hostile": true`; neutral ones strike only the player that provoked them, also in a crowd). A player provokes it by a blow or a shot (that player; damage without a player, such as lightning, fire or water, provokes nobody) or, with `"gaze"`, by looking at its head: `tolerance` (0.001–1, default 0.025: the player's look and the direction from their eyes to the middle of the head agree when look · direction > 1 − tolerance / distance, so the allowed angle narrows with the distance, about 4.5° at 8 m and 1.8° at 50 m), `range` (1–128 m, default 64) and `headShare` (0–1, default 0.9: where the head is, as a share of the height); walls and glass hide the head. `"teleport"` lets it jump to a random safe place (a full solid floor that is no liquid and does not hurt, room for its whole height, no liquid, fire or magma, only in loaded chunks: it never crosses into a chunk that is not loaded): `range` (2–64 m, default 32, horizontally and vertically; it then goes down to the first floor), `attempts` (1–64, default 16 random places per jump), `cooldownSeconds` (0–60, default 0.5), `dodgesProjectiles` (default true: projectiles do not hurt it, it teleports away and the projectile bounces off or breaks), `whenWet` (default true: it teleports out of water at once and away from rain), `towardsTargetChance` (0–1 per second, default 0.05: an angry one more than 12 m from its target jumps next to it) and `sound` (played where it leaves and where it arrives). `"waterDamage"` (0–100, default 0) hurts it that much every 0.5 s in water or rain, and it then never stands in water on its paths. `"carries"` lets it take single blocks and put them down elsewhere, only with the game rule `mobGriefing`: `blocks` (the block names, any of their states; **Golems** (decision E-471, server side only): `"ai": "golem"` (peaceful walkers only) goes with a `"golem"` object, and that object only with it: `knockbackResistance` (0–1, default 0: share of a blow's push it shrugs off), `lift` (0–4, default 1: its blows throw upwards this many times a usual blow's lift), `attackSound`, `repairItem` (used on a hurt golem, one of the held stack heals `repairHealth`, 0–1000, default 25, with `repairSound`; empty: not repaired) and `build` with `body` and `head` blocks (players build it from four `body` blocks standing upright in a T, along either horizontal axis, with air beside the head and the foot, by placing `head` on top; the blocks vanish and the golem never attacks players). **Guardians and crumbling** (decisions E-593, E-594, server side only): `"ai": "guardian"` (needs `"hostile": true`) keeps a creature to the zone it guards (a structure's `guardians` zone, see Structures): it chases only players it sees within its `sightRange` who are at most `"guardian": {"leash": 6}` blocks outside the zone, lets them go beyond, strolls inside the zone and walks back into it when it stands outside; summoned without a zone it is an ordinary hostile creature. `"crumbles": {"liquid": "water", "body": "sand", "head": "carved_sandstone", "sound": "..."}` (walkers only): where the body (grown by 0.05 sideways and below) reaches into a **source** block of `liquid`, the creature is removed without loot or experience and its build stands in its place, an iron golem's T in reverse: `body` at the feet, in the middle above them and on both sides of the middle across its facing, `head` on the middle, turned to its facing when the block has a `facing` state. A block goes only into an open cell (air, a replaceable block, flowing liquid, never a source); otherwise it drops as an item. An unknown liquid or block switches crumbling off with a warning. The base game's sand golem has both and spawns nowhere by itself (`"spawn": {"weight": 0}`).

**Families and hovering** (decision E-839, server side only except the thread): `"family": {"child": "kjut_child", "maxChildren": 4, "childrenPerHit": 1, "maxSplits": 8, "popDrops": [{"item": "gunpowder", "count": 1}], "popSound": "mob.kjut.pop", "orbitRadius": 1.1, "orbitSeconds": 4, "tetherTexture": "kjut_thread", "tetherRange": 12}` (creatures on land only) makes a creature a parent: every fresh hurt it survives that takes health (a snowball or an egg does not count, nor a stronger hit during its invulnerability) splits off `childrenPerHit` (1–16) creatures of kind `child` next to it, while fewer than `maxChildren` (1–16, default 4) of its children live and it has split fewer than `maxSplits` (0–256; 0 or missing: twice `maxChildren`) in its life (not saved). When the parent dies, every child of it pops in the next tick of the creatures, like the children of a QObject on `deleteLater`: it is gone with `popSound` and leaves `popDrops` instead of its own drops; there is no explosion and no block breaks. A child killed on its own leaves its own `drops`. A parent leaving without a death (despawned, removed, its chunk unloaded while not kept) takes its children quietly, without drops. A kept parent (placed by a structure, or kept by `/mob … noai on`) keeps its children too; when its chunk unloads they wait for it and are linked again when it loads (never more than `maxChildren`; extra ones go on alone); once the chunk it was last in is loaded without it (it died while they were unloaded), they go on as ordinary monsters. The child must be another creature on land without a family of its own (else the parent does not split, with a warning); give it `"spawn": {"weight": 0}`. Children count against the monster cap like other monsters. Children with a mind that chase nobody orbit their parent on a radius of their own (`orbitRadius` 0.3–8 m ± 30 %, one round in `orbitSeconds`, 0.5–60) around the middle of its body; this works best with hovering children. The client draws a glowing thread of `tetherTexture` (empty: none) from each creature of the child's kind to the nearest living parent of the kind within `tetherRange` (1–64 m); the client knows no family links, so a child keeps the parent it was tied to while that one stays in range, and changes to another one only when that is clearly nearer (under 60 % of the distance). `"hover": {"height": 0.6, "bob": 0.08, "bobSeconds": 2.5, "maxHeight": 3, "turnSpeed": 90}` lets a creature on land float instead of walking: without gravity, `height` (0–2 m) above the ground or a liquid below its middle, bobbing by `bob` (0–0.5 m) every `bobSeconds`, never more than `maxHeight` (up to 16 m) above the ground and lower under a low ceiling; it goes where its brain wants (paths as a walker), rises over a wall in its way and turns towards where it goes at `turnSpeed` degrees a second. Keep `height` + `bob` below 1 so its paths start in the cell above the ground. A hoverer stays out of the walkers' crowd (no throttling, no cramming), never swims and never takes fall damage; hoverers that chase someone push each other apart. A child split off pops up about 1 m before it floats back.

**Taming, pets, shy creatures and packs** (decision E-480, server side only; wolves, dogs, cats, ocelots): `"tameable"` lets players tame a creature of the passive or neutral AI that walks and is not hostile: `items` (the items that tame it, up to 64; each used on it is used up and tames it with `chance`, 0–1, default ⅓; empty for a kind that is only ever tame), `becomes` (a tameable creature it turns into when tamed, e.g. `"dog"` for the wolf; it keeps its share of health; a name that is no tameable creature is ignored with a warning), `healItems` and `healAmount` (0–1000, default 4: food that heals a tame one; anyone may feed it), `followDistance` (1–32 m, default 6), `stopDistance` (0.5–16, default 2) and `teleportDistance` (4–64, default 12; `stopDistance` < `followDistance` < `teleportDistance`), `defends` (default false: it attacks the creature that hurt its owner or that its owner struck in the last 5 s, for up to 20 s and 24 m; never a pet, its owner's or another player's, never a player; it keeps a target until its owner fights anew) and `collar` (`{"default": "red_dye", "dyes": {"red_dye": "#b02e26", …}}`, up to 32 dyes: its owner colours the collar with one of them; without `collar` there is none). A pet belongs to the identity of the player who tamed it, not to an entity id: the fingerprint of a player's proven identity, or `name:` and the lower-case name for the local player (decision E-252); it stays theirs while they are offline and waits standing (or sitting). A tamed one sits at first; its owner's use with an empty hand or any other item makes it sit or stand up. One that does not sit follows its owner beyond `followDistance` until `stopDistance` and teleports next to its owner beyond `teleportDistance` (a random cell within 3 cells, at most one up or down, where its body fits on a solid floor, only in loaded chunks; never while confined). Tame creatures are kept with the world. Players never hurt the pets of other players (blows and their arrows). `"shy": {"distance": 8, "calmItems": ["raw_cod"], "calmSpeed": 1.5}` makes a creature run from players closer than `distance` (1–32 m) unless they hold one of `calmItems` and move no faster than `calmSpeed` m/s (0–10). `"packRange"` (0–64 m, neutral AI only) angers every wild creature of the kind within the range at the player who struck one of them. `"frightens": true` (cats) scares away creatures with `"scaredOfCats": true` within 6 m (no creature of the base game is scared of cats yet). Model parts of box models take `"tint": "collar"` (drawn in the collar's colour; the texture should be light) and `"sitOffset": [x, y, z]` (within 1 m: where the box moves while the creature sits). A structure's `mobs` entry may tame its creature with `"owner"` (an owner key; the showcase uses the made-up `"showcase"`) and `"sitting"` (default true); this holds for structures of world setups (the showcase), while village pieces place their creatures wild, and an owner on a kind that is not tameable is ignored with a warning.

Further procedural texture patterns: `lava`, `flower`, `tall_grass`, `mushroom`, `sugar_cane`, `bottle` and `bucket` (contents in the secondary colour, transparent `#00000000` for empty), `lantern` (a lamp housing with a glowing window, for `uv: "box"`). Since the block and recipe expansion: `nugget`, `metal_block` (storage blocks), `bars`, `bookshelf`, `paper`, `book`, `bowl`, `stew` (a bowl with its contents in the secondary colour), `apple`, `leather`, `scrap`, `string`, `cobweb`, `dead_bush`, `fern`, `firefly_glass`, `barrel_side`, `barrel_top` and `stained_glass` (tinted glass that stays partly transparent). Since the ores and raw metal (decisions E-740, E-742): `raw_chunk` (a lumpy chunk of raw metal, an item icon), `raw_block` (rounded lumps with crevices in the secondary colour), `chain` (links from top to bottom through the middle four columns) and `chain_across` (the same from left to right through the middle four rows), for the two planes of the base shape `chain`. Since the backpack (decision E-832): `backpack_side` (a strap with a buckle in the secondary colour), `backpack_front` (a stitched flap with its buckle) and `backpack_top` (a carrying loop), leather with a darker stitched seam. Since the building variants (decision E-750): `mossy_bricks` (moss in the secondary colour), `cracked_bricks`, `chiseled_bricks`, `smooth_stone` (a smooth face in a thin frame) and `glazed_terracotta` (an ornament without symmetry in the secondary colour, so its turn shows). Ice has no frame and tiles without seams, so a frozen lake shows no grid: `ice` (a smooth face in the primary colour, whose alpha is kept – `#9ec4f290` stays translucent, an opaque colour gives blue ice – with soft diagonal streaks in the secondary colour) and `packed_ice` (opaque, with fine wandering cracks in the secondary colour); decision E-860. A block whose texture uses `ice` with a translucent colour needs `"render": "translucent"` (and `"opaque": false`), like `content/qtcraft/blocks/ice.json`; in the opaque layer the alpha is ignored. `slime` is a translucent fill in the primary colour inside a one-pixel rim in the secondary colour, both keeping their alpha (decision E-860); the base `slime_block` draws it on the shape `slime_block`, an outer cube with an inner core cube (3/16 to 13/16, texture slot `core`, darker and more opaque, `uv: "box"` so the core has its own rim), in the translucent layer with `lightOpacity` 0: a shape whose boxes cover every side keeps light out of its own cell when its `lightOpacity` is above 0, and the core would be drawn dark. Since the capes: `emblem`, pixel art from the data (decision E-241): `"bitmap"` holds up to 16 rows of up to 16 characters (top row first), `"palette"` maps single characters to `"#rrggbb"` (up to 16 colours); every other character and every pixel the bitmap leaves out shows finely woven cloth in the `primary` colour. `content/qtcraft/textures/cape_green_emblem.json` is an example. `icon` reads `bitmap` and `palette` the same way but leaves every other pixel transparent: item icons drawn from data (signs, compass and clock, decisions E-766, E-769).

Characters come from data as well: `models/*.json` defines skeletons (bones with a role, a pivot and boxes with slot names), `appearance/*.json` outfits (a texture and an optional tint per slot) and hair styles (extra boxes on the head). A creature can use `"skeleton": "qtcraft:humanoid", "outfit": "mymod:robe"` instead of `model` boxes and is then animated like players (walking, attacking, hit, death; `"armsForward": true` for zombie-like arms). New outfits and hair styles appear in the character screen of players who have the mod; `"playable": false` keeps a creature outfit out of that list, and the server refuses it for players. Tinted textures should be light (near white); the player's colour is multiplied in.

Capes are appearances of `"kind": "cape"` (decision E-240) and appear in the character screen's cape list. The cape hangs from the top of the torso's back and swings with the movement (lifted by walking and more by sprinting, upwards when falling, flat when sneaking, swaying when standing). `"shape"` sets `width` (0.05–1 m, default 0.6), `length` (0.05–1.6 m, default 0.95), `thickness` (default 0.04 m) and `offset` (gap to the back, 0–0.3 m, default 0.02). Layers: `outside` (required) textures the outer side below the emblem, `emblem` the upper square part of the outer side (as long as the cape is wide; the whole outer side uses `outside` without it), `inside` the side towards the back and `edge` the narrow sides; missing ones fall back to `outside` (emblem, inside) and `inside` (edge), tints work as for outfits. A skeleton creature can wear one with `"cape": "mymod:red_cape"`. Example:

```json
{
  "name": "red_cape",
  "kind": "cape",
  "shape": { "width": 0.6, "length": 1.1 },
  "layers": {
    "emblem": { "texture": "red_cape_emblem" },
    "outside": { "texture": "cloth", "tint": "shirt" },
    "inside": { "texture": "red_cape_inside" }
  }
}
```

### Signal Dust components (stage 29a)

A block joins circuits with a `signal` object (decision E-333). `type` picks a behaviour the server implements; the other fields tune it, so a mod adds its own sources (levers, buttons, plates, torches, repeaters), wires and consumers ("slots": lamps, openers, pistons) in data. A block without `type` can still set how pistons treat it (`movable`) and whether it carries power (`conducts`).

```json
{ "name": "ruby_lamp", "sound": "glass", "hardness": 0.5, "textures": { "all": "ruby_lamp" },
  "signal": { "type": "lamp", "active": false, "counterpart": "ruby_lamp_lit", "offDelayTicks": 4 } }
```

| Field | Meaning |
|-------|---------|
| `type` | `dust`, `lever`, `button`, `plate`, `torch`, `repeater`, `lamp`, `opener`, `piston`, `piston_head`; since stage 29.2 also `comparator`, `observer`, `hopper`, `dispenser` (below); since stage 32.2 `rail` (powered and activator rails, with the state `powered`; see the rails below); since package 62.1 `constant` (always on: gives `power` to dust and components on all six sides, but powers no block and passes no power through itself, like the block of Signal Dust; decision E-752); since package 62.2a `note` (plays a note when its power rises or a player uses it, using raises the note by a semitone; decision E-767) and `target` (a projectile hitting it sets its state `power` to 1–15 by how close to the middle of the face it hit, released after `stuckHitTicks` (arrows, default 20) or `hitTicks` (other projectiles, default 8); it gives that strength to dust and components like `constant`; decision E-768); since package 62.3 `hook` (a tripwire hook, states `attach` (north, east, south, west), `attached` and `powered`: powered like a button while something touches the tripwire of its line, strongly into the block it hangs on; `wireReach` cells of wire at most between two hooks, default 39), `tripwire` (states `attached`, `powered`, `disarmed`: powered while an entity stands in it, released `pulseTicks` after nothing does; torn while attached and not cut with shears it sets its hooks off once; decision E-782) and `viewers` (state `power` 0–15 = the players looking into the container, at most 15, to all sides and strongly into the block below: the trapped chest, decision E-783) |
| `instruments` | Note blocks: `{"default": "note.harp", "blocks": {"gold_block": "note.bell"}, "sounds": {"wood": "note.bass"}}` – the sound played for the block below, by its name, else by its sound material, else `default` (names without namespace get the pack's). The pitch goes from 0.5 (note 0) over 1 (note 12) to 2 (note 24) times the sound's own; the base game's `note.*` sounds are tuned to F#3, F#4 and so on, so note 12 is an F# |
| `power` | Strength a source emits, 1–15 (default 15) |
| `pulseTicks` | Buttons: ticks until they spring back (stone 20, oak 30) |
| `offDelayTicks` | Lamps: ticks until they go dark after losing power (default 4, 0 at once) |
| `detects` | Plates: `all` (any entity, default), `living` (players and creatures) or `carts` (minecarts only: a detector rail) |
| `wireReach` | Tripwire hooks: cells of tripwire at most between two hooks of a line (default 39, 1–64) |
| `reach` | Rail slots: how many rails of the same block along the line pass the power on (default 8, 0–64) |
| `sticky`, `pushLimit`, `head` | Pistons: pull back the block in front, blocks pushed at most (default 12), the block of the extended head |
| `quasiConnectivity` | Pistons, dispensers and droppers: also powered through the block above them, noticed only on a block update next to them (default `true`; the world's game rule `quasiConnectivity` can switch it off for all; the base game's decoupled variants set it `false`, decision E-870) |
| `active`, `counterpart` | Torches and lamps come as two blocks (light belongs to a block): `active` marks the lit one, `counterpart` names the other one with the same properties |
| `strongPowersAbove` | Torches: whether a lit torch strongly powers a conductor above it, which passes the power on to dust and components around it (default `true`; the Small Signal Torch `false`, decision E-745). A component directly above a torch is powered either way |
| `movable` | How pistons treat the block: `default` (unbreakable blocks stay, blocks that hang, wash away, flow or give way break, the rest moves), `push`, `immovable`, `breaks` |
| `conducts` | Whether a full solid opaque block passes power (default `true`; pistons and heads `false`) |

A piston's `head` must be a `piston_head` block with the piston's `facing` values and `sticky`; a torch's or lamp's `counterpart` must be the same kind with the opposite `active` and the same states. A block whose link is broken takes no part in circuits (a warning when the content loads). Internal variants like a lit lamp set the block field `"item": false`: they get no item of their own.

Each kind needs certain states, which the parser checks: dust `power` (`"0"`–`"15"`) and `north`, `east`, `south`, `west` (`none`, `side`, `up`); levers, buttons and plates `powered`; torches `attach`; repeaters `facing` (four sides), `delay` (`"1"`–`"4"`), `powered`, `locked`; note blocks `powered` and `note` (`"0"`–`"24"`); targets `power` (`"0"`–`"15"`); openers `open`; pistons `facing` (six sides, a `rotate` of the shape turns up and down too) and `extended`; heads `facing` and `sticky`. Chests, barrels and furnaces move with their contents; mods' storage blocks and machines do too.

### Signal machines and comparator readings (stage 29.2)

Four more `type`s (decisions E-342 to E-346): `comparator`, `observer`, `hopper`, `dispenser`. A mod's block of such a kind behaves like the base block of that kind; its states are checked like the others: comparators `facing` (four sides), `mode` (`compare`, `subtract`), `powered`, `power` (`"0"`–`"15"`); observers `facing` (six sides, the direction it watches) and `powered`; hoppers `facing` (`down` and four sides) and `enabled`, plus a `container`; dispensers `facing` (six sides) and `triggered`, plus a `container`, and `"uses": false` for a dropper (only throws). Dispensers take `quasiConnectivity` like pistons. A block's `container` may set `"columns"` (slots per row of its screen, 1–9, default 9) and `"portable": true` (a backpack, decision E-832: broken, it drops as one item that carries its contents, its item stacks to one and opens from the hand used in the air, and nothing with contents goes into it, by hand or hopper; at most 54 slots), and `"facing": "into"` makes a block face into the clicked block (down when placed on top).

```json
{ "name": "ruby_hopper", "shape": "qtcraft:signal_hopper", "facing": "into", "render": "cutout", "hardness": 3,
  "container": { "slots": 5, "columns": 5 },
  "states": { "facing": ["down", "north", "east", "south", "west"], "enabled": [true, false] },
  "textures": { "all": "ruby_block", "slots": { "inside": "ruby_block" } },
  "signal": { "type": "hopper", "comparator": "contents" } }
```

**What a comparator reads** is set per block with `signal.comparator`, also on blocks that are no component (then `signal` holds only this field):

| Value | Reading |
|-------|---------|
| `"contents"` | Fullness of the block's container or machine: 0 when empty, else ⌊1 + 14 · mean of count/maxStack over the slots⌋ (needs `container` or `machine`) |
| `{"property": "<name>"}` | The index of the value of that state property, scaled to 0–15 (the property needs at least two values; the base game uses it for crop stages) |

**What a dispenser does with an item** is set per item with `dispense`: `throw` (default; also seeds, carrots and potatoes — they are thrown and plant themselves on farmland, never planted by the dispenser, E-294, E-345), `place_liquid` (pours the liquid block of `places` and becomes `emptiesTo`; needs both, and only liquids are poured), `scoop` (needs `scoops`: takes a liquid source and becomes that liquid's bucket), `equip` (needs `armour`: puts it on a player or armour stand in front), `ignite` (needs `ignites`: lights fire in front and wears the item by one, decision E-393), `shoot` (needs `projectile`: flies straight out of the front as that projectile at 22 m/s without spread, can be picked up again; arrows and splash potions, decision E-621). A failed action throws the item out, also in front of a container (as in the reference); a failed `ignite` keeps the item in the dispenser. A dropper ignores `dispense`; facing a container, it puts the item into it.

Hoppers reach a mod's containers and machines like the base ones: machines take items from above into their input and from the sides and below into their fuel slot (fuel only) and give their output downwards. A hopper collects items lying on any block above it whose collision does not fill its cell; a mod's slab or path block keeps working as a hidden collector.

### Armour and armour stands (stage 23)

An item becomes armour with an `armour` object (decisions E-234, E-235): `slot` (`head`, `chest`, `legs`, `feet`), `points` (0–20; 4 % less damage per point, at most 20 count), `set` (name of the set it belongs to; the showcase puts every set on a stand and the handbook groups by it; its title is the translation `armour_set.<namespace>.<name>`; default: the item itself) and how it looks: `layers` (at most 8) – `covers` (slots of the boxes of the humanoid model, e.g. `["torso", "sleeve"]`), `texture`, optional `front` (the face looking forward, e.g. a helmet with a transparent opening), `inflate` (metres added on every side, 0–0.2, default 0.03), `fromY`/`toY` (cut, model metres) – and `parts` (at most 16 extra boxes): `bone` (`head`, `body`, `right_arm`, `left_arm`, `right_leg`, `left_leg`), `from`, `to` (model metres like the model's boxes), `texture`, optional `front`. `durability` counts hits. Armour never stacks. Layers and parts turn with the body parts in every animation. Recipes are ordinary crafting recipes. New texture patterns for icons and armour faces: `helmet`, `chestplate`, `leggings`, `boots`, `armour_plate`, `armour_leather`, `helmet_front`, `visor`, `armour_trim`, `armor_stand`.

`"placesStand": true` makes an item place an armour stand (E-238), which drops that item again; `"placesCart": true` makes it place a minecart on a rail (E-382). A block with `"rail": true` is a rail: it needs the states `facing` (`north`, `east`, `south`, `west`) and `shape` (`straight`, `ascending`, `curve`), cannot be solid, and takes its state from the rails around it; draw it with a shape turned by `facing` (the base shape `qtcraft:rail`). A rail without the `shape` value `curve` never bends (powered, detector and activator rails, E-384); `"railAction": "boost"` (powered rail: speeds carts up while its state `powered` is true, brakes them while it is false) or `"activate"` (activator rail: while powered the rider gets out and hopper carts stop pulling, unpowered they pull again) needs the state `powered`, cannot have the `shape` value `curve` and usually goes with `"signal": {"type": "rail", "reach": 8}`, a slot powered while it or a rail of the same block within `reach` along its line gets power. A detector rail is a plate that only carts press, `"signal": {"type": "plate", "detects": "carts", "comparator": "carts"}` (a comparator behind it reads the container cart on it, E-385). An item that places a cart can carry a block, `"cartBlock": "chest"` (a container cart with that block's slots) or a Signal Hopper (a hopper cart, E-386); `"supportsAbove": true` lets a block without a full top carry rails and other blocks that need support (the Signal Hopper). A cart reaching the end of a track stops before a block with a collision box level with the end (a buffer stop) and otherwise leaves the track with its speed and flies on, up off the top of a ramp (E-430); a cart that comes within 0.5 m of a rail gets on it with its speed along the track, in the air only from above or level with it. Structures may put minecarts on their rails: `"minecarts": [[x, y, z], {"at": [x, y, z], "item": "chest_minecart"}]` (the rail's cell); `contents` at the cell of a container cart fill the cart. Structures may bring stands: `"stands": [{"at": [x, y, z], "yaw": 180, "properties": ["equip qtcraft:iron", "pose right_arm -90 0 0", "name Knight", "showname true"]}]` (properties as for `/armorstand`, E-239; ones that do not apply are logged and skipped).

### Held items

How an item sits in the hand comes from content, never from code (decision E-831). Every item belongs to a **category**: `tool` (has a `tool` or is a fishing rod), `weapon` (attack damage above 1), `launcher` (a bow), `sprite` (any other item drawn as its icon: torches, flowers, doors, rails), `block` (a full cube) and `partialBlock` (a block drawn from its boxes: slabs, stairs, fences, walls, carpets). `held.json` at the pack root gives each category its defaults; an item or a block may carry a `hold` object that overrides single fields; the block's `hold` applies to the item that places it. The levels stack field by field: the item's `hold`, then its block's `hold`, then the category in `held.json` (the base game's plus every later pack's, in load order).

A `hold` object (and a category entry in `held.json`, which has no `category`):

- `category`: one of the names above, to be held like that kind (only in `hold`).
- `grip`: where a hand takes a sprite: `handle` (the lowest-left opaque texel of the icon and up to two texels along it, tools and weapons), `middle` (the centroid of its opaque texels, launchers) or `base` (the bottom middle). Blocks are always held by the middle of their boxes.
- `firstPerson` and `thirdPerson`: where it sits at rest around the grip in the first-person view and in the fist of a figure (players seen by others, the character preview, armour stands). Each has `translate` `[x, y, z]` (metres, each within ±2), `rotate` `[x, y, z]` (degrees, ±360) and `scale` (a number or `[x, y, z]`, 0.01–2: metres per unit, where a sprite is one unit across and a block one unit per block edge). A point of the item is scaled, then turned about y (positive turns its front, −z, towards +x), then about x (positive tips its top towards +z, negative tips it forward towards −z) and z (positive leans its top towards −x), then moved. The frame is the camera's for `firstPerson` (x right, y up, z backwards, the grip low right of the crosshair) and the arm's model space for `thirdPerson` (the arm hanging down, the figure facing −z, the grip in the fist).
- `swing`: where it sits in the first-person fist in the middle of a swing (mining or attacking), with `translate` and `rotate` like `firstPerson` (no `scale`; the size stays). Over a swing the hand turns the item from `firstPerson` to `swing` and back, each value blended on its own (as written, so −10 and 350 are not the same here), smoothly and fully turned halfway through the swing; the grip stays in the fist. Unset fields keep the `firstPerson` value, so an item without a `swing` keeps its placement. The base game's tools and weapons rest flat and diagonal (`rotate` `[0, -20, 62]`) and turn to `[0, -85, -15]` in the swing, so the point of a pick or the edge of a sword, not the flat side, comes down onto the block. Note that a `swing.rotate` of a lower level (the category) still applies to an item that changes only its `firstPerson.rotate`; set both.

Values out of range or of the wrong type refuse the definition; unknown keys are logged (`qtcraft.registry`) and ignored. Example, a smaller door and a wand held like a tool but upright:

```json
{"name": "oak_door", "hold": {"firstPerson": {"scale": 0.3}, "thirdPerson": {"scale": 0.4}}, ...}
{"name": "wand", "hold": {"category": "tool", "firstPerson": {"rotate": [0, -20, 10]}}}
```

Icons with a shape (every texel the game draws, alpha from 0.1) are drawn one texel thick in the hand, with sides in the colour of their edge texels; the sides follow a grid of at most 16 texels per edge, so a 32× pack keeps its full picture on the faces and gets sides in 2×2 steps. Generated building parts (slabs, stairs and the other parts of a material) take the `partialBlock` defaults.

### Sounds

Sounds are not audio files but synthesis parameters; the game renders them when a world starts (decision E-040). A sound has up to 8 layers; each is a tone, noise or crackle with an envelope and simple filters:

```json
{
    "name": "block.crystal.break",
    "volume": 0.8,
    "variants": 3,
    "pitchVariation": 0.1,
    "layers": [
        { "wave": "sine", "frequency": 3500, "endFrequency": 3200, "duration": 0.4, "attack": 0.001, "curve": 2.5, "gain": 0.5 },
        { "wave": "crackle", "density": 1500, "highpass": 2500, "duration": 0.3, "curve": 2, "gain": 0.6 }
    ]
}
```

| Field | Meaning |
|-------|---------|
| `bus` | `effects` (default), `ambient` or `music`: which volume slider applies. |
| `volume` | 0–1 (default 1). Every sound is normalised to the same peak; `volume` sets its loudness, layer `gain`s (0–1) only weigh layers against each other. |
| `variants` | 1–8 differently seeded renderings, one picked per play; `pitchVariation` (0–0.5) changes the pitch randomly by up to that share. |
| `loop` | Rendered seamless and played until stopped (the ambience loops `qtcraft:ambient.wind`, `.cave`, `.water`). |
| `range` | 1–128 m (default 16): beyond it a positioned sound of volume 1 is not heard. |
| layer `wave` | `sine`, `square`, `triangle`, `saw`, `noise` (default) or `crackle` (sparse clicks, `density` 1–5000 per second). |
| layer `frequency`, `endFrequency` | 20–20000 Hz (default 440); `endFrequency` sweeps exponentially to that value (0: none). |
| layer `start`, `duration` | Seconds (0–10, 0.001–10, default 0 and 0.2). |
| layer `attack`, `curve` | Linear rise in seconds (at most `duration`), then decay `(1 - t)^curve` (0–8, default 2; 0 holds the level). |
| layer `lowpass`, `highpass` | Filter frequencies in Hz (20–20000; 0 or missing: off). |
| layer `tremoloRate`, `tremoloDepth` | Volume wobble: 0–50 Hz and 0–1. |

Blocks name a sound **material**: `"sound": "stone"` makes the block use `<namespace>:block.<material>.<action>` for the actions `break`, `place`, `step` (walking, jumping, landing) and `hit` (mining strikes). Base materials are `qtcraft:stone`, `wood`, `dirt`, `gravel`, `sand`, `grass`, `snow` and `glass`; a mod block writes `"sound": "qtcraft:wood"`, a mod's own material `"sound": "crystal"` needs the four sounds `block.crystal.break` etc. in the mod. Without `sound` a block gets wood (tool `axe`), dirt (`shovel`), grass (cross shape or `cutout`), glass (`translucent`) or stone; liquids and invisible blocks are silent. `"sounds": {"hit": "chime"}` replaces single actions. Creatures have `"sounds": {"ambient": …, "hurt": …, "death": …}` (default: no ambient sound, `qtcraft:mob.generic.hurt` and `.death`), machines `"machine": {"sound": …}` (default `qtcraft:machine.furnace`, heard while fuel burns). A definition with the name of a base sound replaces it, e.g. `"name": "qtcraft:block.stone.break"`. Names that no pack defines are reported as warnings and stay silent. `qtcraft-headless --export-sounds <dir> --mods-dir <mods>` writes all sounds as WAV files to listen to them.

The fields of every definition type are listed in `docs/Architektur.md` (sections Content, Interaction, Crafting, Creatures). Display names are never stored in definitions: blocks, items and mobs use translation keys (`block.<namespace>.<name>`, `item.…`, `mob.…`, `biome.…` by default) that the `lang/` files fill. English (`en`) is the fallback.

### Handbook (stage 15)

The handbook (F1 in the game, `qtcraft-headless --export-handbook <dir>` as Markdown) is built from the loaded content, so every block, item, recipe, smelting recipe, creature, biome, liquid, ore, feature and item tag of a mod appears automatically, in its own section after the base game (grouped by the namespace of its names). What a mod can add:

- **Texts:** blocks, items, mobs and biomes take an optional `"description"` (a translation key; default `<translation>.description`, e.g. `block.mymod.gem_ore.description`). Fill it in the `lang/` files; without it the page shows only the facts. Generated building parts share `part.<namespace>.<family>.description` of their family. Titles of features come from `feature.<namespace>.<name>` (else the file name), of item tags from `tag.<namespace>.<tag>`, of part families from `handbook.family.<family>`. Texts may use a small Markdown subset: paragraphs, `- ` lists, `**bold**`, `` `code` ``. Descriptions and chapters may quote values as `{name}` instead of writing numbers: rule values of the game (below) and content values `<block>.toolLevel`, `.slots`, `.flowDistance`, `.light`, `.hardness`, `.biteFood` (cake), `.cookSeconds` (campfires), `<item>.toolLevel`, `.food`, `.fuelSeconds`, `.durability`, `<mob>.health` (e.g. `{mymod:gem_ore.toolLevel}`).
- **Chapters:** `handbook/<name>.json` with `name`, `order` (sort number, base chapters use 10–120), `icon` (an item), `sections` (1–32 lower-case words) and `related` (content names linked at the end). The title is the translation of `chapter.<namespace>.<name>`, each section `chapter.<namespace>.<name>.<section>.title` and `.text`. A text may quote rule values of the game as `{name}` (e.g. `{hunger.maxFood}`, `{day.length}`; the list is `QcHandbookRules::values()`); an unknown name is reported as a handbook problem.

```json
{ "name": "gems", "order": 200, "icon": "gem", "sections": ["finding"], "related": ["gem_ore"] }
```

`qtcraft-headless --mods-dir <mods> --export-handbook <dir>` (without `--mods-dir` the export covers only the base game) prints every problem (links to unknown content, unknown rule values) and writes the pages to check a mod.

### Structures and the showcase world

A structure (`structures/<name>.json`, decision E-219) is a building made of block layers. `palette` maps single characters to block states (`"T": "torch[attach=north]"`, at most 64; a space in a layer keeps whatever is there, so map air explicitly to clear cells). `layers` go from the bottom up; each layer is a list of rows from north to south, each row a string from west to east (at most 64 × 64 × 64). Optional: `mobs` (`{"mob", "at": [x, y, z]}`, with `"confined": true` a creature that never teleports or changes blocks, decisions E-460 and E-510; with `"noAi": true` a creature without a mind like the reference's NoAI, decision E-510: it neither thinks, walks, jumps, swims, attacks nor teleports and changes no block, but it still falls, is pushed and takes damage, and is saved with the mark (`/summon <creature> [count] noai` and `/mob <nearest|looking|id> noai <on|off>` set it in game); with `"owner"` and `"sitting"` a tame one in world setups, not in villages, decision E-480; with `"children": 3` a parent of a family with that many children split off at once, in world setups, decision E-839; the children keep a mind even when the parent has `"noAi"`, so they orbit it), `stands` (armour stands, see above), `contents` (`{"at": [x, y, z], "items": [{"item", "count"}]}`, fills the chest, machine or campfire in that cell; machines take input, fuel, output, a campfire one item per place), `labels` (`{"at", "text" (a translation key), "detail", "heading"}`), `updates` (cells whose block update runs after placing: a liquid source starts to flow, sand falls) and `growing` (saplings that grow). Positions are local; points may lie up to 4 blocks outside the structure (labels above a roof). The translation key of its title is `structure.<namespace>.<name>`.

`"showcase": {"order": 100}` puts the structure into the showcase world as a demo (ordered by `order`, the base game uses 10–70); `"front": true` makes its tour stop look from in front of its south side at eye height (a room behind glass) instead of from the lookout. There, layer 0 is the ground layer (replace it for pools and floors). The showcase also picks up everything else of a mod by itself: every state of every block on a podium (sorted by the categories of `worldgen/showcase.json`), every creature in an enclosure, every item in a chest and every tree feature with its saplings. The example mod adds `ruby_shrine`:

```json
{
    "name": "ruby_shrine",
    "showcase": { "order": 100 },
    "palette": { "B": "ruby_block", "S": "qtcraft:stone_bricks", "L": "ruby_lantern", "R": "ruby_rose", "G": "qtcraft:grass_block" },
    "layers": [
        ["SSSSS", "SGGGS", "SGSGS", "SGGGS", "SSSSS"],
        ["L   L", " R R ", "  B  ", " R R ", "L   L"],
        ["     ", "     ", "  B  ", "     ", "     "]
    ],
    "labels": [{ "at": [2.5, 4.0, 2.5], "text": "block.rubies.ruby_block" }]
}
```

**Adventure allow-lists** (decision E-735): `"adventure": {"canBreak": {"stone_pickaxe": ["mossy_cobblestone"]}, "canPlaceOn": {"lime_wool": ["lime_concrete"]}}` adds entries to the allow-lists of adventure mode when the showcase places the structure (names without a namespace get the pack's, `*` stands for every item and the empty hand; at most 256 items with 256 blocks each). Like the lists set with `/adventure`, they hold in the whole world. Example: the base game's `adventure_station`.

`worldgen/showcase.json`: `timeOfDay` (seconds after sunrise, 150 = noon), `layers` (`{"block", "depth"}` from the bottom up), `podium`, `enclosure`, `container` (blocks), `lookout` (a structure placed in front of every area), `rowWidth` (metres) and `categories` (`{"name", "translation", "match"}`; `match` may hold `liquid`, `part`, `light`, `plant`, `functional`, `falls` (true/false) and the lists `render`, `tool`, `nameContains`; a block goes to the first category whose conditions all hold, else to the last one).

**Surface structures and guardian zones** (decisions E-590, E-591, server side only): `groundLayer` (default 0) is the layer that lies at the ground's top block wherever the world generator places the structure by itself or in a village; the layers below are buried (a cellar) and must name every cell. `"surface": {...}` lets the terrain generator place the structure by itself: at most one copy per square region of `spacing` blocks (320, whole chunks, at least twice the structure's width) with `chance` (0.5), at the first of `attempts` (4) places, each with its own centre and quarter turn drawn from the seed and the structure's name, whose footprint lies wholly inside the region, on land above the sea in one of `biomes` (required) at its four corners and its middle (with `waterDepth` 0–16, default 0, also ground under at most that much water; then nothing at or below the water's surface is cleared, and `preferWater` takes the first place whose middle lies under water over the first that fits; decision E-622), with the ground varying by at most `maxSlope` (3) there and no village (and no surface structure whose name sorts before it) within `villageMargin` (16) blocks. The terrain above the footprint is cleared from its layer `clearFrom` (default 1) up to 4 blocks over the top (a hut on stilts clears from its platform and keeps the ground and water between the stilts, whose cells are spaces; with `"clearTerrain": false`, decision E-630, nothing is cleared and the structure's keep cells keep the terrain, also in its buried layers, so a ruin lies half in the ground where the ground rises; name air cells where the structure needs open space), `foundation` (a block, default none) fills the ground below it down to solid ground (at most 16 blocks), then its cells are written; its `loot` chests are filled when their chunk first arrives. Its `choices` and `parts` vary every copy like a village building's (drawn from the region, so fixed for a given seed and name and different under another seed); keep loot chests out of parts. No trees, plants or surface pools grow within 3 blocks of a surface structure. Water in a structure needs written, non-falling cells below and beside it (sandstone rather than sand), or it may drain into a cave under the keep cells. The base game has `desert_temple`, `jungle_temple` (jungle), `witch_hut` (swamp, over water, a witch's zone), `ruined_portal`, `ruined_portal_sunken`, `ruined_portal_large`, `well`, `desert_well` and `oasis` (decisions E-621, E-622, E-631..E-633). `"guardians": [{"mob", "from", "to", "max", "cooldownSeconds", "minPlayerDistance", "maxPlayerDistance", "maxLight"}]` (at most 8) are zones whose creatures come back by themselves, in placed copies everywhere (surface, villages, the showcase): every second the server gives a zone one creature of `mob` (spawner rules: no villagers or water creatures) when fewer than `max` (1) creatures guard it, `cooldownSeconds` (120) passed since the zone was last full or last got one (a zone first seen in a session is ready), no living player is within `minPlayerDistance` (12) of the box `from`..`to` (local cells, the creature's feet) and one is within `maxPlayerDistance` (48, at most 128), every chunk of the zone is loaded and the world holds fewer than the server limit `guardians` (64) guardians. It comes into the first of 8 random cells of the zone with room for its body, solid ground below and block light at most `maxLight` (7; sky light does not count). Guardians are not saved; the zones come from the generator's plans, their cooldowns are kept while the server runs. The base game's `desert_temple` uses all three.

### Spawners, loot tables and dungeons (stage 38.1)

**Spawner blocks** (decision E-520, server side only): a block with `"spawner": {...}` is a monster spawner. Each placed spawner keeps its creature kind, the ticks to its next cycle and whether its creatures are confined as a block entity (table 10 of the chunk's block entities, entries framed and versioned per E-440; a later version or a mod may append fields, they are kept). Fields, all optional: `mob` (the kind a new spawner of this block starts with; without it an empty cage that waits for `/setblock <x> <y> <z> spawner <creature>` or the world generator), `range` (16: a player within this many blocks of the block's centre makes it work; otherwise its delay stands still), `areaX`/`areaY`/`areaZ` (9/3/9, odd: the spawn area centred on the block), `count` (4: random cells of the area tried per cycle), `maxNearby` (6: creatures of its kind within `nearbyRange`, 4, blocks of the spawner on every axis, a cube of 9 × 9 × 9 apart from the spawn area like the reference; with as many it waits a delay), `minDelay`/`maxDelay` (10/40 seconds between cycles that spawned; a cycle that found no fitting cell tries again the next tick), `maxLight` (11: highest block light at a spawn cell, for every kind, also passive ones; sky light does not count, like natural spawning, so a spawner works in daylight). A cell fits when the body has room (no solid, liquid, hurting or slowing block in its height and, for a body wider than a block like the spider's, in the cells around it) and, unless the kind flies, solid ground is below. Villagers and water creatures (`aquatic`, fish) never come from a spawner (villagers belong to a village and are kept with the world, fish need water and a spawn cell holds no liquid; `/setblock` refuses them, a spawner block, structure or dungeon naming one gets a warning at load and spawns nothing; dungeons leave the kind out). Spawners work only while a player is in the world. Spawned creatures are ordinary and not persistent; they count against their spawner and the server limit `spawnerCreatures` (256 awake), not against the natural caps per player. Spawners are not affected by the game rule `mobSpawning`. The base game's `spawner` has no item recipe and drops nothing (`"drops": []`) but `"experience": [15, 43]` with a pickaxe.

**Loot tables** (`loot/<name>.json`, decision E-521, server side only, replaced by name): `{"name": ..., "pools": [{"rolls": n | [min, max], "entries": [{"item": <item>, "weight": w, "count": n | [min, max]}, ...]}]}`. Each pool draws its rolls, each roll one entry by weight (default 1); an entry without `item` gives nothing; an unknown item gives nothing. The stacks (split at the item's stack size) go to random free slots of the chest; the same seed gives the same loot. Used by dungeon chests, the chest minecarts of mine shafts and the top rooms of coastal towers. Structures name loot chests with `"loot": [{"at": [x, y, z], "table": "dungeon_chest"}]` and spawners with `"spawners": [{"at": [x, y, z], "mob": "zombie", "confined": true}]` (`confined`: the spawner's creatures are confined like `mobs` with `confined`: they walk, but never teleport, carry blocks or change the world); the server puts both in when the chunk first arrives and marks the chunk (table 11), so an emptied chest stays empty; `/regenerate` puts them in again. Unknown loot tables (the chest stays empty), unknown items of a table (they give nothing) and unknown creatures of spawners and dungeons are reported when the content loads. Showcase structures write text on their signs with `"signs": [{"at": [x, y, z], "lines": ["...", ...], "color": "blue"}]` (at most 4 lines of 32 characters, cleaned and cut to the sign's own limits when the world is made; decision E-766; the optional `color` is one of the 16 dye colours, black by default, decision E-830); a turned placement turns a sign's `rotation` with it.

**Dungeons** (`"dungeons"` in `worldgen/terrain.json`, decision E-522; without the object, or with `"enabled": false`, there are none): one dungeon at most per square region of `regionSize` blocks (48) with `chance` (0.6); `attempts` (6) places with the floor between `minY` and `maxY` (14–48), at least 6 blocks of ground above the room, where caves take at most `maxCaveShare` (0.25) of the room. The room has odd outer sizes between `minSize` and `maxSize` (7–9) and is 5 high: a shell of `wall` with `moss` at `mossChance` (0.3, twice on the floor), the `spawner` in the middle with one of `mobs` (`[{"mob": ..., "weight": ...}]`), `minChests`–`maxChests` `chest`s against the walls filled from `lootTable`. From the middle of each wall the generator looks for a cave within `reach` (24) cells, straight on or with one bend, and carves at most `corridors` (3) of these, the shortest first, each at most `maxLength` (28) cells, one wide and two high. Corridor cells that border no rock (cave air, liquids, earth) get wall or moss blocks; a `light` (torch, attached to a wall) every `lightSpacing` (8) cells from the cave end inwards, only where it is at least `lightDistance` (8) cells (taxicab) from the spawner's spawn area: block light falls by one per cell, so a torch (14) leaves at most 6 there and the spawner's light condition (11) holds. Everything is planned from the seed and the terrain noise alone and built chunk by chunk, so dungeons across chunk borders are the same in any generation order; corridors are carved only when the world is generated.

### Mine shafts (stage 38.2)

**Mine shafts** (`"mineshafts"` in `worldgen/terrain.json`, decision E-570; without the object, or with `"enabled": false`, there are none): one mine shaft at most per square region of `regionSize` blocks (128) with `chance` (0.3); the whole network stays inside its region (`regionSize` ≥ twice its reach, `radius` × (`levelSpacing` + 3) + 5, plus 2). up to `minLevels`–`maxLevels` (2–3) levels (fewer where the ground allows no staircase down), `levelSpacing` (6) blocks apart, the top one with its feet between `minY` + the levels below and `maxY`, the lowest at `minY` (14) or above. `attempts` (6) places for the central room (inner width 2 × `roomHalf` + 1, `roomHalf` 4, `roomHeight` 4 high) with a solid floor and `groundCover` (4) blocks of ground above. Each level is a network on a square lattice (`levelSpacing` + 3 blocks between crossings, up to `radius`, 4, lattice steps from the centre) grown to `minNodes`–`maxNodes` (7–13) crossings, corners and dead ends; a corridor between two crossings already joined another way with `loopChance` (0.25). A staircase (`levelSpacing` steps of one block, four cells high, so one jumps up each step) leads from a crossing of a level to a new crossing of the next one, from which that level grows; a second staircase with `extraStairChance` (0.5). Corridors are three cells wide and three high, with a support every `supportSpacing` (3) cells: two `post`s and a `planks` beam. Where the terrain noise says a floor crosses a cave, the open floor cells become `planks` (a bridge) and pillars of `post`s go down from the supports (and from the middle of a crossing) to the ground; a corridor whose pillars would need more than `maxPillar` (20) blocks is not made, and staircases and the central room need a solid floor. Liquid beside an opened cell, and sand or gravel right above it, becomes `seal` (cobblestone), so generated liquids stay still and nothing falls in. Details: `minSpawners`–`maxSpawners` (1–2) `spawner`s of `mob` (cave spider) in the middle of corridors without rails, against a wall and off the supports, thick with `cobweb`s around; `rail`s along a corridor with `railChance` (0.6), on which a `cart` (a container minecart item, `chest_minecart`) stands with `cartChance` (0.2), filled from `lootTable` (`mineshaft_cart`) when its chunk first arrives; a `light` on a beam with `lightChance` (0.3), only `lightDistance` (8) cells (taxicab) from every spawn area; `cobweb`s in the upper corners with `cobwebChance` (0.08, a quarter of that lower down). **Surface entrance:** with `entranceChance` (0.3), or the chance of the biome at the shaft in `entranceBiomes` (`{"mountains": 0.8, ...}`), a ladder (`ladder`) shaft goes from a corner of the central room up to two cells above the ground's top, lined with `planks` where it passes something open, under a headframe (a plank ring, four `post`s and a plank roof); not where the ground's top lies at or below the sea, the ground under the headframe lies more than one block above or below it or the ground around it more than one block above, a cave opens at the top or a village is within 8 blocks. It is built after trees, cacti and surface pools: its headframe stands in the clear, leaves and cacti right around it are removed. Names in `entranceBiomes` that are not biomes are reported when the world starts. **Rooms:** a structure with `"mineshaft": {"weight": 2}` (odd sides of at most 7, lower than `levelSpacing`) is a room of the mine shafts: at dead ends with `roomChance` (0.3), at most `maxRooms` (2) per mine shaft, centred on the dead end's crossing with its bottom layer as the floor, turned so that its door (the middle of its north side, one above the bottom layer; keep it open) faces the corridor; its `loot` and `spawners` are furnished like the corridors', its `minecarts` stand there empty. The base game has `mineshaft_storeroom`. Mine shafts are planned from the seed and the terrain noise alone and keep clear of dungeons, and built chunk by chunk, the same in any generation order. A chunk that arrives with a rail, a spawner or a block with storage asks the generator for its carts, spawners and loot once.

### Coastal towers (stage 51.2)

**Coastal towers** (`"coastalTowers"` in `worldgen/terrain.json`, decision E-605; without the object, or with `"enabled": false`, there are none): one tower at most per square region of `regionSize` blocks (384) with `chance` (0.4), and towers of neighbouring regions at least `minDistance` (300, at most `regionSize`; 0 for no limit) blocks apart from centre to centre: of two that would stand closer, the one of the region with the lower random priority is left out (decision E-857), built from a structure of `structures` (`[{"structure": "coastal_tower", "weight": 1}]`, by weight; mods add their own towers here) and standing wholly inside its region. Sites are the columns of a grid `gridStep` (6) blocks apart whose ground lies at a tower's height, tried in a random order, at most `attempts` (16): every column under the footprint has its ground's top from sea level up to `maxRise` (5) blocks above it, no overhang and no cave in its top three blocks, and the highest and lowest columns differ by at most `maxSlope` (3); the structure is turned so that its door (the middle of its **south** side, one above the bottom layer; keep it open) opens onto ground at most one block below or above the floor; the open sea (a column with land factor below one half whose ground lies at least `oceanDepth`, 3, blocks below the water's surface; lakes and rivers do not count) lies within `coastDistance` (12) blocks of the footprint; and no village, no mine shaft entrance and no surface structure (a structure with a `surface` rule) lies within `clearance` (8) blocks; no trees, plants or surface pools grow near a tower. The bottom layer replaces the ground's top block of the highest column; below it `foundation` (cobblestone) fills everything that is not ground (solid, opaque, no liquid) down to the ground, at most `maxFoundation` (12) blocks; above it the footprint is cleared of trees and plants. The structure's `loot` and `spawners` are furnished when the chunk first arrives. Towers are built after trees, cacti, surface pools and mine shaft entrances, before villages, chunk by chunk, the same in any generation order. The base game's `coastal_tower` has four floors joined by a ladder and a top room whose chest (`loot/coastal_tower.json`: gunpowder, explosives, iron, gold, emeralds, food) stands behind a stone pressure plate on an explosive in the floor, with three more explosives beside and behind it.

### Villages (stage 37.2)

Villages (decision E-403) are built from structures and two kinds of data files. A **style** (`villages/<name>.json`) says how a village of some biomes looks:

```json
{
    "formatVersion": 1,
    "name": "desert",
    "biomes": ["desert"],
    "centre": "village_desert_well",
    "lamp": "village_desert_lamp",
    "path": [
        { "block": "terracotta", "step": "sandstone_slab" },
        { "block": "packed_mud", "step": "mud_bricks_slab" }
    ],
    "branchPath": { "block": "cut_sandstone", "step": "sandstone_slab" },
    "crops": [
        { "block": "wheat_crop", "weight": 2 },
        { "block": "potato_crop", "weight": 2 },
        "carrot_crop"
    ],
    "foundation": "sandstone",
    "pieces": [
        {
            "structures": [
                { "structure": "village_desert_house_small", "weight": 2 },
                { "structure": "village_desert_house_small_b" }
            ],
            "weight": 5
        },
        { "structure": "village_desert_temple", "weight": 2, "max": 1 },
        { "structure": "village_desert_pen", "max": 1, "chance": 0.4 },
        {
            "structure": "village_desert_fisher_hut", "max": 1, "water": 12,
            "jetty": { "deck": "birch_planks", "post": "birch_log", "width": 3, "over": 5 }
        },
        { "structure": "village_desert_tower", "max": 1, "minRoadLength": 200 }
    ],
    "layouts": [
        { "kind": "plaza", "weight": 3, "exits": [2, 3] },
        { "kind": "street", "weight": 2, "winding": 0.15 },
        { "kind": "tree", "arms": [2, 4], "bends": [1, 2] }
    ],
    "palette": { "oak_door": "spruce_door" }
}
```

`biomes`: the biomes built in this style; `fallback: true` makes it the style of every biome with villages that no style names (the base game's `plains`). `centre` (required): the meeting point in the middle, its centre on the village centre; the bell inside it is the meeting point. `lamp`: a lamp post set along the roads (optional). `path`: the surface of the roads from the centre (default gravel), `branchPath` of the roads branching off them (default `path`); each is one surface or a list of up to 8 (decision E-406), and a village takes one per rank, by `weight` (1–1000, default 1), so two villages of a style may have different roads. A surface is a block name or an object with `block` and optionally `weight` and `step` (a slab): the step is laid on a road cell next to a road cell one block higher, so a road over a terrace step reads as a stair (steps of two blocks stay as they are; a road ends at higher ones). Where a branch meets its road, the road keeps its surface. `crops` (up to 16, decision E-406): the crops of the fields, each a block name or `{ "block", "weight" }`; every crop cell of every piece of the style (a block with `crop`) is planted with one of them, one crop per row (a run of crop cells along x in one layer of the structure), each plant ripe with a chance of one half and else at an earlier stage. Without `crops` the pieces keep the crops they are written with. A mod adds a seed to the villages of a base style by extending the style (see "Extending a style" below), or adds a style of its own. A crop that is no block with `crop` is left out with a warning. `foundation`: fills the ground under a piece where it lies lower than the floor (default cobblestone). `pieces` (1–32): the kinds of buildings, each with a relative `weight` (1–1000) and an optional `max` per village (0–64, 0 = no limit), and either one `structure` or up to 16 blueprints in `structures` (`structure` with its own `weight` among the blueprints, default 1); every building of the kind is one of its blueprints, chosen by weight (decision E-404), so a mod adds a house variant by adding a blueprint. **Rules** make a kind conditional (E-404): `chance` (0–1, default 1: drawn once per village), `minRoadLength` (0–4096: only in villages whose roads are at least this many blocks long together, measured along their middle lines: the village's size, decision E-408; the base game's watchtower needs 200, about one village in ten) and `water` (1–32: only beside the end of a road with water at most this many blocks straight on, with a `jetty` from the road end over the ground to the water and `over` (1–16, default 4) blocks out over it, just above the water, `width` 1–5 (odd, default 1), `deck` and `post` blocks (default oak planks and log; posts under the edges reach down to the ground, and the style's palette applies)). Kinds with rules are placed first, each up to its `max` (at least one), on a random free spot along the roads; the weighted filling never takes them. `palette` (up to 64 entries): block name → block name, applied to every structure of the style (states keep their properties where the new block has them), so a mod makes a new style from existing houses (the base game's `taiga` is the plains houses in spruce; `snowy`, the tundra's style, adds its own igloo and snow-covered cabin to them). `layouts` (1–16, decision E-408): the street plans of the style's villages, one chosen per village by `weight` (1–1000); without the field a mix of all six kinds (street 3, cross 2, T 2, L 1, plaza 1, tree 2). `kind` (required) is one of `cross` (four roads from the centre, one to each side), `street` (one long main road through the centre, along an axis or a diagonal, with side roads), `t` (three roads: two opposite, one across), `l` (two roads at a right angle), `plaza` (a ring road around a square with the centre and a side road from the centre to the ring, roads out from the ring, each leaving its side of the ring off the middle by up to half the ring's distance so that they never line up into a cross; houses stand outside the ring, the square stays open; a ring that water or a steep step would cut makes the village a cross) or `tree` (`arms` roads from the centre at random angles, the first on a diagonal, each bending `bends` times by 45 degrees). Roads are three blocks wide and run in eight directions; diagonal roads are staircases of cells, and houses at them face the road along the nearer axis with a forecourt of side road three blocks wide from their door to the road. Parameters (each kind has its own defaults): `armLength` (a share of `radius`, 0.2–1, the length of a road from the centre or from the ring), `branches` (`chance` 0–1 per spot, `every` 0–64 blocks between spots along a road, 0 for one spot at 50–70 % of it; `length` a share of the radius), `arms` (2–5), `bends` (0–2), `ring` (8–20 blocks from the centre to the ring's middle line) and `exits` (1–4); a range is a number or `[low, high]`, drawn per village. `winding` (0–1): the chance per village that its roads wind with the terrain, turning by 45 degrees every 6 to 11 blocks towards the flatter neighbouring direction (at random on level ground), at most 45 degrees off their heading. `diagonals` (default true): false keeps every road on the axes and switches winding off. A style over water never lays diagonal or winding roads (a house's front lies along a boardwalk). A later pack replaces a style of the same name; a style without a known centre, foundation or at least one known surface per road rank is left out with a warning (unknown surfaces and steps are skipped with one), unknown pieces are skipped. `rareCentre` (decision E-592, optional): `{"structure": "<name>", "chance": 0.25}` takes that structure instead of `centre` with the chance per village (drawn from its own position, so the rest of the plan stays as it is), turned like the centre with its entrance (the middle of its south side) to the main road and its `groundLayer` at the ground, where its footprint fits the ground (else the usual centre); its loot chests are filled and its guardian zones work. The base game's desert style has the desert temple with 0.3.

A **piece** is an ordinary structure (see above) built for a road on its south side: the door is in the last row of the first layers, layer 0 is the floor that replaces the ground's top block, and the planner turns the piece in quarter turns so the door faces the road (states turn along, so stairs keep their slope). Where the ground is lower than the floor, the foundation fills it (up to 16 blocks); above the footprint the terrain is cleared. Beds (blocks with `"bed": true`, their head), workstations and the bell inside a piece are listed in the village's state, and the creatures in its `mobs` (an animal pen's pair) appear, persistent like natural animals, when their chunk is first seen. The other extras of a structure (`contents`, `stands`, `labels`, `minecarts`, `updates`, `growing`) are left out in villages, with a warning when the style is loaded: chests and furnaces of a piece stand empty, saplings are only planted. Every outer door gets a doorstep at the floor's height in front of it (the ground there is levelled and laid as side road), so the door opens onto walkable ground.

Further style fields (decision E-421): `look` dresses the style's villagers (see Villagers below; empty lists take the species' default look), `villager` names the creature kind living in its villages (default: the settings' `villager`), `golem` changes the settings' golems for its villages (an object with fields of the settings' `golem`, each over the settings' value as all packs leave it, so `{ "minVillagers": 5 }` keeps the settings' creature kind; or `false` for none), and `residents` (up to 8) lists other creatures of its villages, each `{ "mob", "min", "max" }` (0–16, default one each), such as the cats of a later stage. Residents are data only for now: no village spawns them yet (the place to do so is beside the pen animals of the village plan, `QcVillagePlan::creatures`, or `QcMobManager::spawnVillagers`).

**Extending a style** (decision E-421): a style file with `"extends": "<style>"` starts from that style as the earlier packs and files left it. Without its own `name` it changes that style in place (a patch); with a `name` it is a new style made from a copy, which starts without the base's `biomes` and as no fallback (it builds nowhere until it names its own biomes or sets `fallback`), so a copy never takes over the base's villages. Fields it gives replace the base's (`ground`, `stilts` and `wetland` together; `golem` field by field over the base's), the others stay; its `remove` object takes `biomes` from the base's list, its `add` object appends to the base's lists: `biomes` (each biome once), `crops`, `pieces` and `layouts`, each within its limit. An extension may extend a style another extension made (a named one of an earlier file or pack). Two mods that each add a crop and a biome to the plains both keep theirs:

```json
{ "formatVersion": 1, "extends": "qtcraft:plains", "add": { "biomes": ["qtcraft:forest"], "crops": [ { "block": "qtcraft:pumpkin_stem", "weight": 2 } ] } }
```

Conflict rules: in each pack the files without `extends` load first (each replaces a style of the same name whole, with all extensions of earlier packs), then the extensions in file-name order; packs load in their order, so an extension applies to the style as it stands when its pack is loaded, and a later full definition of that style drops it. `add` or `remove` without `extends` and an extension of a style no earlier file has are left out with a warning (when a later file of the same pack defines that style, the warning says to rename the extension so it sorts after it). Unqualified names in an extension take its own pack's namespace, so a base style is extended as `qtcraft:plains` and the base game's biomes and blocks are written `qtcraft:forest`. **A biome belongs to one style:** when two styles name it, or two are the fallback, the style changed last keeps it (by pack order: the last pack that defined or extended it; within a pack the later file), with a warning; a mod that wants a base style's biome takes it with `remove` in an extension of that style. Unknown biomes, a `villager` that is no villager creature and unknown `residents` are warned about when the content is finished (an unknown golem creature is not: the rule rests until the content has it, see the settings below).

**Format versions** (decision E-421): style files, `worldgen/villages.json`, villager species, professions and trades carry `"formatVersion"` (a whole number, 1 when missing; the current format is 1). A file with a newer version than the game reads is left out with a warning naming both versions. Files of the earlier format are refused with where their content went: a pack's `villagers.json`, a style's `villagers` (now `look`), the settings' `workstations` and a profession's `workstation` (now the profession's `workstations`).

**Variation inside a blueprint** (decision E-404): where a village places a structure, two optional fields make each building different, drawn per building from the seed (the same world builds the same houses). `choices` is an object of named choices (up to 8), each a list of 1–16 options, one taken per building, all equally likely (list an option twice to make it likelier); an option is an object of name swaps like the style's palette, applied to the structure's block names (states kept) and to its creatures' names, `{}` keeps the structure as written. The style's palette is applied first, so a taiga style that turns oak into spruce keeps its spruce even where a choice would turn oak into birch. `parts` (up to 16) are optional pieces of the building, each with a `name`, a `chance` (0–1, default 0.5), its north west bottom corner `at` ([x, y, z] inside the structure) and `layers` like the structure's own, in its palette (a space keeps the structure's cell); the structure's size must already hold them (a chimney on the ridge, flowers in a front row of grass, a shed beside the house):

```json
"choices": {
    "wood": [ {}, { "oak_planks": "birch_planks", "oak_log": "birch_log" } ],
    "animal": [ {}, { "pig": "sheep" } ]
},
"parts": [
    { "name": "chimney", "chance": 0.5, "at": [5, 5, 2], "layers": [ ["C"], ["C"], ["C"] ] }
]
```

Elsewhere (the showcase world, other structures) a structure is placed as written; the showcase's village rows show every blueprint with all its parts.

**Villages over water** (decision E-407): `"ground": "water"` (default `"land"`) makes a style stand on stilts, like the base game's `swamp`:

```json
{
    "name": "swamp",
    "biomes": ["swamp"],
    "ground": "water",
    "stilts": { "post": "spruce_log", "stair": "spruce_stairs", "height": 4, "spacing": 3, "maxDepth": 8, "water": 0.06 },
    "wetland": { "depth": 1, "margin": 4, "fray": 3, "blend": 4, "bottom": "mud", "water": 0.4, "mudBand": 2, "scale": 8,
                 "plant": "sugar_cane", "plantChance": 0.12 },
    "path": "spruce_planks",
    "branchPath": "spruce_slab[type=top]",
    ...
}
```

Every floor (layer 0 of every piece) and every road lies at one height, `height` (2–8, default 3) blocks above the water surface (the block below the sea level). A place carries stilts where its ground lies at most at that height and at most `maxDepth` (0–16, default 5) blocks below the water surface. A centre needs at least 60 % of the ground around it carrying stilts and at least `water` (0–1, default 0.25) of it under water; of the places tried in a region, the wettest one that fits wins. Pieces stand on `post` blocks (default spruce log) every `spacing` (1–8, default 3) cells and at their far edges, down to the bottom, instead of a foundation; their floors join the road directly (no strip of ground between them), and a piece is only placed where its whole front lies along the road. Roads are **boardwalks**: the road surfaces (`path`, `branchPath`; here a surface may be a block state such as a top slab, as may a `step`) at the floor height with posts on a world grid every `spacing` cells; they end where the ground cannot carry them. Where a boardwalk ends on dry land, `stair` blocks (default spruce stairs, facing up) lead down to the ground, one block per cell. The optional `wetland` shapes the ground around the village (decisions E-407, E-660, E-661): within `margin` (0–12, default 4) blocks of its pieces and boardwalks, plus up to `fray` (0–8, default 3) more where a noise bends the edge, the ground lies at the water surface, deeper water filled up to it; from there it returns to the terrain by at most 0.6 blocks per block of distance, ending `blend` (1–8, default 4) blocks beyond the edge, so ground far above the water is only cut a few blocks near the village and never gets a cliff. On the flat wetland a noise of `scale` (2–64, default 8) blocks forms irregular pools `depth` (1–4, default 1) blocks deep (their middle a block deeper) over the share `water` (0–1, default 0.4) of the open ground (not under pieces and boardwalks; only where no neighbouring column lies above the water surface), ringed by `mudBand` (0–4, default 2) blocks of the `bottom` block (default mud), with grass between; under pieces and boardwalks lies the bottom block. The pools never drain: every water block has a block or water beside and below it. `plant` (a block, default none) grows beside the pools on a share `plantChance` (0–1, default 0) of the columns, one or two blocks tall. The stairs and a strip beyond them stay as they are (the way to land). No trees or plants grow in that area. Villagers walk the boardwalks; creatures do not climb ladders on paths (decision E-402), so a style over water reaches land by stairs.

The **settings** (`worldgen/villages.json`; a later pack's file changes the fields it gives and keeps the others, `golem` field by field, so a mod setting `spacing` keeps the villagers and golems): `spacing` (128–4096, default 384: the edge of the square regions, at most one village each), `chance` (0–1, that a region tries to have one), `attempts` (1–32: places tried for the centre), `radius` (16 to spacing / 2 − 16: how far pieces and roads reach from the centre), `maxHeightSpread` (largest height difference of the ground around the centre), `maxPieceSlope` (under one piece), `lampSpacing` (blocks between lamp posts), `bell` (the meeting point block), `villager` (the creature kind living in villages whose style names none, the base game's `villager`) and `golem` (decisions E-415, E-470; a style may have its own): `mob` is the creature kind villagers summon as their golem. A villager wants a golem while it slept in its bed within the last `sleptSeconds` (0–86400, default 600, one day). A villager that wants one and panicked at a hostile creature within its `fleeDistance` in the last `panicSeconds` (default 10) summons a golem when at least `minVillagers` (1–1024, default 3) villagers of its village (or, without a village, any) that want one, itself included, are within `gatherDistance` (1–64, default 10) of it; without panic `gossipVillagers` (1–1024, default 5) of them summon one with `gossipChance` (0–1, default 0.1) per check (every 5 s). No creature of the golem kind may be within `golemDistance` (0–64, default 16). The golem appears within `spawnRadius` (2–32, default 8) blocks horizontally and 6 up and down, at the highest place of a column where it stands on dry ground of the opaque render layer that does not hurt (not on glass, panes, leaves or ice) with its whole body clear. A village summons at most once per `cooldownSeconds` (default 30; villagers without a village keep that pause per chunk, so several farms summon apart), also without the game rule `mobSpawning` (like the reference), and never beyond the server limit `villageGolems` (counted per golem kind over the villages and the loaded golems outside them, built ones included; 0: none). A player who hurts a villager or a golem of a village is its enemy for `grudgeSeconds` (default 300): its golems attack them. While the content has no creature of the `mob` name the rule rests and the server logs it once; a mod with its own golem names it here or in its style. Which blocks are workstations comes from the professions (see Villagers). A biome gets villages with `"villages": true`.

A block with `"bed": true` is two blocks long like a door is two high: it needs the states `facing` (`north`, `east`, `south`, `west`) and `part` (`foot`, `head`), else the block is rejected; placed from the foot, the head goes one block further in `facing`; breaking either half takes the other one, and only the foot drops the item.

### Villagers (stage 37.2b)

Villagers (decision E-411) are creatures of a kind with `"villager": "<settings>"`, naming the villager settings they live by (a `skeleton` is required, they are peaceful walkers; they never spawn by themselves, give them `"spawn": {"weight": 0}`; a kind naming settings no pack has, or settings left out for a broken `unemployed`, is no villager, with a warning). When a chunk of a village is seen for the first time, a villager of the kind its style or `worldgen/villages.json` names moves into every free bed whose head lies in it, up to the server limits `villagersPerVillage` and `villagers`. It claims the bed and, when it finds a free one, a workstation, opens wooden doors (blocks with `toggles` and an `open` state; iron doors without `toggles` stay shut) and is drawn in the look the server gives it, not in its `outfit`. Children belong to the kind of their parents, and only villagers of one kind breed together.

The **villager settings** (`villagers/<name>.json`, decision E-421; a later pack replaces settings of the same name) are those of one species (settings whose `unemployed` is no profession without workstations are left out with a warning); every species shares all professions and their trade files, and a style's `look` goes before the species' default look; the base game has one, `villager`, and a mod adds a second species with its own creature kind, settings and style:

```json
{
    "formatVersion": 1,
    "name": "villager",
    "unemployed": "unemployed",
    "routine": [ { "from": 0.0, "do": "wander" }, { "from": 0.04, "do": "work" }, { "from": 0.53, "do": "sleep" } ],
    "fleeDistance": 10,
    "shelterFromRain": true,
    "trading": { "levels": [0, 10, 70, 150, 250], "offersPerLevel": 2, "restocksPerDay": 2, "restockGap": 0.1 },
    "breeding": { "food": 3, "growUpSeconds": 1200, "cooldownSeconds": 300, "partnerDistance": 5, "shareAbove": 6, "shareDistance": 4, "youngSpeed": 1.3, "foods": { "bread": 3, "carrot": 1, "potato": 1, "wheat": 1 } },
    "look": { "outfit": "villager_tunic", "hair": ["short_hair", ""], "skin": ["#d8a07a"], "hairColor": ["#4a3020"],
              "shirt": ["#3a7bc8"], "pants": ["#34406a"] }
}
```

A **profession** (`professions/<name>.json`, decision E-421; a later pack replaces one of the same name, so two mods each adding a profession keep both) is shared by every species:

```json
{
    "formatVersion": 1,
    "name": "farmer",
    "workstations": ["composter"],
    "hat": "villager_straw_hat",
    "tendsCrops": true,
    "layers": { "torso": { "texture": "villager_farmer_apron", "tint": "none" } }
}
```

- Professions: `name`; `workstations` (up to 16 blocks the profession works at; the village state lists them, and the workstation kind of such a block is the profession's qualified name, e.g. `qtcraft:farmer`; none for the unemployed; a block two professions name goes to the later one, with a warning); `layers` (slots of the outfit replaced for this profession, written like an outfit's layers: an apron on the `torso`), `hat` (a hair-kind appearance worn instead of the style's hair) and `tendsCrops` (harvests the ripe crops within 8 blocks of its workstation, on any field, a player's too (decision E-490), and plants them again in one step; the harvest counts as the villager's produce, no items drop; not with the game rule `mobGriefing` off); optionally its own `routine` (as below, in place of its species') and `offersPerLevel` (1–8, in place of its species' `trading` value). A species' `unemployed` names the profession without workstations; an unemployed villager takes the profession of the free workstation it claims, and one that loses its workstation before it has any experience is unemployed again. Its offers are the trades files naming it (see Trading).
- `routine` (1–24 steps): from `from` (a share of the day: 0 sunrise, 0.25 noon, 0.5 sunset, 0.75 midnight) on the villagers do `do` until the next step, the last step lasting into the first of the next day: `wander` (stroll near home), `work` (at the workstation), `meet` (at the village's bell), `home` (by the bed) or `sleep` (in the bed; a villager gets up when it is hurt, its bed is gone or the routine says so).
- `fleeDistance` (0–32): villagers run home from hostile creatures this close; `shelterFromRain`: they go home while it rains at the village's middle.
- `breeding` (decision E-415): two grown-up villagers of a village, each holding `food` (0–64) produce, that see each other within `partnerDistance` (1–16) blocks by day (the routine says neither `home` nor `sleep`) and in dry weather at the village's middle get a child when the village has a free bed; each gives `food` and rests for `cooldownSeconds` (0–86400). The child moves into the free bed nearest to them, has the unemployed profession, wanders instead of working at `youngSpeed` (0.5–3) times the walking speed, is drawn at half size and takes a workstation once grown up after `growUpSeconds` (1–86400). Produce is what farmers (`tendsCrops`) harvest; a farmer holding more than `shareAbove` (0–1024) gives villagers within `shareDistance` (0–16) that hold less than `food` what they lack. `foods` (decision E-490; item names with what each is worth, 1–64, at most 64 items) are the items grown-up villagers (awake, not lying in bed) pick up from the ground at their feet as produce while they hold less than `shareAbove` + `food`: players feed a village by throwing it bread. With the game rule `mobGriefing` off they pick nothing up. Server limits: `villagersPerVillage`, `villagers`.
- **Villages as points of interest** (decision E-490): beds (their head) and workstations are the points of interest of villages. One set within a village's area (its box plus 16 blocks) is listed there; where the areas of two generated villages overlap, it belongs to the village whose box is nearer. One set outside every area but within 32 blocks of a village's box joins the nearest such village, whose box grows to hold it (up to 384 blocks wide), unless the grown area would meet another village's; any other founds a **settlement**, a village without a plan whose id comes from that first bed or workstation, with its centre (the meeting point) there and the style of its first villager, unless its area would meet a village's (then the spot belongs to no village). A bed or workstation set while its village already lists the most it may (server limits `villageBeds`, `villageWorkstations`) is not listed, not even after another one is broken; breaking and placing it again lists it. Breaking a bed or workstation drops it and its claim; a settlement without beds, workstations and villagers is forgotten. A villager that stands more than 16 blocks beyond its village's area (32 beyond its box; carried off, pushed or led away) leaves it; a villager without a bed whose village has none free, or without a village, moves into the village with the free bed nearest to it within 48 blocks that has more beds than villagers, unless it stands more than 16 blocks beyond that village's area. World generation places beds and workstations in the showcase outside its village rows as blocks that count as placed (the generator's points of interest). Villages of the generator keep their plan (roads, fields) and id.
- `look`: the default look (an `outfit`, hair styles to choose from, an empty name for none, and lists of `skin`, `hairColor`, `shirt` and `pants` colours as `"#rrggbb"`, at most 16 each). A village style dresses its villagers in its own look with `"look": { ... }` in the same form; empty lists take the default look's. Each villager draws one of every list from its own seed. For every look and every profession with `layers` the server registers the joined outfit `<outfit>@<profession>` (not playable), which the clients receive with the other appearances.

The base game has farmers (composter, apron and straw hat), smiths (furnace, leather apron) and fishers (barrel, oilskin vest and hat) and the looks of the plains (tunic), desert (robe and headwrap), taiga (fur coat and hat), snowy (pale fur coat and fur hat) and swamp (smock, waders and reed hat). Trading (stage 37.2c, below) and breeding (decision E-415, above) build on a villager's profession, level, experience and produce, which are saved with it.

### Trading (stage 37.2c)

A villager with offers opens its trading screen when a player uses it (decision E-414). Its offers come from the files in `trades/`; how villagers level and restock from `trading` in the settings of their species (`villagers/<name>.json`):

```json
"trading": { "levels": [0, 10, 70, 150, 250], "offersPerLevel": 2, "restocksPerDay": 2, "restockGap": 0.1 }
```

- `levels`: the experience a villager needs for each of the five levels (novice, apprentice, journeyman, expert, master), starting at 0 and rising.
- `offersPerLevel` (1–8; a profession's own value takes its place): for each level it reached, a villager draws this many offers of that level from its profession's offers (by a stable hash of its look, the level and the offer's id, so it keeps them for good); a level with fewer offers gives all of them. Offers a villager already has stay when a mod adds offers to the level; only an offer that no longer exists is replaced by a new draw.
- `restocksPerDay` (0–8) and `restockGap` (share of a day): during work time at its workstation a villager whose offers were used restocks them, at most this often a day and this far apart.

A trades file (`trades/<name>.json`) lists offers of one profession:

```json
{
    "formatVersion": 1,
    "name": "farmer",
    "profession": "farmer",
    "offers": [
        { "level": 1, "costs": [ { "item": "wheat", "count": 20 } ], "result": { "item": "emerald", "count": 1 },
          "maxUses": 16, "villagerExperience": 2, "playerExperience": 1, "demand": 2 },
        { "level": 4, "costs": [ { "item": "emerald", "count": 3 }, { "item": "wheat_seeds", "count": 8 } ],
          "result": { "item": "melon_seeds", "count": 4 } }
    ]
}
```

- `level` (1–5, default 1): from which level a villager may offer it. `costs` (1 or 2 stacks) are what the player pays, `result` what they get; `count` 1–64 (at most the item's stack size). Items are checked when the server starts: an offer naming an unknown item is left out with a warning.
- `maxUses` (1–999, default 12): trades until the next restock. `villagerExperience` (default 2) and `playerExperience` (default 1, dropped as orbs) per trade. `demand` (0–64, default 0): an offer sold out at a restock asks for this many more of its first cost for each such restock, at most twice the base count; each restock where it was not sold out takes one step back.
- `id` (default `<first cost>><result>`, e.g. `qtcraft:wheat>qtcraft:emerald`): unique within the profession; the saved uses and demand of a villager's offers belong to it. A later file with an offer of the same id replaces that offer.
- A file of the same `name` as an earlier pack's replaces it; a file of another name adds its offers to the profession. The base game's files are `farmer`, `smith` and `fisher`; the unemployed have none.

The base game's currency is the emerald (ore deep in the stone in small veins, item, block). `/profession <profession> [level]` (operators) gives the nearest villager a profession and level, e.g. to try a mod's offers on a summoned villager.

### Commands (stage 24)

Mods cannot run code, so they add commands as **macros** (decision E-248): `commands/kit.json`

```json
{
    "name": "kit",
    "permission": "player",
    "usage": "/kit <item> <count>",
    "description": "Gives a starter kit.",
    "run": ["/give $1 $2", "/give torch 8"]
}
```

- `name`: the command players type (`/kit`), lower-case letters, digits and `_`, at most 32. It is not namespaced; a later pack replaces an earlier macro of the same name, and a command of the game always wins over a macro (the server ignores the macro then).
- `permission`: `player` (everyone may call it) or `operator` (default).
- `run`: 1 to 16 command lines starting with `/`, at most 256 characters each. `$1` … `$9` are the words after the macro's name, `$*` all of them; called with fewer words than the highest `$n`, the macro answers with its `usage`.
- Every line runs as the player (or console) who called the macro and is checked for him again: in the example a player without operator rights gets "Only operators can use /give". A macro never grants rights. Macros cannot call other macros.
- `usage` and `description` are shown by `/help` as they are (not translated).

Code that is compiled into the game (not mods) adds real commands through the registry: `QcServer::commands().add(QcCommandSpec{...})` with a name, aliases, the permission (`QcPermission::Player`, `Operator`, `Console`), whether it needs a player, the minimum number of words, usage and description (English texts marked with `QT_TRANSLATE_NOOP("QcServerMessages", …)`) and a handler that receives a `QcCommandContext` (source, words, whole line). Taken names are refused. See `src/server/commands/QcCommandRegistry.h` and the command groups next to it.

### Replacing existing content

A definition whose name already exists **replaces the earlier one completely** (decision E-026), for example `blocks/glass.json` with `"name": "qtcraft:glass"`. Copy the original file and change what you need; fields you leave out get their defaults, not the old values. Runtime ids stay the same, so saved worlds are not affected. Translations are merged key by key.

## Textures, texture packs and mods

A mod's `textures/` are content: the server sends them to every client, and they are the base level of the mod's namespace. Texture packs (client side, `docs/Texturpakete.md`, decisions E-297 and E-302) override them by name like the base game's (`textures/<mod id>/<name>.png|json` in a pack), and a pack with `"procedural": true` such as the built-in **QtCraft HD** paints a mod's procedural textures at its resolution too. A procedural definition may say how it looks above 16×: `"detail": {"grain": 0–1, "bevel": 0–1, "smooth": true|false}` (E-299). A mod can ship texture packs of its own in `texturepacks/<folder>/` (with `texturepack.json`); players who installed the mod find them in **Settings → Texture packs** as `mod:<mod folder>/<folder>`. They are never sent over the network.

## Worlds and mods

A saved world remembers the packs it was played with (`world.json`, `packs`). Opening it without one of them logs a warning; blocks of the missing mod become air and its items disappear from inventories. Adding a mod to an existing world is safe; new ores and biomes only appear in chunks generated afterwards. Creatures, dropped items and falling blocks of a missing mod are left out of their chunk with one warning per name. Saved entities are a header and versioned components (decision E-420): data a later version of the game stores with an entity (a component or the newer fields of one) is kept when this version saves the world again, and data an older version stored is read with defaults for what it lacks, so new entity fields need no new world format. The block entities of a chunk are stored the same way (decision E-440): one versioned table per kind (containers, machines, saplings, circuit memory, scheduled ticks, fires, …) whose entries carry their own version and length, so a table a later version or a mod adds and the fields appended to an entry survive a save by a version that does not know them. Mods cannot add tables themselves yet (no script API). Table ids from `0x8000` on belong to mods and those below to the game (`QcBlockEntityRecord::Table`); the same holds for the component ids of entities (`QcEntityCodec::Component`), so a mod's data never collides with a later version of the game.

## Boundary between core and mods

Mods **can**: add and replace blocks (with states, shapes and light), shapes, building-part families and materials (and exclude materials from parts), items with tags, recipes, smelting recipes, fuels, machine blocks with their own categories, mobs, biomes, features, ores, terrain settings, structures, village styles and settings, showcase settings, textures, sounds and translations; depend on other mods.

Mods **cannot**: run code, add new kinds of behaviour (a new AI, a new block mechanic, new UI: every machine uses the furnace logic and screen, every storage block the chest screen, state rules are the fixed ones above), change the protocol, the save format or the rules the server enforces, or read and write files outside their own pack directory. Everything a mod provides goes through `QcContentPackLoader` (the only code that reads pack files) into `QcContentRegistry`; the rest of the game only sees the registry. The server sends the registry to clients, so clients never read mod files themselves.

Only regular files and real directories are read. A linked mod folder is reported as not loaded; linked sub-folders and files and special files such as pipes or devices are not read (silently inside the content folders, with a warning for `pack.json` and `worldgen/terrain.json`). Size limits: 4 MiB per file, 256 mod directories (64 loaded), at most 64 drops per block, at most 64 `plantOn` entries per sapling, manifest `name` 256 and `version` 64 characters; the parser checks every field's type and range. All mods together may make the loader read at most 64 MiB: the files of a mod are measured before anything is read (each file counts at least 256 bytes, a hard link as often as it appears), and every attempt counts, also for mods that are refused afterwards or loaded a second time. Each mod is checked right after loading, exactly as its content would reach clients (including the items created for its blocks): the counts clients accept and the 32 MiB content sync. Translations: a language file holds at most 65,536 entries (a larger one is skipped with a warning), all languages of the base game and all mods together at most 262,144 (the base game uses about 2,600); a language file that would go beyond that is skipped with a warning, and a mod whose generated part names would is refused (decision E-371; files are checked before part names exist, so a mod just under the limit can still be refused once its parts are named). Skipped files appear as warnings in the log like other broken files (`content warning:` on stderr for `qtcraft-headless`); the Mods screen shows only why a mod was not loaded. A mod that fails is refused and leaves no trace; at most 64 mods are loaded and checked per start (refused ones count too). Shaped recipes have at most 9 keys; procedural textures keep only `pattern`, `primary`, `secondary` (at most 32 characters each), `variation`, `seed`, `detail` (only `grain`, `bevel` in 0–1 and `smooth`) and an emblem's `bitmap` (16 × 16) and `palette` (16 colours). A final read-back like a client's is the safety net: should it ever fail, the game starts without mods. World generation is limited to 256 ore definitions with at most 4,096 ore blocks per chunk in total, 256 biomes, 1,024 features and 4,096 feature placements (at most 64 per biome) and 64 pool attempts per chunk. PNG textures may be at most 128 × 128 pixels (checked before decoding). Sounds are limited to the ranges above (8 layers of at most 10 s, 8 variants), checked by the parser and again by every client; a client renders at most 16 Mi samples (64 MiB) of sound, sounds beyond that stay silent. A mod that fails a check is skipped together with its dependents; the Mods screen shows the reason after the next world start. Security questions that go beyond that (sandboxing, signatures, permissions for future script hooks) are collected in `docs/Mod-Sicherheit.md`.
