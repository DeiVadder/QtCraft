# QtCraft architecture

This document describes the current state. Sections marked *planned* are not implemented yet.

## Modules

| Target | Layer | Depends on | Content |
|--------|-------|-----------|---------|
| `qc_common` | Common | QtCore | Coordinates, chunk storage (palette sections), content registry and JSON parser, block states and shapes (`QcBlockStateTable`), building parts (`QcPartGenerator`), block light flood fill (`QcLightVolume`, used by the server and as the reference), the handbook model (`QcHandbook`, `QcHandbookBuilder`, Markdown and JSON forms), protocol messages and codec, transports (`QcTransport`, `QcInProcessTransport`, `QcConnection`), shared physics, thread hand-over helpers (`QcMailbox`, `QcWorkerPool`). |
| `qc_network` | Common | `qc_common`, Qt Network | TCP transport (`QcTcpTransport`: length-prefixed frames, keep-alive, timeout, send limit), connecting (`QcTcpConnector`), server addresses (`QcServerAddress`); decision E-251. |
| `qc_base_content` | Data | – | Base game content pack embedded as `:/content/qtcraft`. |
| `qc_texture_packs` | Data | – | Built-in texture packs embedded as `:/texturepacks/<folder>` (stage 28). |
| `qc_server` | Server | `qc_common`, `qc_base_content` | `QcServer` (authoritative tick loop, players, chunk streaming, neighbour updates), `QcBlockRules` (placement states, connections, support and ground rules), `QcLiquidFlow` (flowing water and lava, E-054; spreading prefers the way to the nearest drop, E-103), `QcFallingBlockManager` (falling sand and gravel, E-055), `QcMachineManager`, `QcContainerManager`, `QcHunger`, `QcHandbookRules` (rule values quoted by the handbook), `QcServerWorld`, world generators, content-pack loader, mod loader (`QcModLoader`), `QcLocalServerHost` (server thread for single player, optionally listening for network players), `QcNetworkServer` (TCP listener in the server thread), `QcServerLogin` and `QcIdentityStore` (login of remote clients, E-252), `QcServerSettings` (server.json). |
| `qc_clientcore` | Client (GUI-free) | `qc_common`, `qc_network`, QtGui (`QImage` only) | `QcClientSession` (world mirror, prediction, login answer `QcClientLogin`), `QcNetworkClient` (joining a network game), `QcChunkMesher`, `QcMeshScheduler`, texture atlas, camera, the character preview's logic (`QcPreviewCamera`, `QcPreviewPose`, `QcPreviewPacer`, `QcPreviewScene`), `QcControlInterface`, debug data (`QcDebugSnapshot`, `QcDebugText`, `QcDebugJson`, `QcDebugLines`, `QcLightProbe`, `QcStatsLog`), sound synthesis and mixing without audio devices (`QcSoundSynthesizer`, `QcSoundBank`, `QcAudioMixer`, `QcSoundSpatial`, `QcLocalSounds`, `QcAmbience`, `QcMusicComposer`). |
| `qc_audio` | Client (audio) | `qc_clientcore`, Qt Multimedia, Qt Concurrent | `QcAudioOutput` (default device through `QAudioSink` in pull mode, `QcMixerDevice`), `QcAudioEngine` (cues, UI clicks, ambience loops, music scheduling). |
| `qtcraft` | Client (UI) | `qc_server`, `qc_clientcore`, `qc_audio`, Qt Quick | QML UI, `QcGameController`, `QcHandbookModel`, `QcWorldView`/`QcWorldRenderer` (QRhi), screenshot hook. Links the server only to host it in-process. |
| `qtcraft-headless` | Tool | `qc_server`, `qc_clientcore` | Server plus control-interface client without a window; with `--server` the dedicated server (`QcDedicatedServer`, `QcSignalWatcher`, E-255); with `--join` the control-interface bot joins a server over TCP instead (`QcHeadlessJoin`, E-270). |

The client code never includes server headers except in the two composition roots (`QcGameController` and `QcHeadlessGame`), which only create the `QcLocalServerHost` and take a transport from it. All game interaction goes through protocol messages.

## Threads

| Thread | Runs |
|--------|------|
| GUI | QML, `QcGameController`, `QcClientSession` (20 Hz tick timer), mesh scheduling decisions |
| Render (Qt Quick) | `QcWorldRenderer` |
| Server | `QcServer` and, when listening, `QcNetworkServer` with every TCP socket of the remote clients (no locks for the game state, E-251): client messages and the 20 Hz ticks (1–100 Hz with `/tick rate`, back to back in 20 ms slices during `/tick sprint`, E-249) in one event loop; input budgets, rate limits, autosaves and confirmations follow the players' time (`QcServerState::playerTimeNs`, the real time each tick stands for), not the tick count; the next tick is a single-shot timer on the deadline grid of `QcTickScheduler` (E-090); console commands arrive as blocking queued calls from the host (E-247) |
| Generation workers | `QcTerrainGenerator::generate` (`QcWorkerPool` in `QcServerWorld`) |
| Mesh workers | `QcChunkMesher` on immutable chunk snapshots (`QcWorkerPool`), including sky light of the section's neighbourhood |
| Light worker | `QcBlockLightEngine` (one `QcWorkerPool` thread of `QcMeshScheduler`): incremental block light, published as immutable section snapshots |
| Backup copy | `QcBackupRunner`: copies the hard-linked snapshot of `/backup` (one `std::thread` at a time, result through a `QcMailbox`, collected every tick; E-256) |
| Qt thread pool | Rendering the sound bank and music pieces (`QtConcurrent::run`, results to the GUI thread through `QFutureWatcher`) |
| Audio (Qt Multimedia) | Pulls mixed samples from `QcMixerDevice`; every access to the mixer is guarded by one mutex in `QcAudioOutput` |

Data crosses threads only as immutable snapshots (`std::shared_ptr<const QcChunk>`, encoded frames) through `std::mutex`-guarded mailboxes; Qt queued calls only wake the receiver (see decision E-010).

## Protocol

Frames are `[quint16 type][QDataStream payload]`, see `QcProtocol.h` and decision E-007. Over TCP every frame is preceded by its length as a big-endian `quint32` (a length of 0 is a keep-alive, `QcFrameReader`, E-251). Version: `QcProtocol::version` (currently 28: stage 26 added `GameMode`, `CreativeItem`, `PickBlock` and the flight in `PlayerInput` and `PlayerState`, E-282 to E-285; 27: stage 25b added the server's time of the tick to `EntityMoves` for the client's interpolation buffer, E-271; 26: stage 25 added the login messages `LoginChallenge` and `LoginResponse`, `PlayerList`, translation keys in `Disconnect` and the granted view distance in `Welcome`, E-252; 25: the review of stage 24 widened the range of `WorldTime.speed` for sprints, E-249; 24: stage 24 added the speed of the time of day to `WorldTime` for `/tick`, E-249; stage 23 added the armour stand entity type with its pose to `EntitySpawn` and armour/`placesStand` to the content sync, E-237, and the cape (`QcAppearance::cape` in `Hello`, `SetAppearance` and `EntitySpawn`, the appearance kind `cape` with its shape and `QcMobDefinition::cape` in the content sync), E-240; both halves were developed as 22 and merged as 23; 21: stage 22 added the armour slots (`QcEquipment`) to `InventoryState` and `EntitySpawn`, decision E-232; 20: stage 21b added `DebugSubscribe` and `ServerDebug`; 19: stage 21 added `ChunkLabels` and `WorldTime.running`; 18: stage 20 changed `ChatMessage` and added `QuickMoveItem`, the block and recipe expansion added the block fields `slowsInside`, `surface.speed`, `surface.jump` and the item field `bottles` to the content sync, because client prediction needs them). The payload codecs are one encode/decode overload pair per message, grouped by topic (`QcSessionCodec`, `QcWorldCodec`, `QcPlayerCodec`, `QcEntityCodec`, `QcMachineCodec`, `QcDebugCodec`, shared field codecs in `QcProtocolCodec`, chunks in `QcChunkCodec`); `QcProtocol.cpp` dispatches on the type tag. Each peer only accepts the message types the other side may send. Chunk sections are a palette plus run-length encoded indices (E-016).

| Message | Direction | Content |
|---------|-----------|---------|
| `Hello` | C→S | protocol version, player name (at most 256 characters before cleaning), appearance (outfit, hair, four colours, cape); the layout up to the name never changes, so other versions get a clean refusal |
| `LoginChallenge` | S→C | to remote clients after `Hello`: server name, message of the day, 32-byte nonce, the world's 16-byte salt, whether a password is needed, whether the name has a registered identity, the largest view distance, the server's content packs (id, version, file hash) (E-252) |
| `LoginResponse` | C→S | password proof, identity proof, the identity itself only to register it, wanted view distance, the client's content packs; accepted once before playing |
| `Welcome` | S→C | protocol version, entity id, world name, seed, saved view direction, the view distance streamed to this player |
| `PlayerList` | S→C | everyone on the server (entity id, name, operator), to all players when someone joins or leaves or operator rights change |
| `ContentSync` | S→C | complete content registry (incl. the list of loaded packs, block properties and resolved shapes); runtime block ids = block state ids |
| `ChunkData` | S→C | one chunk column (compressed palette sections) |
| `ChunkUnload` | S→C | chunk position (the client drops the chunk's labels too) |
| `ChunkLabels` | S→C | the labels floating in a chunk, right after its `ChunkData` when it has any: position, text (translation key), detail line, heading; at most 4096 per chunk, texts at most 256 characters (decision E-222) |
| `BlockUpdate` | S→C | position, block state id |
| `PlayerInput` | C→S | sequence, movement intent (with the wish to fly, E-284), view direction |
| `PlayerState` | S→C | last processed input sequence, authoritative motion (with `flying`) |
| `Disconnect` | both | reason (English) with a translation key and up to 16 arguments like `ChatMessage` (E-094) |
| `StartMining`, `CancelMining`, `FinishMining` | C→S | block position |
| `UseItem` | C→S | clicked block, face and the aimed point inside the block (0..1 per axis; picks slab halves, door hinges) |
| `SelectHotbarSlot`, `MoveInventoryItem` | C→S | slot numbers (36–44: crafting grid, 45–47: open machine input, fuel, output, or 45 onwards the open chest's slots), count |
| `QuickMoveItem` | C→S | shift-click on a slot (numbers as above) or the crafting result (−1); the server picks the target (`QcQuickMove`, E-099) |
| `ChatInput` / `ChatMessage` | C→S / S→C | text; `ChatMessage` also a translation key (English text with `%1`…, context `QcServerMessages`) and up to 16 arguments, translated by the client (E-094) |
| `InventoryState` | S→C | all 36 stacks, selected slot, crafting grid, grid size, result, the four armour slots (head, chest, legs, feet; empty until stage 23) |
| `OpenCrafting` | S→C | grid size (3 at a crafting table) |
| `TakeCraftingResult`, `CloseCrafting` | C→S | – |
| `CraftRecipe` | C→S | recipe name, count (recipe book) |
| `ConsumeItem` | C→S | – (eat the held item) |
| `EntitySpawn`, `EntityMoves`, `EntityRemove` | S→C | creatures, other players and falling blocks (`mobType` −3 with the block state) within 64 m, dropped items within 32 m (`mobType` −2 with the item stack; sent again when the count changes, moves only when the item moved); players' appearance, armour slots, view pitch, state flags (swing started, on ground, in water, sneaking, sprinting) and held item; `EntityRemove.died` for deaths; `EntityMoves` carries the server's time of its tick (players' time in ms, E-271) |

| `WorldTime` | S→C | seconds, day length, whether the time runs (game rule `daylightCycle`, E-221), speed of the time of day in server ticks per client tick (tick rate / 20, the sprint's rate / 20 during a sprint, 0 while frozen; E-249) |
| `AttackEntity`, `Respawn` | C→S | target id / – |
| `DropItem` | C→S | whole stack or one item of the selected slot |
| `SetAppearance` | C→S | new appearance (checked by `QcProfileValidation` like the one in `Hello`, re-sent to other clients) |
| `OpenMachine` | S→C | position and category of the machine the player opened; an empty category opens a chest |
| `MachineState` | S→C | input, fuel and output stack, share of fuel left and of the current item done; for a chest its 1–54 stacks |
| `CloseMachine` | both | the machine or chest screen closed (client) / was closed (server: out of reach, broken, death) |
| `PlayerFood` | S→C | food points, maximum |
| `UseEntity` | C→S | use the held item on a creature (catch a firefly with an empty bottle; E-057) |
| `SoundEvent` | S→C | sound name (at most 256 characters), position, volume (0–4), pitch (0.25–4); sent only to players within the sound's range (decision E-043) |
| `DebugSubscribe` | C→S | which debug data the client wants: flags statistics and creature goals, 0 stops it; state, not rate limited: the latest subscription counts; only operators (the local player and listed operators) are served (decision E-225, widened in stage 24) |
| `GameMode` | S→C | the receiving player's game mode (survival 0, creative 1), after `ContentSync` and with every change; the client derives the rules (`QcGameModes::rules`, E-282) |
| `CreativeItem` | C→S | slot (0–35, armour 100–103, −1 = into the inventory) and a stack from the catalogue (empty clears the slot); refused outside creative mode (E-283) |
| `PickBlock` | C→S | block position; the server selects, swaps in or (creative) adds the block's item (E-285) |
| `ServerDebug` | S→C | to operators while subscribed, at most every 10 ticks (a new subscription does not restart the pace): mean and maximum per tick phase over the latest 100 ticks, tick duration and lateness, durations of the ticks since the previous message, tick number, skipped ticks, loaded chunks, players, creatures, items, falling blocks, block updates, biome at the feet, world type, with the goals flag where creatures within 48 m are heading (at most 256) |

The TCP transport (`QcTcpTransport`) implements `QcTransport`; `QcNetworkServer` accepts connections into `QcServer::addClient` as remote clients, which log in before they play (E-252, `docs/Multiplayer.md`). Before the login a client may only send `Hello`, `LoginResponse` and `Disconnect`.

## Content

Content packs are directories with `pack.json` (`id`, `name`, `version`, `dependencies`) and the folders `blocks/`, `textures/`, `lang/`. Names are `namespace:path`; unqualified names get the pack id as namespace. Block JSON fields: `name`, `translation`, `render` (`opaque`, `cutout`, `translucent`, `invisible`), `solid`, `opaque`, `liquid`, `replaceable`, `lightOpacity` (0–15), `hardness` (seconds by hand, negative = unbreakable), `tool`, `toolLevel`, `drops` (`[{item, count, chance}]`), `crafting` (crafting table), `machine` (`category`, `speed`), `fuelSeconds`, `shape` (name of a shape, `cube`, `cross`, or an inline shape object), `states` (property → list of values, the first is the default), `light` (0–15), `support` (`none`, `below`, `attached`), `facing` (`away`, `toward`), `toggles`, `door`, `climbable`, `connects` (`group`, `to`), `container` (`slots`), `tags` (of its item), `itemTexture`, `sapling` (`feature`, `minSeconds`, `maxSeconds`, `plantOn`, `plantChance`), `flow` (`distance`, `ticks`, `dropSearch`, `infinite`, `movement`, `bucket`, `bottle` (server only, E-211), `reactions`, `sound`; liquids with the states `level` and `falling`), `contactDamage`, `washable`, `falls`, `ground`, `groundLiquid`, `growth` (`maxHeight`, `averageSeconds`), `slowsInside` (0.01–1, factor on movement inside a block that is neither solid nor liquid, E-207), `surface` (`speed`, `jump`: factors for bodies standing on the block, E-207), `hardens` (`with`, `into`: the block becomes `into` when it touches `with`, server only, E-208), `textures` (`all`, `side`, `top`, `bottom`, or per face `east`/`west`/`south`/`north`, plus named `slots` for shape parts). Procedural textures: `name`, `pattern` (`noise`, `speckle`, `planks`, `bricks`, `log_side`, `log_top`, `leaves`, `glass`, `grass_side`, `ore`, `water`, `tool`, `lump`, `pickaxe`, `axe`, `shovel`, `sword`, `stick`, `ingot`, `gem`, `sapling`, `face`, `furnace`, `torch`, `torch_item`, `ladder`, `door_lower`, `door_upper`, `trapdoor`, `chest_side`, `chest_front`, `chest_top`, `lava`, `flower`, `tall_grass`, `mushroom`, `sugar_cane`, `bottle`, `bucket`, `lantern`, `limb` and `sleeve` for the character's arms, E-096; from the block and recipe expansion `nugget`, `metal_block`, `bars`, `bookshelf`, `paper`, `book`, `bowl`, `stew`, `apple`, `leather`, `scrap`, `string`, `cobweb`, `dead_bush`, `fern`, `firefly_glass`, `barrel_side`, `barrel_top`, `stained_glass`, in `QcTextureCraftPatterns`), `primary`, `secondary` (`#RRGGBB[AA]`), `variation`, `seed`, `detail` (`grain`, `bevel` 0–1, `smooth`: how the texture is painted above 16×, E-299); PNG files in `textures/` (at most 128×128) are used as they are, scaled to the atlas tile size. Texture packs override any of these textures on the client (section Texture packs and atlas). `lang/<locale>.json` maps translation keys to text.

World generation data (server only, not sent to clients): `biomes/*.json` (`name`, `temperature`, `humidity`, `ruggedness` in 0..1 (the climate point; ruggedness counts twice and is high only along winding chains, so a biome with a high value forms mountain ranges in every climate; default 0.2), `baseHeight`, `heightVariation`, `ridges` (0..1, share of the variation from sharp crests), `overhang` (blocks; a 3D noise cuts hollows under the ground and piles blocks without gaps above it: overhanging cliffs and ledges), `terraceHeight` (flat steps with cliffs in patches, 0 = none), `steep` and `steepSlope` (surface and soil block where the ground drops at least that many blocks to a neighbour), `surface`, `subsurface`, `subsurfaceDepth`, `underwater`, `beach`, `frozenWater`, `snowLine` (ragged by ±3 blocks), `snow`, `features: [{feature, density}]`), `features/*.json` (`type` `tree`/`column`/`plant`/`pool`, `trunk` (`block` for plants and pools), `leaves`, `minHeight`, `maxHeight`, `shape` `round`/`cone`, `ground`, `nearWater`, `patchSize` (blocks; groups the feature in patches with about the same average density, 0 = evenly scattered); pools: `minY`, `maxY`, `attempts`, `chance`, `radius`, `depth`, tried in every chunk, decision E-063; `surface: true` digs the basin into dry ground under open sky after the features (lava lakes), `biomes` limits a pool to biomes), `ores/*.json` (`block`, `replaces`, `minY`, `maxY`, `veinsPerChunk`, `veinSize`; a vein is a compact clump of `veinSize` face-connected blocks inside one chunk), `worldgen/terrain.json` (`seaLevel`, `stone`, `water`, `bedrock`, `bedrockLayers` (solid bottom, thinning out over the layers above), `caves`, `caveTunnelWidth` (tunnel width varies along a tunnel between 0.45 and 1.55 times this), `caveCavernThreshold` (caverns fade out near the bedrock and towards y 50), `caveRoof` (blocks of rock kept above caves except at entrances), `caveEntrances` (share of the land where caves may open to the surface), `caveLiquid`/`caveLiquidLevel` (cave cells up to this height are filled, base game: lava up to y 10), E-087). A later pack replaces entries with the same name.

Character content (sent to clients): `models/*.json` (`name`, `bones`: `name`, `role` head/body/right_arm/left_arm/right_leg/left_leg/none, `pivot`, `boxes` with `from`, `to`, `slot`), `appearance/*.json` (`name`, `kind` outfit/hair/cape, `layers`: slot → `texture` and `tint` skin/hair/shirt/pants/none, hair `boxes`, cape `shape`); mobs may use `skeleton`, `outfit`, `cape` and `armsForward` instead of `model` boxes (E-032).

Capes (E-240, E-241): `QcFigureLook` resolves the look's cape, `QcEntityMesher` hangs it as two plates (square emblem part, bending lower part) from the top of the body bone's back, at the cape's `offset` plus `ModelLook::capeClearance` (room for armour layers). `BodyPose::capeLift`/`capeSway` turn it; `QcCapeSwing` (clientcore, GUI-free) computes them from the movement (`QcCapeDrive`) with a damped spring integrated in fixed 1/120 s steps, independent of the frame rate. `QcRenderBridge` keeps one swing per drawn figure in a `QcCapeTracker` (the local player under a reserved key), the character preview its own. Emblems are textures of the pattern `emblem` (`QcTextureEmblem`: a bitmap and a palette in the data).

Sounds (sent to clients, decisions E-040, E-042): `sounds/*.json` (`name`, `bus` `effects`/`ambient`/`music`, `volume` 0–1, `pitchVariation` 0–0.5, `variants` 1–8, `loop`, `range` 1–128 m, `layers`: 1–8 of `wave` `sine`/`square`/`triangle`/`saw`/`noise`/`crackle`, `frequency`, `endFrequency`, `start`, `duration`, `attack`, `curve`, `gain`, `lowpass`, `highpass`, `tremoloRate`, `tremoloDepth`, `density`). Blocks have a sound material (`sound`, default from tool, shape and render layer) and optional `sounds` per action (`break`, `place`, `step`, `hit`); the sound of an action is `<namespace>:block.<material>.<action>` (`QcSoundKeys`). Mobs have `sounds` (`ambient`, `hurt`, `death`), machines a `sound`. Names nothing defines are reported when loading and are silent at run time.

Runtime block ids are block states, assigned in registration order and never stored; persistent data uses names (decisions E-045, E-046).

Shapes and states (E-045, E-046): `shapes/*.json` (`name`, `parts` with `when` conditions on state values, `boxes`/`crosses` as `[x0, y0, z0, x1, y1, z1]` in block metres, optional `collision` boxes up to 1.5 m high, a texture `slot`, `uv` `cell`/`box`; `rotate` names a facing property, `flip` a property whose value `top` mirrors the shape). `QcBlockStateTable` derives for every state its boxes, collision, full faces, face texture turn and whether it is a full opaque cube; mesher, physics, raycast and selection use the same boxes. Every combination of a block's property values is a runtime id (at most 1024 per block); a block's name resolves to its default state.

Building parts (E-048): `parts/*.json` describe families (`name`, `kinds`, `suffix`, `block` template, `hardness` and `fuel` factors, `recipe` with `@` for the base, `translations` with `%1` for the material's name), `materials/*.json` materials (`name`, `block`, `kind`, `exclude` families, `translation`) or exclusion entries (`excluded`, `blocks`). `QcContentRegistry::finish()` runs `QcPartGenerator` after all packs and then creates block items. Recipes accept item tags (`#qtcraft:planks`, `items/*.json` field `tags`, block field `tags`).

Handbook content (server side, not synchronised): optional `description` translation keys on blocks, items, mobs and biomes (default `<translation>.description`), `handbook/*.json` chapters (`name`, `order`, `icon`, `sections`, `related`; texts from `chapter.<ns>.<name>[.<section>.title|.text]`), labels as `handbook.*` translations. Language files may be split: `lang/<language>.handbook.json` adds to `<language>` (only this suffix is removed).

Mods are content packs in the mods directory (`<data root>/mods`, `--mods-dir`); `QcModLoader` loads the base game first and then every mod after its dependencies, skipping broken ones. The base game goes through exactly the same loader. Details, the boundary between core and mods and the file formats are in `docs/Modding.md`; open security questions in `docs/Mod-Sicherheit.md`.

## Game modes

The game mode is a server state per player (E-282): `QcGameMode` and its rules (`QcGameModes::rules`) live in `qc_common`, so the server (`QcServerGameModes`, `QcServerClient::gameMode`) and the client (`QcClientGameMode`, mirrored from `GameMode`) apply the same table. Flight is part of the shared physics (`QcPhysics::stepPlayer` with `mayFly`; the wish to fly travels with every numbered input, E-284), so prediction and server agree. Creative rules are checked where the action happens: instant breaking in `QcServerInteraction::finishMining`, endless placing in `applyPlacement` and `QcServerStands`, invulnerability in `QcServerCombat::damagePlayer` and the creatures' targets, frozen hunger in `QcHunger`. Survival and creative keep separate inventories (`keptInventory`, E-283). The creative inventory is `QcCreativeCatalog` (`qc_common`, tabs and search), `QcCreativeItemModel` and `CreativeScreen.qml` (E-286); pick block is `PickBlock` (E-285).

## Persistence

A saved world is a directory below `<app data>/worlds/<folder>` (`QTCRAFT_DATA_DIR` overrides the base; `QcWorldLibrary` lists, creates and deletes worlds). `QcWorldStorage` reads and writes:

| File | Content |
|------|---------|
| `world.json` | `formatVersion` (2; format 1 loads as a set-up terrain world), `name`, `seed` (string, 64-bit), `created`, `lastPlayed`, `worldTime`, `defaultGameMode` (`survival` or `creative`, the mode of new players, E-282; missing: survival), `packs` (`id`, `name`, `version` of the base game and mods in use), `generator` (`type`: `terrain`, `flat`, `void` or `showcase`, `options`: the layers of a flat world or the platform of a void world, resolved when the world is created, `setupDone`: the generator's one-time setup ran, E-221, E-223), `gameRules` (`keepInventory`, `daylightCycle`, `mobSpawning`) |
| `regions/r.<rx>.<rz>.qcr` | Modified chunks of a 32 × 32 chunk region: palette of block state names (`name[property=value,...]`, format 2; format 1 has plain names, which load as default states) + chunks (palette sections, run-length indices) |
| `players/<name>-<hash>.qcp` | Position, velocity, view direction, health, selected slot, inventory (item names, counts, damage), food points and exhaustion, armour slots (format 3, E-234; format 2 files load without armour, format 1 files with full food), game mode, flight and the kept inventory and armour of the other mode (format 4, `QcPlayerStorage`, E-283; older files load as survival) |
| `stands.qce` | Armour stands: position, yaw, pose, name, the item they drop, held item, armour and cape (items and cape by name; E-238, E-239; version 2, version 1 loads without capes). Worlds without the file have no stands |
| `mobs.qce` | Persistent animals (kind name, position, yaw, health) and the chunks that already got their animals (E-086) |
| `entities.qce` | Dropped items (name, count, damage, position, velocity, age, pickup delay; waiting drops included), growing saplings (position, seconds left) and falling blocks (state name, position, velocity, age; format 2, format 1 files load without them) |
| `machines.qce` | Machines (position, input, fuel and output stack by item name, fuel left and its full time, progress) |
| `containers.qce` | Chests (position, slot count 1..54, stacks by item name); missing in older worlds |
| `blockupdates.qce` | Pending neighbour updates and planned flow steps of liquids (positions); absent when none are pending |
| `access.json` | Operators, banned names (reason, by whom, since when) and the whitelist (on/off, names), written at once with every change; a damaged file is kept aside as `access.json.damaged` and the world opens with a switched-on, empty whitelist (E-244) |

Player files are named after the player in lower case plus a hash of the exact name, so names differing only in case keep separate files; files of older versions (`players/<name>.qcp`) are renamed when that exact name joins (E-093). While a server has the world open it holds `session.lock` (`QLockFile`); a second window or process cannot open the world (E-093).

When a world is opened with a different set of packs than it was saved with, the server logs a warning per missing or changed pack (`QcServer::openWarnings()`); blocks of a missing mod load as air and its items are dropped from inventories.

Binary files share a container: magic (`QCRG`/`QCPL`/`QCEN`/`QCMA`/`QCCO`/`QCBU`), format version (per file type; older versions stay readable), payload size, CRC-32, payload. Loading validates every part; a damaged file stops the world from opening with a message naming the file. Unknown block or item names (e.g. after removing a mod) become air or are dropped, with a warning; unknown state properties or values keep their defaults, also with a warning. Block light is not stored; it follows from the blocks (E-049). Only modified chunks are stored; they stay in memory while the world is open and their regions are rewritten (atomically via `QSaveFile`) on `/save`, every 60 s and when the server stops. Everything else is regenerated from the seed.

## Interaction

The client sends intentions; the server decides (`QcServer`):

- **Limits for every action:** spammable messages pay into per-player token buckets (`QcRateLimiter`, E-091; over the limit they are dropped and logged, nobody is kicked; the local player of the in-process host is exempt from the chat bucket only). Mining, using, placing, scooping, attacking and catching need reach and a line of sight from the eye (now or before the last input) to a point of the target, with the client's raycast (`QcLineOfSight`, E-092).

- **Mining:** `StartMining`/`CancelMining`/`FinishMining`. The server checks reach (5 m + 1 m slack), the target and the elapsed ticks against `QcMining::breakSeconds` (hardness × 1.5 s, divided by the tool speed with the right tool; × 5 s without a required tool, which also gives no drops). Drops (each with its `chance`) fall into the world as item entities (E-028); tools lose durability; a double slab drops two slabs, the upper half of a door nothing.
- **Placing:** `UseItem` on a block face places the held item's block into the neighbouring cell if it is replaceable, within reach and no player is inside its collision boxes. `QcBlockRules::placement` derives the state (E-046): `facing` from the player's view (`away` or `toward` the player), `half`/`type` from the clicked face or the height of the aimed point, `attach` towards the clicked block (`floor`, `ceiling`, a side; values the block does not list refuse the placement), connections from the neighbours; a slab clicked on its open half becomes a double slab in place; doors need two free cells and take their hinge from the aimed side. Saplings need one of their `plantOn` blocks below.
- **Neighbour updates** (E-047): every block change queues the changed position (unless it became air) and its six neighbours; updates caused by players go into their own queue, which goes first; commands and their cascades use what is left of the budget. Each tick the server works through at most 1024 of them, re-deriving connection properties (fences, walls, panes to their group and full solid blocks; walls show a post except in straight runs) and breaking blocks without support (`below`: full solid top below; `attached`: full solid face on the attach side; doors: the other half) with their drops. A block with `hardens` that finds its `with` block on one of its sides turns into `into` before it could fall (`QcBlockSimulation::processUpdate`, E-208), and a falling one that lands in a `with` cell turns into `into` there (`QcBlockSimulation::landBlock`, E-217); chunks that load re-check such blocks on their borders. Updates only change states derived from neighbour types, so they settle after one pass; the budget bounds the work per tick. Sides towards unloaded chunks keep their state and supports there count as present; updates for unloaded positions wait for their chunk (at most 65,536), and a chunk that loads re-checks the connecting and wall-mounted blocks on its borders and those of its loaded neighbours. Pending updates are saved in `blockupdates.qce`. A door half breaks its partner with the same drop decision; a half without partner breaks without drops. Doors, trapdoors and gates do not toggle onto a player or mob, and no block is placed into one.
- **Doors, trapdoors, gates and ladders:** using a block with `toggles` (not sneaking) flips `open`, for doors on both halves; open gates have no collision. Climbable blocks (ladders) let bodies climb at 2.4 m/s while pushing into the wall or jumping, slide down at most 2 m/s and hold while sneaking (`QcPhysics`, also for client prediction); falls end on ladders.
- **Movement in and on blocks** (E-207): `QcPhysics::stepEntity` (server and client prediction) multiplies the wished horizontal speed by the liquid's `movement`, the smallest `slowsInside` of the cells the body overlaps (cobweb 0.25) and, on the ground, the `surface.speed` of the block under the centre of the feet (mud 0.6); inside a slowing block the vertical speed is scaled by the same factor (slow sinking, no fall damage), and a jump starts with `surface.jump` times the normal jump speed (mud 0.93).
- **Chests** (`QcContainerManager`, E-050): using a block with `container` opens its slots like a machine screen (`OpenMachine` with empty category, slots 45 onwards); contents are kept per position, saved in `containers.qce`, at most 16384 chests; breaking or replacing the block drops the contents; a storage block of another size keeps what fits and drops the rest. When a world opens, chests whose block is no storage block any more (a removed mod) are removed and their contents dropped.
- **Dropped items** (`QcItemEntityManager`, E-028): physics through `QcPhysics::stepEntity` with weak air drag, floating in water, resting items skipped until their ground changes; merging of equal stacks within 1 m every 10 ticks; pickup when touching a living player after 0.5 s (thrown: 2 s), partial when the inventory is full; ageing only in loaded chunks, despawn after 300 s; at most 512 awake items (when a chunk loads with more, the youngest sleep in place: frozen, not sent, same id, woken oldest first), a bounded queue for further drops that appear only in loaded chunks, 4096 items in the world; stacks above `maxStack` are split; moves are sent once an item is 2 cm from its last sent position. `DropItem` (key Q, Ctrl+Q for the stack) throws items from the eyes along the view direction. On death without `keepInventory` (E-029) inventory and grid scatter as items.
- **Plants** (`QcPlantManager`, E-030, E-031): leaves of tree features decay a few at a time once no trunk is within four blocks (checked after a trunk is removed); saplings grow into their feature after a random time while loaded, using the generator's tree shapes (`QcTreeShape`); a despawning sapling item plants itself with its `plantChance`. Blocks with `growth` (sugar cane) grow upwards on random ticks (`QcPlantGrowth`, E-102): every tick picks three random blocks in each loaded section whose palette holds such a plant; a ticked top block grows by one with the chance `68 s / averageSeconds` while the column is below `maxHeight` and its base keeps its ground.
- **Farming** (stage 27, E-289 to E-295): the same random ticks drive crops and soil (`QcCropGrowth`, called by `QcPlantGrowth` for blocks with `crop` or `soil`; the section marks count every block with `QcBlockDefinition::hasRandomTicks`). A crop advances a stage of its `age` property with the chance `68 s / (averageSeconds / steps)`, halved on dry soil, only in light 9 or more (block light, sky light estimated down the column); a ripe stem puts its fruit on a free neighbour. Farmland turns wet with water within 4 blocks, dries without it and reverts to dirt when dry and bare or covered. Block drops can carry `when` conditions (harvest only when ripe). `QcServerFarming` tills with items that `tills` (hoes; wear except in creative mode), feeds animals and spawns the young ones of `QcMobBreeding` (timers `love`, `breedCooldown`, `growUp` in `QcMobManager::Mob`, saved in `mobs.qce` format 2). `QcServerItemsAndPlants::plantSeeds` lets resting seed items on free soil plant one of their stack once a second with the crop's `plantChance`. A seed stack whose own cell is taken plants the free soil in the 3 × 3 ring around it, one seed per check. Items in flowing liquid drift along its current (`QcLiquidFlow::current`, E-296). Food that plants (carrots, potatoes) is eaten where it cannot be planted; the client sends `UseEntity` only for food, armour and what the creature takes (catching item, breeding food, which the content sync carries, protocol 29), other items act on the block behind it. Animals in love walk towards each other, breed only in sight of each other and get their young at a parent's feet, within caps per 3 × 3 chunks and per world (`QcMobBreeding`). The game rule `randomTicks` stops all random ticks (off in the showcase world). Growth runs only in loaded chunks, nothing is made up later.
- **Inventory:** 36 slots (9 hotbar). The server sends the full `InventoryState` after every change; `MoveInventoryItem` merges or swaps stacks.
- **Chat and commands:** `ChatInput`/`ChatMessage`; plain lines go to everyone, lines with `/` run a command (decisions E-243 to E-249). `QcServerCommands` checks the source's rights (`QcPermission`: player, operator, console; the local player is always an operator, `QcServerState::permissionOf`), logs the call (`qtcraft.commands`) and runs the `QcCommandSpec` from `QcCommandRegistry` or a macro of the content (`commands/*.json`, E-248). Command groups: `QcCheatCommands` (give, spawnitem, summon, equip, armorstand, kill, heal, feed, time, gamerule, gamemode, locatebiome), `QcBlockCommands` (setblock, fill with `replace`, clear, regenerate via `QcChunkRegeneration`), `QcPlayerCommands` (list, kick, ban, unban, banlist, whitelist, op, deop, tp; lists in `QcAccessList`, `access.json`), `QcWorldCommands` (save, backup via `QcWorldBackup`, worldinfo, remove, stop), `QcTickCommands` (tick: freeze, step, rate, sprint, query; `QcTickControl`, `QcTickScheduler`). Destructive commands wait in `QcPendingCommands` for `/confirm` (30 s of real time; the confirming source needs the command's rights). The server console (`QcServer::runConsoleCommand`, `QcLocalServerHost::runConsoleCommand`, `qtcraft-headless --console`, control command `console`) uses the same layer with all rights and no position.
- **Eating and hunger** (`QcHunger`, E-039): `ConsumeItem` eats one of the held item if it has `food` and the player is not full; the item's `food` points are added (at most 20). Walking, sprinting, swimming, jumping, mining, attacking and taking damage add exhaustion (rates in `QcHunger`, E-100: a full bar lasts about 124 min of walking or 8 min of sprinting); every 4 points cost one food point. At 18 food or more the player heals one point every 4 s (2 exhaustion each); at 0 food they lose one point every 4 s down to 1. Respawning refills the food. Using a machine or crafting table opens it even with food in hand.
- **Machines** (`QcMachineManager`, E-037, E-038): using a block with `machine` opens it (sneaking places against it) within 5 m + 1 m slack; the server closes it when the player dies, walks away or the block goes. Slots 45–47 of `MoveInventoryItem` are the open machine's input, fuel (fuel only) and output (take only). A machine lights one fuel item when its input has a recipe of its category and the result fits; burning and progress run at the machine's `speed`, without fuel the progress falls back twice as fast. Only machines in loaded chunks tick, at most 4096 exist; breaking or replacing the block drops the contents as items.

Every visible, non-liquid block automatically gets an item of the same name that places it (`QcContentRegistry::createBlockItems`); `items/*.json` defines further items (`name`, `translation`, `texture`, `maxStack`, `places`, `tool`, `toolLevel`, `toolSpeed`, `durability`, `attackDamage`, `food` in food points, `fuelSeconds`, `emptiesTo` (left in the hand when eaten or poured, in the fuel slot when burnt, E-212), `armour` (`slot`, `points`, `set`, `layers`, `parts`; see Modding, E-234/E-235), `placesStand` (places an armour stand, E-238), `scoops` (takes a liquid source that has `flow.bucket`), `bottles` (fills from a liquid that has `flow.bottle` and leaves the liquid, E-211; an item cannot have both)); block items inherit the block's `fuelSeconds`.

UI controls: F1 opens the handbook (at the block or creature in view), left mouse mines or attacks, F mines, right mouse / R places, eats or opens a crafting table or furnace, Q throws one item (Ctrl+Q the stack), 1–9 and the wheel select the hotbar slot, E opens the inventory, T or Enter the chat, Esc the pause menu (save, quit to menu).

## Crafting

- **Recipes** come from `recipes/*.json`: `name`, `type` (`shaped`, the default, or `shapeless`), for shaped recipes `pattern` (up to 3 strings of up to 3 characters, space = empty) and `key` (one character → item), for shapeless ones `ingredients` (1–9 item names), and `result` (`item`, `count`). Patterns are trimmed to their bounding box when parsed. `QcCrafting` (shared by server and client) matches a square grid against all recipes: shaped recipes at any offset and mirrored horizontally, shapeless ones as a multiset. A recipe needs a 3 × 3 grid if its shape or ingredient count does not fit 2 × 2.
- **Grid:** the inventory screen has a 2 × 2 grid; using a block with `"crafting": true` (crafting table) opens 3 × 3 as long as the player stays within 5 m. Grid cells are slots 36–44 (three per row) and live on the server; `MoveInventoryItem` moves, splits and merges between inventory and grid. `TakeCraftingResult` consumes one item per used cell and adds the result if it fits. `CloseCrafting` puts the grid back into the inventory; what does not fit is thrown on the ground (also when the player disconnects).
- **Recipe book:** `CraftRecipe` crafts directly from the inventory, round by round, each round all-or-nothing on a copy of the inventory. 3 × 3 recipes need a crafting table within 5 m. The inventory screen lists the recipes that can be made now; the control interface offers `recipes` and `craft`.
- **Base recipes:** planks from each log (oak, birch, spruce), sticks, crafting table, chest, door, trapdoor and wooden tools from any planks (tag `planks`), torches from a stick and coal or charcoal (tag `coals`), ladder, glass pane, furnace (8 cobblestone), stone/iron/diamond tools, sandstone, and the recipes of the building parts (stairs 6 → 4, slab 3 → 6, wall 6 → 6, fence 4 + 2 sticks → 3, fence gate 2 + 4 sticks → 1).
- **Smelting** (E-037): `smelting/*.json` (`name`, `category` default `smelting`, `input`, `result` with `item`/`count`, `seconds` default 10). Base recipes in the furnace: iron and gold ore to ingots, sand to glass, clay to bricks, cobblestone to stone, logs to charcoal, raw to cooked porkchop. Fuel: coal and charcoal 80 s, logs, planks and crafting tables 15 s, wooden tools 10 s, sticks and saplings 5 s. The furnace screen (`FurnaceScreen.qml`) shows the three slots, a flame for the fuel left and an arrow for the progress.

## Creatures, health and time

- **Mobs** come from `mobs/*.json`: `name`, `translation`, `health`, `width`, `height`, `walkSpeed`, `chaseSpeed`, `hostile`, `attackDamage`, `attackRange`, `attackCooldown`, `sightRange`, `spawn` (`time` `day`/`night`/`any`, `blocks`, `maxGroup` 1–4, `weight`, `caves`; night creatures spawned in caves stay by day), `model` (boxes `from`/`to` in metres around the feet, facing north, with a `texture`) and `drops`; further `spawn.ambient`, `spawn.maxCount`, `spawn.biomes`, `spawn.chunkChance`, `spawn.maxY`, `spawn.also` (up to 8 extra rules with their own `time`, `blocks`, `weight`, `caves`, `maxLight`, `chunkChance`, `maxY` and `biomes`; group size and caps stay shared), `flying`, `glow` and `catch` (E-057). Base mobs: zombie (hostile, night and caves), slime (hostile, caves in slime chunks below y 40, and at night on swamp surfaces up to y 70), pig and sheep (passive, persistent), firefly (ambient, flying and glowing, night, swamps, catchable with a glass bottle).
- **Server** (`QcMobManager`): every second up to four spawn attempts per player in a ring of 20–48 m, on the surface (by time of day) or on cave floors at least 8 blocks below the surface; caps of 8 hostile, 6 passive and 10 ambient mobs per player (plus `maxCount` per kind); biomes come from the generator (`QcWorldGenerator::biomeAt`). Behaviour per tick: hostile mobs chase the nearest player in sight and strike in range with a cooldown; passive mobs wander and flee when hurt; jumping over one-block steps; swimming. Hostile and ambient mobs despawn beyond 96 m, night mobs by day once nobody is near; they are not saved. Peaceful animals are persistent (E-086): 10 % of the chunks seen for the first time get a group, they never despawn, rest (`dormant`: not ticked, sent or counted) while their chunk is not loaded and are saved in `mobs.qce` with the set of populated chunks; natural animal spawns happen only while no awake animal is within 128 m. `spawn.chunkChance` limits a kind to a seed-chosen share of chunks (slime chunks), `spawn.maxY` caps the spawn height. No mob spawns on a block with `contactDamage` (magma) or with its feet or head in a block with `slowsInside` (cobwebs), whatever its `blocks` list; the block fields decide, not names.
- **Combat:** `AttackEntity` (reach 4 m plus the target's size, 0.4 s cooldown, damage from the held item's `attackDamage`, 1 by hand), 0.5 s invulnerability after a hit, knock-back both ways. Loot falls where the mob died.
- **Contact damage:** `contactDamage` hurts players and mobs whose body touches such a block and, for solid blocks, those standing on it: the block under the centre of the feet counts, a liquid beside it does not (magma, `QcServerCombat`, E-209).
- **Health:** 20 points; fall damage of one point per metre beyond 3 m; regeneration of one point every 4 s while food is at least 18 (see Eating and hunger); death shows a screen and waits for `Respawn` (back to the spawn point with full health; the inventory is kept or dropped depending on `keepInventory`). Health is saved with the player.
- **Time:** a day lasts 600 s (`QcDayCycle`); the server keeps `worldTime` (saved in `world.json`) and sends `WorldTime` every second; the client advances it between updates and derives sky colour, fog and the daylight factor of the block shader.
- **Client:** `QcClientSession` mirrors entities (`EntitySpawn`/`EntityMoves`/`EntityRemove`, interpolated between ticks) and finds the creature under the crosshair; `QcEntityMesher` turns the boxes into triangles every frame and draws dropped items as small spinning, bobbing cubes (cube blocks) or crossed sprites (other items), up to three copies for larger stacks; the HUD shows hearts, the food bar and the time of day.

## Sound and music

- **Synthesis** (E-040): `QcSoundSynthesizer` renders a definition and a variant into mono float PCM (44.1 kHz by default, the output device's rate in the game): per layer a tone (with exponential sweep), white noise or sparse crackle, two one-pole low-pass stages, a one-pole high-pass, linear attack, decay `(1 - t)^curve`, tremolo and a 3 ms fade at the end. The result is normalised to a peak of 0.9; loops blend their tail into their head (equal power, a quarter of the length, at most 0.3 s). Noise comes from a seed derived from the sound's name and the variant, so renderings are deterministic. `QcSoundBank` renders all sounds of the content on a worker thread within a budget of 16 Mi samples (64 MiB); sounds beyond it stay silent with a warning.
- **Mixing** (E-041): `QcAudioMixer` plays voices (buffer, gain, constant-power pan, pitch with linear interpolation, loop, bus) on the buses effects, ambient and music under a master volume and mute; at most 32 voices, a new sound replaces the quietest voice that does not loop; gain changes ramp over one mix block; a soft limiter (above 0.75, tanh) keeps the sum below full scale. `QcAudioOutput` opens the default device (float stereo, else 16 bit) with an 80 ms buffer; without a device or when it fails, the game stays silent and logs the reason once.
- **Events** (E-043): the server sends `SoundEvent` for broken and placed blocks, creature ambience (on average every 10 s per creature), hurt and death of creatures and players, eating, picking up items and burning machines (on average every 2.5 s). The client computes the gain `(1 - d / range)^2` with `range` = the sound's range × max(1, volume), damps sounds behind the listener by up to 25 % and pans them by the side (`QcSoundSpatial`, at most 85 % to one side). Client-side cues (`QcLocalSounds`, `QcClientSession`): own steps every 1.7 m on the block below, jumps, landings (louder above 6 m/s), splashes (entering water faster than 3 m/s), swimming strokes every 2.2 m, mining strikes every 4 ticks, steps of other creatures from their movement; UI clicks on buttons come from the controller. `QcClientSession::recentSounds()` keeps the last 64 cues for the control interface.
- **Ambience and music** (E-044): `QcAmbience` derives levels for wind (open sky, rising from 0.3 at y 64 to 1 at y 120, muffled under a thin roof), cave (at least 4 opaque blocks within 24 above the head) and water (water blocks in a sampled box of radius 6) every 10 ticks and fades them by 0.5 per second; the three loops play on the ambient bus. `QcMusicComposer` composes a piece per seed on a major or minor pentatonic scale (66–90 bpm, motifs A A' B A, bass per bar, held chords, closing bar on the root, about 30 s); the engine renders it on a worker thread and plays pieces with pauses of 60–180 s while a world is open.

## Keys and screens

Keys (decision E-077): `QcKeyBindings` (`qc_common`, GUI-free) is the table of actions (walk, jump, sneak, sprint, look, mine, use, drop, inventory, chat, command, camera view, handbook, debug display, debug options, labels, hotbar 1–9, pause) with a primary and a secondary `Qt::Key` each, portable key names (`V`, `F5`, `Space`, `/`) and conflict handling (binding a used key swaps it with the slot's old key) and platform defaults (`Platform::Mac`: sprint Option, no Cmd or Control, Cmd not bindable, whole stack with Control). `QcGameSettings` stores it as `keys/<action>` and `keys/<action>.2` in `settings.ini`; unknown names fall back to the default, keys an earlier action already uses are dropped, Esc (pause) is fixed. `QcKeyControls` (`qc_clientcore`, QML name via `QcKeyControlsForeign`) exposes it to QML as `GameController.keys` (rows for the controls page, labels of the primary keys for hints, `matches()`, `bind()`, `reset()`), `QcKeyLabels` gives translated key and action names (Cmd/Control/Option on macOS). In the world `QcGameController::handleWorldKey` maps every key event through the table and takes all of them, so nothing below the world reacts; movement keys count while held. The controller filters application events, so it also accepts the `ShortcutOverride` of every bound key (Qt sends it to the focused item). The handbook fills `{key.<action>}` (all keys), `{key1.<action>}` (primary key) and `{key.stackModifier}` from the same table: the export with the Windows/Linux defaults (platform-neutral), the game with the player's keys and the platform's key names.

Colours (E-097): every screen takes its colours from `Theme` (`QcUiTheme`, the palette `QcUiPalette`); HUD texts lie on a dark semi-transparent backdrop (`HudLabel.qml`). `test_ui_palette` checks every text/background pair of the palette over seven world backgrounds (snow, sand, sky, water, grass, night, cave) against WCAG 4.5:1 (3:1 for large text) and that no QML file has colours of its own. Slot screens (E-099): `SlotScreen.qml` with `InventorySlot.qml` and `PlayerSlots.qml` is the base of the inventory, chest and furnace screens: the picked-up stack follows the mouse, its slot is dimmed, shift-click sends `QuickMoveItem`, slot clicks sound like buttons. Mouse capture (E-098): `QcMouseCapture` captures the mouse again whenever the input steps back from a screen into the world; the release of a button held at that moment does nothing.

Screens (E-078): overlays are QML items over the world (`GameController.overlay`); the pause and main menus own their sub-screens (settings with the pages General and Controls, character, mods, delete dialog) as popups and close them when the menu is hidden or the overlay changes, so no popup outlives its menu (closing stores the settings). Esc closes the topmost popup first (the popup's own Esc handling), then the menu; a closed popup gives the keyboard back to its menu. Every screen takes the keys it does not use (Tab still moves the focus); text fields keep typed letters, so a letter handbook key in the handbook search types instead of closing.

## Handbook

`QcHandbookBuilder::build(registry, language, rules)` (`qc_common`, decision E-064) turns a complete registry into a `QcHandbook`: twelve categories (playing, blocks, building parts, liquids, items, tools and weapons, food, creatures, biomes, world generation, item groups, overviews), entries with id (`block:<name>`, `item:`, `mob:`, `biome:`, `ore:`, `feature:`, `tag:`, `chapter:`, `world:terrain`, `table:fuels|tools|smelting`), title (and English title for search), icon item, description, facts and sections with links and recipes. Facts are computed with the shared rules (`QcMining` break times, tool levels, drops, light, support, flow, machine and fuel times, spawn rules with the caps from `QcHandbookRules`). Cross references come from reverse indices built once: recipes by result and ingredient (tags expanded), smelting by input and result, drops of blocks and mobs, biome layers, features, ores and pools, spawn blocks, catches, building parts by base. Entries are sorted by pack (namespace of the name, packs in load order, unknown namespaces after them) and title; links are checked at the end (`problems()`). Labels and texts come from the registry's translations, so the same code serves the game and the export (E-065). `QcHandbook::search` matches all words against titles (language and English), names and texts, without case and accents.

- **Export** (E-066): `QcHandbookMarkdown::files` gives `index.md` and one file per category, entries as `### <a id="block-qtcraft-stone"></a>…` with relative links; byte-identical for the same content. `docs/handbook/` (English) and `docs/handbook/de/` are the base game's handbook; `test_handbook` fails when they differ from a fresh export.
- **Game** (E-067): `QcGameController` builds the handbook on first use from the full content of the world (or, in the menu, the content it loads for the character screen and menu sounds) and again after a content or language change; in the menu it also draws the item icons from that content. `QcHandbookModel` gives QML the categories, entry lists (with pack headings when mods are loaded), search results and pages (`QcHandbookJson`, converted per page). `HandbookScreen.qml` lies above every other screen and keeps the screen below open; it opens with the handbook key (H or F1 by default; in the world at the target, in inventory, furnace and chest at the hovered item), from the main and pause menus and with the "?" on a hovered slot.
- **Control interface:** `handbook` in `qtcraft-headless` (see `docs/Steuerschnittstelle.md`).

## World generation

`QcTerrainGenerator` (decision E-014) is deterministic per seed and thread-safe. The climate (temperature, humidity, ruggedness) is read at coordinates bent twice: the large warp shared with the coasts (420 blocks, ±140) and a smaller one only for the climate (160 blocks, ±200), which frays biome borders; mountains cover about a quarter of the land (E-085, E-101). Players spawn on natural ground of the stored world near the generator's spawn point (E-101). Features and ores take their seeds from their names (`qcNameSalt`, FNV-1a, plus a fixed offset per purpose, E-214), so new content does not move the trees and ores of others; ores may replace cave air (cobwebs, E-216). The server generates chunks on a `QcWorkerPool` (`QcServerWorld::requestChunk`), nearest first with a bounded queue, and collects finished chunks every tick; chunks no player needs are unloaded. Sky light is computed client-side while meshing, block light incrementally on the client's light thread (decisions E-015, E-049).

World types (E-221, E-223): `terrain` (`QcTerrainGenerator`), `flat` (`QcFlatGenerator`: the same layers everywhere, from `worldgen/flat.json` or the world's own layer list), `void` (`QcVoidGenerator`: air but a platform at the spawn, `worldgen/void.json`) and `showcase`; `QcWorldGenerators::create` builds the generator of a world's type and options.

Showcase world (stage 21, decisions E-219 to E-222): generator type `showcase` (`QcShowcaseGenerator`), chosen when a world is created and stored in `world.json`; `QcWorldGenerators::create` builds the generator of a type. `QcShowcasePlanner` lays out a `QcShowcasePlan` once per content: flat ground from `worldgen/showcase.json`, then in rows north of the spawn the demo structures (`structures/*.json` with `showcase`), the trees, an enclosure per creature, a podium area per block category with every state of every block, and every item in chests, each with a title and a lookout (tour stop). The plan holds `QcStructurePlacement`s indexed by chunk; `generate()` writes the ground and the placements of a chunk. Labels come per chunk (`labelsIn`, sent as `ChunkLabels`); the one-time setup (`setup()`: noon standing still, no natural spawning, creatures, chest and furnace contents, block updates, growing saplings) is applied by `QcServerSetup` when the world opens for the first time. Structures are general: a palette of block states and layers of palette keys, placed in quarter turns with turned states (QcStateRotation), chunk by chunk and thread-safe, so villages (stage 30) can use them. On the client `QcLabelProjector` picks the labels to draw each frame (reach, view, not behind an opaque block) and `QcWorldLabelModel` hands them to `WorldLabels.qml`.

Graphical game: `QcFrameMonitor` collects frame statistics only as deep as needed and hands render samples to the benchmark; `QcDebugHud` (`GameController.hud.debug`; the frame phases include the character previews' meshing, E-231) updates text, graphs (`QcGraphItem`, QML `DebugGraph`) and light labels four times a second and keeps the server subscription in step with the settings (`QcDebugSettings`, `QcDebugOptions`: `debug/level`, `debug/<option>`); `QcDebugVisuals` builds `QcDebugLines` per frame while a visualisation is on, `QcDebugLineRenderer` draws them (`debugline.{vert,frag}`). QML: `DebugOverlay.qml`, `DebugOptionsPage.qml` (settings page "Debug", overlay `debug`).

## Rendering

Sky (E-095): `QcSky::at(worldTime)` gives the colours of zenith and horizon, the sunrise and sunset glow, sun and moon directions, the moon phase, star visibility and cloud drift; `QcSkyRenderer` draws it first as one screen-filling triangle (`sky.{vert,frag}`, no vertex buffer, no depth test) with sun disc, lit-sphere moon, turning stars and noise clouds on a layer at 160 m. Fog takes the horizon colour.

`QcWorldView` is a `QQuickRhiItem`. GUI-thread setters (camera, atlas, mesh submissions) are copied to the render thread in `QcWorldRenderer::synchronize()`. Meshes are immutable `std::shared_ptr<const QcChunkMesh>` snapshots. Vertex format: position (world space, float), atlas UV, shade (face shading × ambient occlusion), sky light, block light; the shaders take the brighter of sky light × daylight and a warm-tinted block light. Cross-shaped blocks become two double-sided diagonal quads.

Block light (E-049): `QcBlockLightEngine` keeps the light of all loaded chunks (each step costs max(1, opacity), opacity 15 stops it, unloaded chunks are dark walls). Partial shapes of light-dimming blocks (stairs, slabs) have opacity 0 and stop light only at the faces they cover completely (`QcBlockState::lightBlockedFaces`, `QcLightPassage`, E-104); block light, sky light in the mesher and the sky column used for remeshing all follow that rule. A loaded chunk floods its sources and the light over its borders; a block whose light level or opacity changes clears the light that depended on it breadth-first and refills the cleared cells from their lit boundary and from sources; an unloaded chunk takes its light along. The engine runs on its own thread in `QcMeshScheduler`; results are immutable section snapshots (`QcChunkLight`) that the mesher reads instead of flooding (`QcMeshInput::blockLight`). A chunk is meshed once its light is known; a block change marks the sections next to the block, the sky-light column only when the opacity changed, and the sections whose light changed (plus neighbours of changed border cells); changes with light work are meshed together with their new light. `QcLightVolume` floods a volume in one go: the server uses it on demand for spawning, the mesher without light snapshots, and the tests as the reference the engine must match. Partial shapes (`QcBlockRenderTable` quads per state): faces on the cell border are hidden when a neighbour's faces on that side cover them (any opaque state, or the same translucent block), interpolate corner light and ambient occlusion of the full face, faces inside the cell take the light of the open space in front; faces lying on another box of the same state are left out. Entities and the hand read the engine's light at their position; items whose block gives off light are drawn at least that bright (`ItemLook::glow`); the server computes exact block light on demand for spawning (hostile mobs need at most 7 by default, `spawn.maxLight`). Inventory icons of blocks are drawn from their boxes (`QcBlockIcon`). Entities and the first-person hand use their own vertex format with a tint colour and the shaders `entity.{vert,frag}`; the hand is drawn last with `hand.vert`, which squeezes its depth to the front (E-034). Skeleton models are meshed every frame by `QcEntityMesher` from `QcAnimator` poses (E-033); the camera mode and its wall collision come from `QcViewCamera` (E-035). Block pipelines: opaque with alpha test, translucent (blended, no depth write, sorted back to front per section). Shaders: `src/app/shaders/block.{vert,frag}` (GLSL 440, compiled for all RHI backends by `qt_add_shaders`); the opaque pipeline uses the variant `block_opaque.frag.qsb` (`block.frag` baked again with `QC_OPAQUE`), which writes alpha 1, and `entity.frag` writes alpha 1 too: both pipelines draw without blending, and the partial alpha of the mip levels must not reach the target (screenshots, transparent targets such as the character previews; a colour write mask without alpha did the same but cost GPU time; E-332).

## Texture packs and atlas

Decisions E-297 to E-304 (stage 28), author guide `docs/Texturpakete.md`. Client side only; the content (and with it the mods' textures) still comes from the server.

- **Packs** (`QcTexturePackManifest`, `QcTexturePackLoader`, `QcTexturePackLibrary`): a folder with `texturepack.json` (format 1, name, description, resolution 16–512 as a power of two, licence, credits, `procedural`, preview) and `textures/<namespace>/<name>.png|json`. Found in `:/texturepacks` (built in), `<data>/texturepacks` and `<mods>/<mod>/texturepacks`; ids `builtin:`, `user:`, `mod:<mod>/`. The loader checks everything at the boundary (only listed plain files, no links or hidden files, file count and sizes, PNG signature and size against the resolution, damaged images, a decoded-memory budget, previews) and turns each problem into a translatable `QcTexturePackProblem`; a bad file is skipped, only a bad manifest makes a pack unusable. A loaded `QcTexturePack` is immutable and shared (`QcTexturePackRef`).
- **Sources** (`QcTextureSources`): per texture the active packs in priority order (image before spec; a `procedural` pack paints the content's definition), then the content; everything scaled to the atlas tile size (pixel-exact when enlarging).
- **HD procedural textures** (`QcProceduralTexture`, `QcTextureDetail`): the 16×16 pattern enlarged with Scale2x on similar colours (per pattern on or off), then grain and a bevel along strong edges; amounts per pattern, `detail` in a definition overrides them. 16× stays bit-identical to before.
- **Atlas** (`QcTextureAtlas`, `QcAtlasLayout`): a grid of cells of 1.25 tiles with a gutter of tile/8 that repeats the edge pixels; UVs measured in eighths of a tile, so the same for every tile size (`sameLayout`). Tiles are drawn in parallel by up to 8 short-lived `QThread`s (half the cores), each writing its own tiles and ending with a release store the caller reads after `wait()`; a thread that cannot start leaves its share to the caller (QtConcurrent's hand-over is invisible to ThreadSanitizer on macOS). The tile size is at most 256 (`Options::maxTileSize`; a 512× pack is shown at 256× with a notice), procedural packs paint at the tile size, not larger. Mip levels by alpha-weighted 2×2 averaging down to tiles of 8 pixels (gutter ≥ 1 pixel); cut-out tiles get their alpha raised per level until the share of drawn texels is back at that of level 0 (`QcAlphaCoverage`). Fully transparent texels carry the colour of the nearest drawn one (`QcAlphaCoverage::fillTransparentColour`, while the tiles are drawn; alpha stays 0), and `QcAtlasLayout::halve` keeps the plain mean of the colours of a fully transparent 2×2 block, so the GPU's blending between mip levels does not darken the edges of plants (E-332). The tile size is the highest pack resolution (stored at most 256), halved until the atlas fits `QcGpuLimits::maxTextureSize()` (8192 until a renderer reported `QRhi::TextureSizeMax`) and 256 MiB.
- **GPU** (`QcAtlasTexture`, app): a mipmapped RGBA8 texture from the first level within `TextureSizeMax` (a level the GPU refuses is retried one smaller, then the magenta placeholder, logged; the world renderer tries once per atlas and draws no world without a texture), the chain continued by halving to 1×1; sampler nearest/nearest with linear blending between mip levels. The world renderer and the character previews (`QcPreviewAtlasCache`) share it.
- **Switching** (`QcTexturePackController`, `GameController.settings.texturePacks`; `QcTextureStackBuild` in clientcore): listing the pack folders (on start and Reload), loading the active packs (reusing loaded ones; at most 384 MiB of decoded images for all active packs), reading changed previews (cached by file time) and building the atlas run in a worker thread; the old atlas stays until `atlasBuilt`. Every change (selection, Reload, entering or leaving a world) raises a generation; a result of an older generation is dropped when it arrives, so nothing waits for a running build and no stale atlas is applied. Only the active packs stay loaded. `QcGameController::applyAtlas` re-uploads the texture, redraws icons and previews and keeps render table and meshes when the layout is unchanged (always, unless the content changed). A world start builds the atlas synchronously (`enterWorld`); leaving the world releases atlas, render table and content (`leaveWorld`). The menu's handbook icons use an atlas with tiles of at most 32 pixels; the menu preview's atlas is built in the background. Item icons use a small mip level (`QcBlockIcon::sourceTileSize` 32; 64-pixel icons above 16×). Settings page `TexturePacksPage.qml` (all pack texts as plain text, E-272), previews through the image provider `image://texturepacks/<id>`. Packs change everything drawn from the atlas; QML-drawn HUD elements (hearts, hunger, hotbar frames, crosshair, buttons) are not part of them (E-297).

## Armour and armour stands

Armour (decisions E-234 to E-239): items with `armour` are worn in four slots (`QcEquipment`, slot numbers 100–103 in the inventory messages). The server (`QcServerInventory`, `QcServerCombat`) checks every move, takes 4 % off armoured damage per point (at most 80 %), wears the pieces and breaks them (`QcArmour`), repairs two worn pieces in the grid (`QcRepair`) and drops armour on death. Others get a player's armour with the spawn (sent again on every change). Drawing: `QcArmourLook` turns worn pieces into `QcEntityMesher::Attachment`s – the boxes of the humanoid reference model a layer covers, grown and cut, plus parts on the bones – that `appendModel` draws with the bones (`Figure::attachments`, `Figure::hiddenBones`); the world, the character preview and armour stands share it. Armour stands are entities of their own (`QcArmourStandManager`, `QcServerStands`, `QcStandCommands`/`QcStandProperties`, `stands.qce`), no creatures: no AI, physics or health; they are synced with their pose (`QcStandPose`) and their cape (in the spawn's `appearance.cape`) and never moved. A cape hangs outside a worn chest layer: `QcFigureLook::armour` sets `ModelLook::capeClearance` from how far the body attachments stand out behind the back (`QcArmourLook::capeClearance`), for players, the preview and stands alike. The showcase shows every set on stands (`QcShowcaseArmourArea`) and a pose demo from structure data.

## Character preview

Decision E-231 (stage 22). `CharacterPreview` (`QcCharacterPreview`, a `QQuickRhiItem`) shows the player's figure as a UI element in the character screen (`CharacterScreen.qml` with `CharacterPreviewPanel.qml` and `CharacterPresets.qml`), the inventory and the main menu's `ProfileCard.qml`. Every frame it builds the figure with `QcPreviewScene::build`, which uses the world's code for other players (`QcFigureLook::player`/`item`, `QcAnimator::animateBody`, `QcEntityMesher::appendModel`); `QcCharacterPreviewRenderer` draws it with the world's entity pipeline and shaders (`QcRenderPipelines`) at full daylight over a transparent background. `QcPreviewCamera` turns the figure (dragging) and zooms (wheel), `QcPreviewPose` gives the animations stand, walk and mine and turns the head towards the mouse pointer (`QcEntityPose::headYaw`) while the window is active. `QcPreviewPacer` lets it draw only while it is shown and at most 30 times a second (the menu's profile card 15); a hidden preview stops its timer. `QcPreviewSource` (`GameController.preview`) hands out the content and atlas (the world's, or in the menu the library content with an atlas built on first use), the look, the held item and the `--preview` hook, and sums the meshing time for the debug display's frame phase "Character preview". Looks and presets: `QcCharacterSettings` (`GameController.settings.character`) with `QcCharacterProfile` (colours on offer, four built-in presets, up to eight own presets stored as `characterPresets/<n>/…` in `settings.ini`, random looks). The server checks every look and name before taking them over (`QcProfileValidation`, E-232).

## Release bundle

`scripts/release.sh` (decisions E-073 to E-076) builds the preset `deploy`, copies `qtcraft.app` to `deploy/QtCraft.app`, adds the example mods under `Contents/Resources/mods`, runs `macdeployqt` with `-qmldir=src/app/qml` (Qt frameworks, QML modules in `Contents/Resources/qml`, plugins in `Contents/PlugIns`: platform, image formats, styles, TLS, multimedia with the FFmpeg backend whose libraries go to `Contents/Frameworks`, `qt.conf`), removes the SQL drivers that need foreign client libraries, signs ad hoc from the inside out and checks the result (otool, required parts, universal executable, signature, four starts of a copy in a temporary directory with audio output and caches kept there: world with the list of loaded images, mod and German texts, Launch Services, x86_64 under Rosetta when installed); it packs `QtCraft-<version>-macOS.zip` and `.dmg`. Inside the bundle nothing is looked up by source or build paths: base content, shaders, QML and translations are Qt resources in the executable, the bundled mods are found relative to the executable (`QcBundledMods::directory`). Player data stays in the application data directory (`~/Library/Application Support/QtCraft/QtCraft`: `settings.ini`, `worlds/`, `mods/`); on the first start, while `mods/` does not exist, the bundled mods are copied there switched off (`QcBundledMods::installDisabled`, a new staging folder `mods.installing-XXXXXX` renamed when complete). Info.plist comes from `cmake/Info.plist.in` (identifier `org.qtcraft.QtCraft`, version from `project()`, build number = UTC build time `YYYY.MMDD.HHMM`, minimum macOS 13.3 from `CMAKE_OSX_DEPLOYMENT_TARGET`, category games, high resolution, copyright, English and German).

All own targets are compiled with `-Wall -Wextra -Wpedantic -Werror -fno-exceptions` (MSVC: `/W4 /WX /EHs-c-`) through the `qc_project_options` interface target. Qt headers are system includes.
